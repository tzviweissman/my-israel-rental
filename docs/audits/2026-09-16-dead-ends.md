## Orphaned capabilities

### New this round

1. **`POST /admin/auto-owner-nudge/run-now` and `GET /admin/auto-owner-nudge/status`
   have no frontend caller.** `backend/routes/admin/chats_nudge.py:525,540`. The
   `status` handler's own docstring says it exists "so the admin Chats tab can render a
   'auto-nudges on · 12h threshold' strip with counts"; `run-now`'s docstring calls
   itself an "admin escape hatch." `frontend/src/components/admin/ChatsTab.jsx` makes
   only 3 API calls (list, reattach, nudge-owner) — the strip and the manual-trigger
   button described in the backend comments were never built.
   **Fix:** build the small status strip + run-now button in `ChatsTab.jsx` the
   docstring already describes — the backend is done and returns exactly the data
   needed (`enabled`, `stale_hours`, `throttle_hours`, last 20 `runs`).

2. **`GET /admin/email/diagnose` has no frontend caller.**
   `backend/routes/admin/events.py:253`. Docstring: "so support can answer \[a
   deliverability question] in one click instead of grepping Mongo shells" — a
   per-user/per-email lookup. `frontend/src/components/admin/EmailHealthTab.jsx`
   renders only aggregate stats and a recent-events list; there's no search box to look
   up one user's email history.
   **Fix:** add a search-by-email/user-id box to `EmailHealthTab.jsx` calling this
   endpoint — small addition, the backend is already built for exactly this.

3. **No in-app control ever calls `POST /marketplace/notification-preferences/snooze`
   (create).** `backend/routes/marketplace/notification_prefs.py:117`.
   `frontend/src/components/dashboard/NotificationSettings.jsx` only reads snoozed
   categories and calls `DELETE .../snooze/{category}` (the "clear" chip) — there is no
   button to snooze a category in the first place from inside the app. The only way a
   snooze gets created today is presumably the magic-link "snooze this" email action
   (`snooze-consume`, wired separately) — a user who wants to proactively snooze rather
   than wait for an email has no way to.
   **Fix:** either add a "snooze this category" action next to each notification type
   in `NotificationSettings.jsx`, or, if email-triggered snoozing is the intended-only
   path, this isn't a bug — but nothing in the code currently says that's a deliberate
   choice, so treat it as open until confirmed.

4. **`POST /marketplace/job-searches/send-digest` has no frontend caller.**
   `backend/routes/marketplace/jobs.py:793`. Comment: "Admin-triggered daily
   digest — kept so a human can force a run." The digest already runs on schedule
   (`jobs_digest_daily_loop`, confirmed registered in `server.py`); this is a manual
   override with no button anywhere. Low severity — the automatic path works — but it's
   dead capacity with an explicit "kept for" rationale that was never finished.
   **Fix:** either wire a "send now" button into whatever admin surface manages job
   digests, or remove the endpoint if the manual-override use case is no longer
   needed.

5. **`GET /admin/properties/{property_id}/blocks` has no frontend caller.**
   `backend/routes/admin/properties_bulk.py:602`. Returns the full admin-block history
   for a property. `frontend/src/components/admin/ListingsTab.jsx` only reads the
   *current* block (`property.active_admin_block`, embedded in the property list
   response) and calls `DELETE /admin/properties/blocks/{block_id}` to lift one — there
   is no history view. Minor: the current-state UI works, only the audit-trail history
   view is missing.
   **Fix:** low priority — add a "block history" expandable row if admins ever ask why
   a listing was blocked before; not urgent.

6. **`POST /notifications/preferences` (`backend/routes/notifications.py:14`) looks
   like dead legacy code, not just an orphaned capability.** File header: "Auto-extracted
   from server.py during the 2026-04 refactor." It stores a `NotificationPreferences`
   document (rental_type/min_bedrooms/max_price/area match filter) to
   `notification_preferences` — a different collection and a different model from the
   `job_notification_preferences` system `NotificationSettings.jsx` actually uses
   (`marketplace/notification_prefs.py`). No frontend code references
   `NotificationPreferences` or posts to `notifications/preferences` anywhere.
   **Fix:** this reads as superseded rather than "never built" — confirm with git
   blame/history whether the old saved-search-alert system this served still has any
   readers of `notification_preferences`, and if not, delete the route and model rather
   than build UI for it.
