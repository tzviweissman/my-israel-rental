# Dead ends — 2026-09-12

Scheduled dead-ends audit, following `.claude/skills/dead-ends/SKILL.md`. Three
parallel passes: (1) a deep dive on the new Orders/courier/delivery feature
(shipped since the last dead-ends audit on 2026-09-03), (2) a forward
link-resolution sweep of the rest of the frontend against the `App.js` route
table, (3) a backward/orphaned-capabilities sweep (model fields, enums,
endpoints, query params, unused components, schedulers). ~300 tool calls total,
cross-referenced against `frontend/src/App.js` and the relevant `backend/routes/*`
guards. Everything found in the 2026-09-03 audit was re-spot-checked and is
still fixed, except one finding (#9 below) that turns out to have been only
half-closed.

No dev server/browser was available this session — every finding below is
static-analysis-confirmed by reading both sides of the call (frontend
source + the backend guard/model it hits), not click-tested. Recommend running
`scripts/screenshot.mjs` / the relevant `scripts/check-*.mjs` against the
items marked high-severity before/after fixing.

## Broken: goes nowhere or errors

### 1. `/terms` link 404s — sits directly on the signup checkbox
`frontend/src/pages/Auth.js:618` and `frontend/src/pages/SignupJoin.jsx:670`
both render `<a href="/terms" target="_blank">` next to "I agree to the
Terms." No `/terms` route exists in `frontend/src/App.js` (confirmed: zero
matches for "terms" there), no `public/terms.html`, nothing in `server.js`.
Opening it renders `NotFound` via the `*` wildcard.
**Fix:** build a `/terms` route/page, point the link at wherever the terms
actually live, or remove the link until one exists. This is a legal-copy
gap, not just a broken link — worth flagging beyond the code fix.

### 2. Google sign-in drops the `redirect` param on every gated route
Verified end to end. Every gated route (`/dashboard`, `/services/post-job`,
`/chat/:id`, `/order/:id`, etc.) sends a signed-out visitor to
`/auth/login?redirect=…` or `/signup?redirect=…` via the `ToAuth` wrapper
(`App.js:71-73`). The **email** sign-in path honors it correctly:
`Auth.js:28-36` reads `redirectParam` and navigates there;
`SignupJoin.jsx:115-118,211,213,720,728` does the same.

The **Google** button does not. `Auth.js:399` renders
`<GoogleSignInButton className="mb-4" />` and `SignupJoin.jsx:543` renders
`<GoogleSignInButton intentRole={...} />` — neither passes a redirect
target, and the component doesn't accept one
(`frontend/src/components/auth/GoogleSignInButton.jsx:26-32` only takes
`intentRole`, forwarded to `useGoogleSignIn().start(intentRole)`).
`useGoogleSignIn.js:56-84`'s `start()` takes no redirect argument, and
`completeGoogleSignIn.js:96-103` hardcodes the post-auth destination purely
by role (`/businesses/add?welcome=1`, `/dashboard?welcome=1`, `/dashboard`).//
So: anyone who reaches a gated route, gets bounced to login/signup with a
`redirect=`, and clicks "Continue with Google" instead of typing
email/password loses their original destination silently — no error, they
just land on a generic dashboard/add-business page.
**Fix:** thread the current `redirect` search param through
`start()` → `completeGoogleSignIn()` and prefer it over the role-based
default. **Severity: high** — every Google-sign-in entry point on the site
is affected, and Google is the faster/more visible option in the UI.

### 3. `/chat/:propertyId` guard is a bare `Navigate`, not `ToAuth` — drops `redirect`
`App.js:385`: `<Route path="/chat/:propertyId" element={user ? <Chat/> : <Navigate to="/auth/login"/>} />`.
Every other gated route uses the `ToAuth` wrapper (`App.js:71-73`), which
appends `?redirect=`. This one doesn't. A signed-out visitor opening a
direct chat link (e.g. a stale session clicking an email notification)
lands on a bare login page and is never returned to the conversation.

### 4. `/payment/success` guard is the same bare-`Navigate` bug
`App.js:387`: `<Route path="/payment/success" element={user ? <PaymentSuccess/> : <Navigate to="/auth/login"/>} />`.
If the session expires mid Stripe/PayPal round trip, the user is dropped on
login with no way back to the success page.
**Fix for #3/#4:** swap the bare `<Navigate>` for `<ToAuth/>`, same as
`/dashboard`, `/services/post-job`, etc.

## Dead-end promises: destination lacks the affordance

### 5. In-platform gig booking has no accept/decline surface anywhere — **high severity**
`booking_mode: 'in_platform'` is settable by a provider in `CreateGig.jsx:689-706`,
and a customer can really request a booking: `GigDetail.jsx:200` posts to
`POST /marketplace/gigs/{gig_id}/book` (`backend/routes/marketplace/gigs.py:1049`).
But `PATCH /marketplace/bookings/{booking_id}` — the only endpoint that can
accept/decline/complete it (`gigs.py:1116`, `BookingPatch.status` in
`shared.py:684`) — has **zero frontend callers** (confirmed:
`rg -rn "marketplace/bookings" frontend/src` returns nothing). There is no
provider-side list of pending gig bookings either: `GET /my-gigs`
(`gigs.py:828`) never returns them. `book_gig` doesn't even notify the
provider on creation — only a halfway-hold reminder and an expiry notice
fire later, and clicking either (`Navigation.js:269-270` → `/dashboard?tab=bookings`)
loads `GET /bookings` (`backend/routes/bookings/crud.py:93`), which is the
**property/sublease** booking collection — a different collection entirely,
so the gig booking is never found there.
**Net effect:** a customer requests an appointment; the provider has no page
anywhere to see it, accept it, or decline it before the hold silently
expires. **Fix:** build the missing accept/decline surface (or route the
notification correctly and add a bookings list), or retire `in_platform`
booking_mode from the gig wizard until it exists.

### 6. Reported/flagged requests: admins can never see them — trust & safety gap
A user can report a request (`POST /marketplace/requests/{id}/report`, wired
from `RequestDetail.jsx`) and posts do get flagged (`needs_review`,
`report_count`). But `GET /admin/request-reports` and
`POST /admin/request-reports/{request_id}` (`backend/routes/admin/marketplace.py:274,346`)
have zero frontend callers, and the count that should surface this,
`posts_awaiting_moderation` (`admin/marketplace.py:266`), is returned by
`GET /admin/attention` but is **not** one of the five rows
`AttentionQueue.jsx:41-85` renders (confirmed by reading the full row list:
`requests-expiring`, `chats-unanswered`, `services-no-photo`,
`businesses-unverified`, `emails-bounced` — moderation isn't among them).
Reports accumulate invisibly forever. **Fix:** add a "posts awaiting
moderation" row to `AttentionQueue` linking to a moderation tab, or build the
moderation queue tab if it doesn't exist.

### 7. Gig `subcategory` has no editor — customer-facing filter chips can never match
`Services.jsx:456-478` renders live subcategory filter chips
(`SUBCATEGORIES[selectedCat]`) for customers to click, and
`GET /marketplace/gigs?subcategory=` is a real, validated backend filter
(`gigs.py:129,179-180`, `_validate_subcategory`). But no provider can ever
set `Gig.subcategory` — `CreateGig.jsx` and `EditListingModal.jsx` never
reference it at all (jobs have a subcategory picker via `PostJob.jsx`/
`EditJobModal.jsx`; gigs don't). A customer filtering by subcategory gets
zero results, forever, for every category. **Fix:** add a subcategory
picker to the gig wizard (mirror the job one), or remove the chips.

### 8. Website order's stated payment method is collected nowhere
`WebsiteOrderIn.pay_by` (`backend/routes/marketplace/orders.py:1667-1670`,
comment: *"How the customer intends to pay… Recorded, never charged"*) is
stored and appended to `notes` (`orders.py:1817-1818,1839`) so it can surface
on the staff board/run sheet/print sheet. But `OrderPage.jsx` — the customer
order form — never sends `pay_by`; there is no input, radio group, or select
for it anywhere in the file (only reference elsewhere is a backend test).
The commit "keeps the store's currency and says how the customer means to
pay" is half-built: currency-keeping works (verified below), the
payment-intent half has no UI. **Fix:** add a picker in `OrderPage.jsx`
(e.g. reading the business's `payment_note`/`payment_links` as options), or
drop the field/comment.

### 9. Sublease `highlight=<id>` is generated but never wired — the 2026-09-03 fix only covers half its own claim
`Navigation.js:275` sends a sublease notification to
`` /dashboard?tab=subleases&highlight=${sublease_id} ``. `Dashboard.js:221`
reads `highlight` and passes it to `<BookingsList>` (line 473) — but
`<SubleasesTab>` (line 415) is rendered with **no** `highlightId` prop, and
`SubleasesTab.jsx` never reads `searchParams`/`highlight` anywhere. The
2026-09-03 audit's resolution note ("`highlight=<booking id>` reaches the
row") is accurate only for bookings — item #4 in that audit named *both*
`?tab=bookings&highlight=` and `?tab=subleases&highlight=`, and the sublease
half was never actually closed. A renter clicking a sublease notification
lands on the right tab with no indication which sublease it's about.
**Fix:** pass `highlightId` into `SubleasesTab` and scroll/ring the matching
row, mirroring `BookingsList`, or stop sending `highlight=` for subleases
until it's wired.

## Wrong destination / minor

### 10. `Auth.js`'s own signup form ignores `redirect` for the provider role
`Auth.js:110-113`: the `mode === 'signup' && role === 'provider'` branch does
`navigate('/businesses/add')` unconditionally, never consulting
`redirectParam` (used correctly by every other branch via
`postAuthDestination`). This is the exact bug fixed in `SignupJoin.jsx:211`
per the 2026-09-03 audit (#6), but the fix was never mirrored into `Auth.js`'s
parallel signup implementation. **Low real-world severity**: `rg "/auth/signup"`
across `frontend/src` finds zero links — every in-app signup CTA goes to
`/signup`/`/join` (`SignupJoin.jsx`) or `ToAuth to="/signup"`. Reachable only
by someone typing `/auth/signup?role=provider…` directly. Worth a one-line
fix for consistency; not user-facing today as far as traced.

### 11. A courier who has accepted an invite can't leave a business from their own side
`POST /marketplace/courier/businesses/{business_id}/leave`
(`backend/routes/marketplace/orders.py:1160-1177`) is fully implemented
(removes the courier, clears `default_courier_user_id` if needed, unassigns
open deliveries) but has no frontend caller anywhere.
`DeliveriesTab.jsx` has Accept/Decline for a *pending* invite, but nothing to
stop delivering for a business once accepted — only the owner's "Remove"
button (`OrdersTab.jsx:1251`) can end the relationship. Found independently
by two of the three passes. **Fix:** add a leave/remove-self action per
business card in `DeliveriesTab.jsx`, or treat this as an accepted gap.

## Orphaned capabilities

- **`GET /admin/marketplace/summary`** (`admin/marketplace.py:124`) — computes
  the exact same three counts (`active_services`, `businesses`,
  `open_requests`) that `GET /admin/metrics` already returns under `stock`
  (`admin/core.py:141-145`), which is what `OverviewTab.jsx:44` actually
  calls. No caller anywhere. **Cleanup, not a user-facing bug** — delete it.
- **`GET/POST /admin/auto-owner-nudge/status,run-now`**
  (`admin/chats_nudge.py:525,540`) — the docstring explicitly promises "the
  admin Chats tab can render a 'auto-nudges on · 12h threshold' strip with
  counts." `ChatsTab.jsx` never calls either endpoint or renders that strip
  (only the manual per-chat nudge is used). Backend built, promise in the
  docstring never kept. Low priority — add the strip or drop the promise.
- **`GET /admin/email/diagnose`** (`admin/events.py:253`) — docstring says
  "support can answer... in one click"; no UI lookup form calls it. Admin-only,
  so this may be an intentional curl-by-engineer tool rather than a missed UI
  feature — flagging as unclear intent, not a confirmed bug.
- **`GET /properties/featured`** (`backend/routes/properties/browse.py:471`) —
  its own comment says it was built to replace `Home.js`'s old pattern of
  fetching the entire catalog and filtering ~8 cards client-side. But
  `useHomeShowcase.js:73` still does exactly that (`axios.get(properties, {limit:200})`
  + client-side filter/sort) and never calls the new endpoint, which has zero
  callers. Low-medium — wire `useHomeShowcase.js` to it or remove it.
- **Scrollcraft build pages have no path to production.** Recent commits built
  full scroll-driven pages for real businesses ("Blazin' Boards", "Michal
  Simkin", "lechem-emek") — these live under `scrollcraft/builds/*`, served
  only on local dev ports gated to `DEV_AUTOLOGIN=1`
  (`backend/server.py:146-151`), and are not referenced anywhere in
  `frontend/src` (confirmed via `rg`, zero hits). The real, live
  `/business/blazin-boards` and `/business/michal-simkin` routes (seeded via
  `backend/scripts/seed_demo_stores.py`) render the generic `BusinessPage.jsx`
  template instead. Several commits' worth of polished, business-specific
  work currently reaches no visitor. **This isn't a small dead end** — worth
  a decision: wire these into the real business-page route (e.g. a
  `custom_page_slug` field selecting the scrollcraft build), or confirm they
  were meant as prototypes and archive them explicitly so future sessions
  don't keep building on an orphaned branch of the UI.
- **Subscription endpoints** (`POST /marketplace/subscription/select-plan,
  upgrade,cancel`, `subscription.py:134,244,386`) — already self-documented
  as intentionally dormant (`CreateGig.jsx:492-494`, `MyGigsTab.jsx:433-435`:
  "listing is free now… kept, dormant"). Not new, no action needed.

Enum tie-in: `BookingPatch.status` (`accepted|declined|completed|cancelled`,
`shared.py:684`) is the enum nothing sends — same root cause as finding #5.
