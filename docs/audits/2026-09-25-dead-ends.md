## Broken: goes nowhere or errors

### 1. `/chat/:propertyId` and `/payment/success` guards drop the destination for anyone who arrives already signed out — via email links and PayPal's redirect, not just in-app navigation

`frontend/src/App.js:435` and `:437`:

```
<Route path="/chat/:propertyId" element={user ? <Chat /> : <Navigate to="/auth/login" />} />
<Route path="/payment/success" element={user ? <PaymentSuccess /> : <Navigate to="/auth/login" />} />
```

Every other gated route in this file uses the `ToAuth` helper (`App.js:74-77`), which
appends `?redirect=<intended path>` so `Auth.js` (confirmed at `Auth.js:25-38,108,113,628`)
sends the user back to where they were headed after sign-in. These two routes use a bare
`<Navigate>` instead, so `redirect` is never set and the user lands on the generic
post-login destination (`/dashboard` or `/businesses/add`) with no way back to the
conversation or receipt they clicked through for.

The code's own comment at `App.js:69-73` says this exact pattern was fixed twice before
("Dead-ends audit 2026-09-03, #3 and #6"), and every in-app JS caller into these two routes
*does* pre-check auth and pass `?redirect=` itself (confirmed: `NotifyMeCard.jsx:49`,
`BusinessPage.jsx:176`, `GigDetail.jsx:610,620,652`, `OrderPage.jsx:349`,
`SubleaseDetail.js:64`, `PropertyDetail.js:279,319`, `WriteReview.jsx:98` all build their own
`/auth/login?redirect=…` before navigating). That is exactly what let `2026-09-13`'s audit
conclude the guard "doesn't reopen … as live dead ends." **But these two routes are also
entry points from outside the React app, which bypass every one of those checks:**

- **Emailed chat links.** `backend/utils/email.py:514,591` and
  `backend/routes/admin/chats_nudge.py:370` build `f"{FRONTEND_URL}/chat/{property_id}"` and
  put it directly in message-notification and owner-nudge emails; `requests.py:922` does the
  same for the requests-board chat link. A recipient who opens that email on a device or
  browser where they aren't currently signed in (different device, cleared storage, expired
  token) hits the bare guard and, after logging in, lands on their dashboard — not the
  conversation the email was about.
- **PayPal's own return redirect.** `backend/routes/payments.py:170,180` sets
  `return_url = f"{FRONTEND_URL}/payment/success"` and hands it to PayPal, which redirects
  the browser there directly after checkout — not through any React `navigate()` call.
  `PaymentSuccess.js:27-29` expects `?orderId=`, `?token=`, or `?flow=` on that URL to know
  which order to show. If the session token expired or was cleared during the PayPal
  detour, the guard drops all three params and the user never sees their receipt after
  logging back in.

**Fix (build the missing affordance):** change both routes to use `<ToAuth />` (or
`<ToAuth to="/auth/login" />`), matching every other gated route in the file — one-line
change per route, already correctly written for every other guard here.

## Dead-end promises: destination lacks the affordance

### 2. `GET /admin/auto-owner-nudge/status` promises an admin Chats-tab status strip that was never built

`backend/routes/admin/chats_nudge.py:525-535`, docstring: *"so the admin Chats tab can
render a 'auto-nudges on · 12h threshold' strip with counts."* Read `ChatsTab.jsx` in full —
it renders a per-conversation manual "Nudge" button (`nudgeOwner`, line 76, posting to
`/admin/chats/nudge-owner`) but has no status strip, no threshold display, and no run
history anywhere in the file. `grep` for `auto-owner-nudge`/`autoNudge`/`AutoNudge` across
`frontend/src` turns up only the *user-facing* opt-out toggle in
`SettingsTab.jsx:28-48,364-395` (a different endpoint, `/user/auto-nudge-opt-out`). The
admin has no visibility into whether the automated nudge sweep is healthy, how many it ran
last, or when — despite the backend explicitly logging that data
(`db.admin_auto_nudge_log`, `chats_nudge.py:516-522`) for exactly this purpose.

This item has appeared in five prior audits (`09-06`, `09-09`, `09-10`, `09-11`, `09-12`) and
is still unfixed today. **Fix:** either build the strip in `ChatsTab.jsx` (the backend data
already exists — this is a UI-only addition), or remove the docstring's promise if the
strip is no longer wanted.

### 3. `GET /businesses/{business_id}/listings` promises to show what deactivating a business would hide — the actual confirm dialog shows a count instead, not what the endpoint returns

`backend/routes/marketplace/businesses.py:676-686`, docstring: *"What deactivating this
business would hide — asked before doing it."* It returns each service's title and status
so an owner can see specifically what disappears. The actual deactivate flow,
`toggleActive()` in `frontend/src/components/dashboard/MyBusinessesTab.jsx:141-168`, never
calls this endpoint — its confirm dialog (line 144-157) uses `biz.gig_count`, a number
already embedded in the business list response, and says only *"Its {{n}} listing(s) stop
showing publicly."* The owner is told how many, never which ones. For an owner running
several services under one business, that is a materially weaker warning than the one the
backend was built to support.

**Fix:** either call `GET /businesses/{id}/listings` in `toggleActive()` and list titles in
the confirm dialog (the backend does this already), or drop the docstring's specific claim
if a count is judged sufficient.

## Orphaned capabilities

### Confirmed dead/superseded (delete-candidates)

- **`POST /notifications/preferences`** (`backend/routes/notifications.py:14-25`, model
  `NotificationPreferences` at `models.py:242-246`: `rental_type`, `min_bedrooms`,
  `max_price`, `area`) — zero frontend callers. `grep` for this path or model across
  `frontend/src` returns nothing. The feature it implements (save a rental alert
  preference) is now fully handled by the separate, actively-used `saved-searches` API
  (`backend/routes/saved_searches.py`, wired through `MyAlertsPopover.jsx` and the
  dashboard alerts tab). Writes to `db.notification_preferences`, a collection nothing
  else reads. Flagged since `09-10`, still present. **Fix: delete the route, model, and
  collection** — this looks like a pre-saved-searches leftover, not a gap to fill.
- **`GET /admin/properties/{property_id}/blocks`** (`backend/routes/admin/properties_bulk.py:601-608`)
  — returns full admin-block history for a property. No frontend caller. The actual
  unblock-confirmation UI (`ListingsTab.jsx:459-481`) reads `property.active_admin_block`,
  a field already embedded on the property object returned by `GET /admin/properties`. An
  admin can see and clear the *current* block but has no way to see a property's *history*
  of admin blocks. Flagged since `09-10`, still present. **Fix: delete**, unless block
  history is wanted, in which case wire this into a details view.
- **`GET /admin/marketplace/summary`** (`backend/routes/admin/marketplace.py:132-146`) — its
  own docstring says *"The counts the Overview row was missing."* They aren't missing:
  `GET /admin/metrics` (`admin/core.py:171-174`) already computes the identical
  `active_listings`/`active_services`/`businesses`/`open_requests` block under `stock`, and
  that is what `OverviewTab.jsx:62,84-87` actually renders. This endpoint duplicates work
  nothing calls. Flagged since `09-13`. **Fix: delete.**

### Dormant by design, flagged as a residual risk

- **`POST /marketplace/subscription/cancel`, `/upgrade`, `/select-plan`, and
  `GET /subscription/plans`** (`backend/routes/marketplace/subscription.py:38,134,244,386`)
  — zero live frontend callers. `MyGigsTab.jsx:434-436,479-481,498-499` documents this
  explicitly in comments: the Pro-plan/subscription pricing tier was removed ("listing is
  free, so there is nothing to upgrade to and nothing to cancel"), and the endpoints were
  left in place rather than deleted. Only `/subscription/activate` (called from
  `PaymentSuccess.js:43`, still needed for the one-time PayPal approval step) and the
  admin-only `plans/status` + `plans/bootstrap` (`PayPalPlansPanel.jsx:33,65`) are still
  called. This is a deliberate pivot, not a bug in the code I read. **The risk worth
  flagging:** if any provider record from before the pivot still carries
  `subscription_status: "active"` with a live `paypal_subscription_id`, PayPal will keep
  billing them on a recurring basis, and there is now no UI path anywhere in the app for
  that person to cancel it themselves — `/subscription/cancel` exists and works but nothing
  can reach it. I found no migration script under `backend/scripts/` that bulk-cancelled
  outstanding subscriptions when the pivot happened. **I could not check** whether any real
  account is currently in this state — that requires a production-database query, which is
  outside a read-only audit and guarded by this repo's own rules against touching prod data
  ad hoc. **Fix:** confirm via a one-off *read-only* query whether any `marketplace_providers`
  row has `subscription_status: "active"`; if none, delete the four dormant routes; if any
  do, cancel them via the existing (working) endpoint by hand and then delete the routes.
