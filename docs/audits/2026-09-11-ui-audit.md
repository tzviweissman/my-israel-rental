## Should fix

### 2. `--copy-h` is a hardcoded measurement of a headline that just changed

`frontend/src/styles/home-v2.css:450`, `:458`, `:549`

```css
.hv2-hero--film { height: 100svh; min-height: 640px; --copy-h: 470px; }   /* ≤1000px */
.hv2-hero--film { --copy-h: 432px; }                                       /* ≤760px  */
.hv2-hero--film .hv2-seq { inset-block-start: var(--copy-h); height: auto; }
```

Below 1000px this is not just a scrim boundary - the film's **top edge** is pinned
to it. The comment at `:446-449` records where the number came from: *"The copy is
a fixed pixel height (it ends at about 420px, the add-your-business link last)."*
That measurement was taken against the previous headline. `6e97bdc0` replaced the
headline, and nothing in the three commits re-measures `--copy-h`.

The headline is `clamp(38px, 6.2vw, 78px)` at `line-height: 1.02` inside a
`max-width: 520px` column (`:437`), so its rendered height is a function of how
many lines the new string wraps to - and that differs between
`'Grow. Build. Any revenue stream'` and `'צמחו. בנו. כל מקור הכנסה'`. One extra
wrapped line at the 768 breakpoint is ~48px, which is more headroom than the
50px the comment leaves. If the copy overruns, the CTA row and the
add-your-business link render on top of the video rather than on white.

**I could not measure this** - see "Not checked". The check is one screenshot pass.

**Exact fix:** run `node scripts/screenshot.mjs` at 768 and 375 in both LTR and
RTL and read the copy block's `getBoundingClientRect().bottom`. If it exceeds
`--copy-h` in either language, either raise the two constants to the larger of
the two languages, or replace the constant outright: give `.hv2-hero-inner > div`
wrappers a wrapping element, measure it with the existing
`frontend/src/hooks/useElementHeight.js`, and write the result to `--copy-h` as an
inline custom property. The hook already exists; this stops being a number that
goes stale every time the copy changes.

### 3. The 2-second start deadline is applied to a phone path that is forbidden to prebuffer

`frontend/src/components/home/SequenceHero.jsx:71` and `:173`

```js
const START_DEADLINE_MS = 2000;
...
preload={i === 0 ? (phone ? 'none' : 'auto') : armed >= i ? 'auto' : 'none'}
```

and the bail-out at `:129-133`:

```js
const bail = window.setTimeout(() => {
  if (!first.currentTime) setFailed(true);
}, START_DEADLINE_MS);
```

The same 2000ms budget governs two non-comparable starting conditions. On desktop
clip 1 is `preload='auto'`, so the browser has been fetching since parse and 2s is
generous. On a phone clip 1 is `preload='none'`, so **no byte is requested until
`playWhenAllowed` runs inside the effect** - the clock and the download start
together, and the budget has to cover connection setup plus enough of a 567 KB
file to decode frame one, on cellular.

When it overruns, `setFailed(true)` is permanent: the resize effect at `:115-120`
deliberately does not reset `failed`. A phone visitor on a merely slow connection
gets the end card for the whole session, and the 32-second film they were meant to
see never plays. That is a false positive in the exact case the fallback was
written to protect.

**Exact fix:** derive the deadline from the starting condition rather than fixing
it. At `:71`:

```js
const START_DEADLINE_MS = 2000;        // preload='auto' - already buffering
const COLD_START_DEADLINE_MS = 6000;   // preload='none' - fetch begins at play()
```

and at `:129` use `phone ? COLD_START_DEADLINE_MS : START_DEADLINE_MS`. Better
still, cancel the timer on the first `loadeddata` rather than only on `playing`, so
a video that has arrived but not yet been allowed to start is not counted as a
failure at all.

nothing else in the foot column moves.

### 7. The logo mark ships without dimensions

## Improvement of the night

**Mechanism: banner blindness** (Benway & Lane, 1998; sustained in eye-tracking
work since). People learn the *visual signature* of advertising - full-bleed,
top-of-page, animated, abstract, product-free - and stop fixating on regions
carrying it, including when the region holds the thing they came for. The failure
is not "they disliked it"; it is that the region is never looked at, so its content
is never evaluated. It is not one of the nine mechanisms already spent here: halo
(09-01), peak-end (09-02), loss aversion (09-03), denominator neglect (09-04-2),
endowed progress (09-05), cognitive fluency (09-06), ambiguity aversion (09-07),
automation bias (09-08), implementation intentions (09-09).

**Surface:** the `/home-preview` hero - `frontend/src/pages/HomePreview.jsx:169-218`
and `frontend/src/components/home/SequenceHero.jsx`.

**Why now:** this window's change moved the hero *toward* every one of those cues at
once. The page's own docblock still describes what it replaced:

> `HomePreview.jsx:9-13` - *"The hero is built from what is actually on the site...
> A visitor sees the site's own supply in the first second instead of generated
> stills."*

That is now exactly backwards. The first screen is 32 seconds of generated abstract
glass, and the site's supply does not appear until the visitor has scrolled past it.
Note this is not an argument against the film - it is a good film, and the
composition deliberately clears space.

**What to change:** put one real listing inside the space the film already leaves
empty. `useHomeShowcase()` is already called at `HomePreview.jsx:97` and already
returns `rentals`, so `rentals[0]` costs no extra request. The CSS has already
*measured* the clear band - `home-v2.css:503-506` records it as flat white,
"YMIN 232, saturation 0, from 44% to 59% of the width", which is where
`.hv2-seq-mark` currently sits at `:511-514`.

Render a single `StaysCard` (already imported, `:47`) in that band, at the hero's
existing `z-index: 2`, revealed on the same `settled` flag that currently fades in
the mark. Let the mark move to the foot of the copy column, where it is decoration
rather than the only concrete object on the screen. On the `≤1000px` stacked layout
(`:536-563`) the band is the inline-start side of the film and the card goes there
instead.

Every figure on the card - price, area, bed count - comes from the listing record
via the component that already renders it elsewhere on this page. Nothing is
invented, nothing is aggregated, and there is no count to get wrong.

**What I would expect to see if it worked:** first click within the hero landing on
a listing rather than on the nav or scrolling straight past; and scroll-depth past
the hero returning toward what the corridor version got. Both are measurable with
instrumentation the page already carries - the hero CTAs have `data-testid`
attributes at `:202`, `:209` and `:213`, and the gallery cards at `:430` already
record `data-href`.

**What would falsify it:** if hero CTA click-through is already at or above the
corridor version's, banner blindness is not what is happening here and this should
not be built.
