# Dead ends - 2026-09-22

Full dead-ends audit per `.claude/skills/dead-ends/SKILL.md`: route table
(`frontend/src/App.js`), forward link resolution (366 `<Link|to=|navigate(|href=|window.location`
sites in `frontend/src`), backward promise-to-destination (checklists,
empty-state CTAs, onboarding, email deep-links), and orphaned capabilities
(332 backend routes cross-referenced against every frontend caller, plus
enum values, unused query params, and an orphaned-component scan).

**Context:** this repo has been through eleven prior dead-ends audits since
2026-09-03. Every canonical example named in the audit brief itself — the
"Message on MyIsraelRental" 400, `_normalize_category` being uncalled,
`GigPatch.status: paused` with no button, the Requests board's unsent
`condition`/`min_price`/`max_price`/`include_sold`, the two admin
moderation endpoints, the jobs-digest scheduler — is **already fixed and
verified working today** (evidence in the relevant section below). The
`?tab=`/`?details=`/`?services=`/`?edit=`/`?highlight=`/`?section=` deep-link
family across the dashboard, checklist and notification system is also
fully wired. This audit's findings are therefore narrower and mostly
carried forward from the 2026-09-12/09-14 audits, independently
re-verified against today's code (one was found newly fixed since 09-14;
the rest are still open — see each entry).

None found. Every `navigate()`/`<Link>`/`href` target resolved against the
route table in `frontend/src/App.js:404-527`, every anchor target existed,

None found live. All "add/upload/set/complete" prompts checked (setup

## Wrong destination

- **`frontend/src/pages/Auth.js:113-118`** — inside the
  `mode === 'signup' && formData.role === 'provider'` branch, the redirect
  is hardcoded to `navigate('/businesses/add')` instead of
  `navigate(destination)` (the variable every other branch in the same
  function uses three lines below, and the pattern `SignupJoin.jsx:211`
  uses: `navigate(redirectParam || '/businesses/add')`). An explicit
  `?redirect=` on a provider-signup URL is silently dropped. **Confirmed
  still present today** (first flagged 2026-09-14, unfixed since).
  Low severity in practice: no in-app control links to `/auth/signup`
  directly (every real entry point is `/signup` or `/join` via
  `SignupJoin.jsx`, which gets this right) — only reachable via a
  hand-typed or externally-bookmarked URL. **Fix:** change
  `navigate('/businesses/add')` → `navigate(destination)` on line 116.

- **`frontend/src/pages/Auth.js:621`** — `<a href="/terms" target="_blank">`
  has no `rel` attribute. Same-origin target, so the `window.opener`
  security risk doesn't apply, but it's the one inconsistent
  `target="_blank"` anchor across the frontend — the equivalent Terms link
  in `SignupJoin.jsx:670` correctly carries `rel="noreferrer"`. **Confirmed
  still present today** (also first flagged 2026-09-14). **Fix:** add
  `rel="noreferrer"` to match.

## Orphaned capabilities

**Backend routes with no frontend caller** (confirmed today by checking
every zero/near-zero-hit route from a full 332-route sweep, not just
grepping the literal path):

- **`POST /marketplace/subscription/cancel`, `/upgrade`, `/select-plan`**
  (`backend/routes/marketplace/subscription.py:134,244,386`) — dormant.
  Confirmed by the frontend's own comments at the exact call sites that
  used to exist: `MyGigsTab.jsx:434-436` ("upgrade() and cancelPro() lived
  here — they POSTed to /marketplace/subscription/upgrade and /cancel and
  handed off to PayPal. Both endpoints still exist server-side, dormant.")
  and `CreateGig.jsx:554-556` ("Publishing used to be followed by
  /subscription/select-plan... Listing is free, so publishing now ends at
  the gig itself."). This is a deliberate business-model pivot (listing is
  now free, per `CLAUDE.md`), not an accidental regression, **but** any
  provider from before the pivot who still has an active PayPal
  subscription now has no in-app way to cancel it — they'd need to email
  support or go to PayPal directly. `GET /subscription/plans` is similarly
  unused (`WhyList.jsx:211-213` explicitly documents why — pricing section
  was replaced with a flat "free to list" message). **Fix:** either delete
  the three dormant endpoints (cleanup, the honest move given the business
  model), or — if any legacy subscriber might still exist — keep `/cancel`
  only and wire a "Cancel subscription" action into Settings for the edge
  case, dropping `/upgrade` and `/select-plan` for good.

- **`GET/POST /admin/auto-owner-nudge/status`, `/run-now`**
  (`backend/routes/admin/chats_nudge.py:525,540`) — the docstrings
  explicitly promise a UI: `/status`'s docstring says "so the admin Chats
  tab can render a 'auto-nudges on · 12h threshold' strip with counts."
  `frontend/src/components/admin/ChatsTab.jsx` has zero references to
  `auto-owner-nudge`, `stale_hours`, `throttle_hours`, or `runs` — no strip
  exists. The background loop (`server.py:328-337`) calls the underlying
  pass automatically, so the feature works without an admin ever seeing
  it — this endpoint pair is purely a documented-but-never-built admin
  visibility/manual-trigger UI. **Confirmed still open** (first flagged
  2026-09-12). **Fix:** build the strip described in the docstring, or
  delete the two endpoints and the promise in the comment.

- **`POST /marketplace/courier/businesses/{business_id}/leave`**
  (`backend/routes/marketplace/orders.py:1373`) — fully implemented
  (removes the courier from the roster, clears them as default courier,
  un-assigns their open deliveries) but has no UI caller. It's reused
  server-side by `POST /courier/invites/{business_id}/decline`
  (`orders.py:1368-1370`, wired via `DeliveriesTab.jsx:69` — but only for a
  *pending* invite). Read all 363 lines of `DeliveriesTab.jsx`: `me.businesses`
  (the list of businesses a courier already delivers for) is rendered only
  as inline text (line 97-99) — never as a list with a per-item action. A
  courier who has **accepted** an invite has no self-service way to stop
  delivering for that business; only the business owner can remove them.
  **Confirmed still open** (first flagged 2026-09-14, unfixed since).
  **Fix:** render `me.businesses` as a small list with a "Stop delivering
  for this business" button calling the existing endpoint — the backend
  side is already correct.

- **`GET /admin/email/diagnose`** (`backend/routes/admin/events.py:268`) —
  docstring: "support can answer 'why didn't user X get the email?' in one
  click instead of grepping Mongo shells." No admin UI lookup form calls
  it — `EmailHealthTab.jsx` (the admin email panel) has zero references to
  `diagnose`, `email/diagnose`, or a per-user search box; it only renders
  the aggregate `/admin/email-health` summary. **Confirmed still open**
  (first flagged 2026-09-12, still "unclear intent" there — today's check
  confirms there is genuinely no UI, so this is a real gap, not just an
  admin-CLI tool: the docstring's own framing is "one click," which implies
  a UI was intended). **Fix:** add a small email/user-id lookup box to
  `EmailHealthTab.jsx`, or reword the docstring to say this is a
  curl-by-engineer tool if that's the actual intent.

- **`GET /properties/featured`** (`backend/routes/properties/browse.py:471`) —
  admin-curated, server-optimized (8 lean rows vs. the full catalog) list
  of featured properties, explicitly built to replace client-side featured
  selection ("Mirrors the client-side selection `Home.js#fetchFeaturedProperties`
  used to do"). The **live** home page (`HomePreview.jsx`, via
  `useHomeShowcase.js:64`) instead fetches up to 200 full property rows
  from `GET /properties?limit=200` and sorts by `is_featured` client-side
  (`useHomeShowcase.js:150-151`). The dedicated lean endpoint this was
  built to replace that work with is never called. **Confirmed still open**
  (first flagged 2026-09-14). Performance-relevant, not just a UI gap: the
  home page downloads ~25x more property data than the endpoint that
  already exists for this exact purpose would require. **Fix:** point
  `useHomeShowcase.js`'s featured-rail source at `/properties/featured`
  instead of sorting the full `/properties` fetch, or delete the unused
  endpoint if the client-side approach is now considered good enough.

- **`GET /businesses/{business_id}/listings`**
  (`backend/routes/marketplace/businesses.py:676`) — docstring: "What
  deactivating this business would hide — asked before doing it," built
  for the deactivate-confirmation dialog described in
  `MyBusinessesTab.jsx`'s file header comment. In the actual
  implementation (`MyBusinessesTab.jsx:137-164`, `toggleActive`), the
  confirm dialog gets its count from the `gig_count` field already present
  on the business list row (`_public()` in `businesses.py:269`) instead of
  calling this endpoint — so the promise ("say how many listings
  disappear") is genuinely kept, just through a different, simpler
  mechanism. This endpoint (which returns full listing titles+statuses,
  not just a count) is dead code, not a broken promise. **Fix:** delete
  it, or repurpose it if a future version of the confirm wants to name the
  specific listings rather than just a count.

- **`RequestIn.furnished` / `RequestIn.subcategory`**
  (`backend/routes/marketplace/requests.py:205,197`) — accepted by the
  API and returned in listings (`RequestsBoard.jsx:158` reads
  `r.subcategory`/`r.rental_kind` for display), but `PostRequest.jsx` (the
  only place a request is created) has **zero** references to `furnished`
  or `subcategory` anywhere in its form — grep confirms no field sets
  either. A rental-type request can never specify "furnished," and a
  service-type request can never specify a subcategory, despite the board
  being able to display both if a record had them. **Confirmed still open**
  (first flagged 2026-09-08/09-14, unfixed since). **Fix:** add a
  furnished toggle to the rental branch and a subcategory picker to the
  service branch of `PostRequest.jsx`, matching the pattern already used
  for `category` there.

- **`WebsiteOrderIn.pay_by`** (`backend/routes/marketplace/orders.py:1898`,
  read at 2049-2050 to append "Pays by: X" to the order's internal notes)
  has no frontend setter — `OrderPage.jsx`'s POST body has no payment-method
  field; the page only shows a static `payment_note` display. **Confirmed
  still open** (first flagged 2026-09-14). Minor: optional field, and the
  order still completes without it.

- **`checkin_time` / `checkout_time`** (`backend/routes/properties/shared.py:29`)
  — settable only through `BulkEditModal.jsx` (multi-listing bulk editor);
  confirmed today that `AddPropertyModal.jsx` (the single-listing add/edit
  form) has zero references to either field. An owner with one listing who
  wants a specific check-in/check-out time has to go through the bulk-edit
  flow for a single property. **Confirmed still open** (first flagged
  2026-09-08/09-14).

- **`GET /admin/gigs` `status` query param** (`?status=published|draft|unpublished`,
  `backend/routes/admin/marketplace.py:42`) — confirmed today that
  `ServicesTab.jsx:52-57` only ever sends `q` (search text); the `filter`
  state used for the "no-photo"/"not-verified" chips is applied
  **client-side** after fetching the (up to 100-row) unfiltered list. The
  admin can't ask the API for just draft or just unpublished gigs.
  **Confirmed still open** (first flagged 2026-09-14).

## Not checked (and why)

- **No click-through / browser verification.** No running dev server or
  browser was available in this environment; every finding above is
  static analysis (grep + route-table cross-reference + reading both
  sides of each call), not a live repro. Per the brief's Part 5, this is
  acceptable when static evidence is unambiguous (file:line + exact
  destination code), which every finding above has. If a live repro is
  wanted before fixing, prioritize the courier-leave gap and the
  `/properties/featured` performance gap — those have the most user/perf
  impact.
- **`scripts/screenshot.mjs` and `scripts/check-*.mjs`** were not run.
  Given the volume of static evidence already gathered and no dev server
  running, standing up the infra wasn't attempted — consistent with prior
  audits' method (09-14 also skipped this).
- **Bilingual (RTL/Hebrew) rendering** of any of the affected screens was
  not checked — out of scope for a dead-ends audit per the skill, and
  covered by the separate `myisraelrental-frontend`/`site-audit` skills.
- **Admin-only surfaces requiring an actual admin account** (Smart Lists
  bulk actions, the Import tab's full flow, impersonation) were checked
  for route/caller wiring only, not click-traced end-to-end — low risk,
  internal-only surfaces.
