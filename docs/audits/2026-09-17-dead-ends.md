## Orphaned capabilities

**New this run:**

- **`posts_awaiting_moderation`** (`backend/routes/admin/marketplace.py:274`,
  returned by `GET /admin/attention`) has **no frontend consumer at all** —
  confirmed via `grep -rn "posts_awaiting_moderation" frontend/src`, which
  matches only a doc-comment in `RequestReportsTab.jsx` describing the old
  bug, never a read of the field. `AttentionQueue.jsx`'s `rows` array (lines
  43-92) has entries for `requests_expiring_unanswered`, `chats_unanswered`,
  `services_without_photo`, `businesses_unverified`, and
  `emails_bounced_7d` — no row for this one. **Severity: minor, not a dead
  end** — the destination it would have pointed to (the "Requests" nav tab)
  is already a permanent, always-visible tab and is also linked from the
  Overview KPI card, so an admin doesn't need the attention-queue count to
  find the moderation queue. But the backend is computing a number nothing
  shows, which is exactly the shape of bug this skill exists to catch before
  it compounds. **Fix:** either add the fifth attention-queue row (`go:
  'requests'`, matching the other four), or remove the field from the
  response and say why in a comment — both are legitimate; the field
  existing unread is the only real problem.

- **`frontend/src/components/dashboard/DeliveriesTab.jsx`, `StopCard.submit`
  (lines 177-198)** — calls `PATCH
  /marketplace/courier/deliveries/{id}/status`, which routes through the
  same `_transition()` helper that `848a6ba` (this window) fixed to return
  409 with `"Someone else moved this order to 'X' a moment ago. Refresh to
  see where it is now."` on a status race. `OrdersTab.jsx` (the
  owner/counter-staff view of the *same* underlying transition) explicitly
  handles this: `if (err?.response?.status === 409) load();` (line 230) —
  reloads so the UI reflects reality. `DeliveriesTab.jsx`'s `submit()` only
  does `toast.error(err?.response?.data?.detail || …)` (line 194) — the
  courier sees the correct message but the card's local state (`mode`,
  the stale `s.status` from props) is never refreshed, so a courier who
  taps "Delivered" into a race could retry against the same stale card.
  **Severity: minor** — a courier is normally the sole person moving their
  own delivery, so the race window this closes is narrow (another surface,
  e.g. the owner dashboard, would need to move the *same* order in the same
  few seconds). Adjacent to a money/order-status fix, which is why it's
  worth flagging even at low probability. **Fix:** call `onChanged()` (or an
  equivalent reload) in the `catch` when `err?.response?.status === 409`,
  matching `OrdersTab.jsx`'s pattern.
