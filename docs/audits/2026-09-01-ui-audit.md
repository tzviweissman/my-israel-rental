## Blockers

### 1. Every new input has no visible focus indicator at all

`frontend/src/components/requests/ItemFilters.jsx:296-297` and `:307-308`
`frontend/src/components/requests/ItemSpecifics.jsx:45` (used at `:169` and `:190`)

All four new inputs carry `outline-none focus:border-[var(--brand-primary)]` **and**
an inline `style={{ borderColor: 'var(--brand-border)' }}`. An inline style beats a
class declaration regardless of specificity, and `frontend/tailwind.config.js` sets
no `important` flag (checked). So the focus border never applies, and `outline-none`
already removed the browser default. The result is a keyboard user tabbing through
the price range and every item-specifics text and number field with zero indication
of where they are. WCAG 2.4.7 (A).

This is the exact bug the board already documents against itself at
`RequestsBoard.jsx:604`: *"The input sets `outline-none` and nothing replaced it."*

**Fix:** delete `borderColor` from the four inline `style` objects and put it in the
class list instead, so the focus variant can win:

```jsx
// ItemFilters.jsx:296 and :307
className="w-24 rounded-xl border border-[var(--brand-border)] bg-white px-3 py-1.5 text-xs outline-none focus:border-[var(--brand-primary)] focus:ring-2 focus:ring-[var(--brand-primary)]/30"
// and drop  style={{ borderColor: 'var(--brand-border)' }}  from :297 and :308

// ItemSpecifics.jsx:45
const inputCls = 'w-full rounded-xl border border-[var(--brand-border)] bg-white px-4 py-3 text-sm outline-none focus:border-[var(--brand-primary)] focus:ring-2 focus:ring-[var(--brand-primary)]/30';
// and drop  style={{ borderColor: 'var(--brand-border)' }}  from :169 and :190
```

A 1px border swap alone measures 4.83:1 between the two states (`#E1D8C6` vs
`#1E5F8C`), which clears the 3:1 non-text minimum, but a 1px hairline is a weak
indicator; the ring is what makes it findable.

### 4. The facet counts fail contrast at 2.97:1

`frontend/src/components/requests/ItemFilters.jsx:77`

```jsx
<bdi className="font-normal" style={{ opacity: active ? 0.75 : 0.55 }}>{n}</bdi>
```

Measured (sRGB, WCAG 2.x formula):

| State | Composite | Ratio | Verdict |
|---|---|---|---|
| Inactive chip: `text-gray-700` `#374151` at 55% on `#FFFFFF` | `#919BA0`-ish | **2.97:1** | fails 4.5:1 |
| Active chip: `#FFFFFF` at 75% on `#1E5F8C` | | 4.64:1 | passes |

The number is 12px, so the large-text 3:1 allowance does not apply. This is the one
piece of text the whole component exists to deliver, and it is the least legible
thing in the panel.

**Fix:** drop the opacity and use a token colour, which also removes the
active/inactive fork:

```jsx
const Count = ({ n, active }) => (
  <bdi className="font-normal" style={{ color: active ? '#FFFFFF' : 'var(--brand-muted)' }}>{n}</bdi>
);
```

`--brand-muted` `#6B6459` on white measures **5.85:1**; white on `--brand-primary`
measures **6.84:1**. The weight difference (`font-normal` against the chip's
`font-semibold`) still carries the visual separation the opacity was there for.

### 5. A second query builder, in the module written to prevent exactly that

`frontend/src/components/requests/ItemFilters.jsx:127-142` versus
`frontend/src/components/requests/itemFilterParams.js:66-89`

`itemFilterParams.js` opens with *"WHY IT IS SHARED RATHER THAN BUILT TWICE... Two
builders drift the moment one of them gains a parameter, and the symptom is the

`RequestsBoard.jsx:474` uses `buildRequestParams`. `ItemFilters.jsx` re-implements
it inline. The two agree today, byte for byte, which is why this is a should-fix and

**Fix:** replace the IIFE at `:127-142` with the shared builder:

```jsx
import { readAttrs, writeAttrs, ITEM_PARAM_KEYS, buildRequestParams } from './itemFilterParams';
// ...
const facetQuery = buildRequestParams(searchParams, 'item').toString();
```

`buildRequestParams` already emits `request_type`, `post_kind` from `side`, `area`,
`q`, every `ITEM_PARAM_KEYS` entry and the `attr` pairs, which is the identical set.

### 6. Filter chips have no accessible grouping, and the count fuses into the name

`frontend/src/components/requests/ItemFilters.jsx:87-93` (the `Row` component)

`Row` renders its label as a bare `<p>` with no programmatic link to the chips
underneath. A screen reader user landing on a chip hears "110V 14, toggle button"
with no indication that it belongs to Voltage, and with the facet count glued onto
the option name.

**Fix:**

```jsx
let rowSeq = 0;
const Row = ({ label, children, testid }) => {
  const id = React.useMemo(() => `item-filter-row-${++rowSeq}`, []);
  return (
    <div data-testid={testid} role="group" aria-labelledby={id}>
      <p id={id} className="text-[11px] font-semibold uppercase tracking-wide mb-1.5" style={{ color: 'var(--brand-muted)' }}>
        {label}
      </p>
      <div className="flex flex-wrap gap-2">{children}</div>
    </div>
  );
};
```

and on the `Chip` button at `:97-110`, name the count for assistive tech:

```jsx
aria-label={count !== null && count !== undefined ? `${label} (${count})` : undefined}
```

### 9. Disabled chips are effectively invisible

`ItemFilters.jsx:105` and `:433`: `color: var(--brand-muted)` with `opacity: 0.45`
measures **1.96:1** on white. The count inside one compounds to
`0.45 × 0.55` = 0.2475 effective alpha, **1.41:1**.

Disabled controls are exempt from WCAG 1.4.3, so this is not a violation. It is
still below the point where a sighted user can read which option is dead versus
which is simply pale, and the component's own reasoning is that a disabled chip
should "say 'not here' and stay where it was" - which requires being readable.

**Fix:** raise to `opacity: 0.7` (`--brand-muted` at 70% on white = 3.44:1, legible,
still unmistakably inactive) and drop the nested opacity on `Count` per finding 4.

## Improvement of the night

**Mechanism: the halo effect.** The first impression of a page colours the
evaluation of everything that follows it, and it forms before any of the content is
read.

**Surface:** the category row of the goods filter panel, `/marketplace`.
**File:** `frontend/src/components/requests/ItemFilters.jsx:263-274`.

The panel renders `schema.categories` in the order the Python taxonomy declares
them, each with its exact facet count, each zero-count option disabled. Every one
of those decisions is right, and on a mature board the result is excellent. On a
board that launched this week, most categories have nothing behind them, so the
first thing a buyer sees at `/marketplace` is a row of greyed-out words with `0`
beside them. The honest-counts rule and the launch inventory combine into a
first impression of "this place is empty" - which then discounts the listings that
*are* there, further down.

**What to change.** Order the category chips by their own facet count, descending,
with zero-count options last and schema order breaking ties. Nothing is hidden,
nothing is invented, every count still comes from `/requests/facets`; the live
inventory simply leads and the dead options fall to the end of the wrap where they
read as "also possible" rather than as the headline.

One constraint, which comes from the component's own reasoning about hidden zeros
("the row reflows on every click and the eye loses its place"): the order must be
computed **once**, from the first facet response of the session, and frozen. If it
re-sorts on every refetch, chips move under the user's finger as they filter, which
is a worse problem than the one being solved. Concretely, hold the initial ordering
in a `useRef` keyed on the unfiltered response and reuse it for the life of the
mount.

```jsx
const catOrder = React.useRef(null);
// after the first successful facets response:
if (!catOrder.current && facets?.exact) {
  const c = facets.facets?.category || {};
  catOrder.current = [...(schema.categories || [])]
    .sort((a, b) => (c[b.slug] || 0) - (c[a.slug] || 0));
}
const orderedCategories = catOrder.current || schema.categories || [];
```

**What I would expect to see if it worked.** On the first paint of `/marketplace`,
every chip in the leading (start-edge) half of the category row carries a non-zero
count, in both LTR and RTL. The behavioural read is the click-through rate from the
board's first screen into any category filter: today a buyer's first available
action is disabled, and the measurable claim is that it stops being so. I have no
baseline for that rate and am not inventing one; instrument it before and after, or
treat this as a first-impression fix on its own terms.

This is not in `docs/goods-marketplace-psychology.md` (B1-B6, T1-T6, §6, §7, §8 all
checked) nor in `docs/research-driven-changes.md`, and `docs/audits/` did not exist
before tonight, so nothing has been proposed here previously.
