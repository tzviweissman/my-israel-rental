## Improvement of the night

**Mechanism: self-efficacy through enactive mastery (Bandura, 1977, "Self-efficacy: Toward a Unifying
Theory of Behavioral Change").** Of the four sources of a person's belief that they can work a tool, the
strongest by a wide margin is having done it once and seen it work; description and encouragement are weak
substitutes. People abandon tools they have configured but never seen act. Distinct from 09-21's trust
calibration (feedback after a rule fires on its own) and 09-08's automation bias: this is the moment
BEFORE any real event, when the owner has just saved a rule and the screen says "Has not run yet"
(`AutomationsPanel.jsx:293`). For an appointment or lead rule that sentence can stay true for days.
Not one of the thirteen mechanisms already used in `docs/audits/`.

**Surface:** the rule row, `AutomationsPanel.jsx:298-304`, and `backend/routes/marketplace/automations.py`
`run_automation` (`:681-700`), which today allows a by-hand run only for `manual.reorder` and `schedule`.

**Change:** a `Try it` button on every rule whose action is `notify_me` or `message_customer`, next to the
existing `Send now`. It runs the rule with a synthetic event `{"type": "test", "by": user_id}` and delivers to
the **owner only**: `notify_me` behaves exactly as live (the owner's bell rings, the email arrives); for
`message_customer` the customer copy is sent to the owner's own bell and email with the subject the customer
would see, so they read their own words as the customer will. `send_order` is excluded: a test must never
create a real order. The run is recorded with `result="tested"` and shown in "What automations did" as
"{{name}} was tried" so the log stays honest; `tested` is not added to `DID_SOMETHING`, so it never counts as
a run or blocks the once-per-source rule. Four keys (`automations.tryIt`, `automations.tried`,
`automations.runTested`, and the test email subject) in `en.js` and `he.js`.

**What you would expect to see if it worked:** among rules created in a week, a lower share deleted or
switched `enabled:false` before their first real run (both are already recorded: `automation_runs` and the
PATCH history), and a shorter median time from `created_at` to the first `notified`/`messaged` run that is
left enabled. Both are counts from real records; if the numbers are not there, the line does not render.
