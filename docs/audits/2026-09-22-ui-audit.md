## Blockers

1. **Em-dash in a `<title>` tag - hard ban, ships to the browser tab and every social share card.**
   `frontend/src/pages/GrowthGuide.jsx:35`
   ```js
   title={`${t('guide.metaTitle', 'How this site grows your business')} — MyIsraelRental`}
   ```
   `PageMeta.jsx` puts this string in `<title>`, `og:title` and `twitter:title` (`frontend/src/components/PageMeta.jsx:55,66,71`). taste-skill §9.G bans `—` outright, everywhere, with no "in the title bar is fine" exception. Fix: `${...} - MyIsraelRental` (regular hyphen). Note: the same pattern already exists at `frontend/src/pages/WhatYouCanDo.jsx:39` (pre-existing, outside this window) - the new file copied a bug that was already live rather than introducing a new one, but it's still new code shipping the ban violation.

2. **New primary tour buttons are solid blue with white text at 3.62:1 contrast, and it's the wrong button style.**
   `frontend/src/components/tour/CoachMark.jsx:233-238` (the Next/Done button) and `frontend/src/components/tour/TourProvider.jsx:294-298` (the "Continue the walk" button) both hand-roll:
   ```js
   className="... text-sm font-semibold text-white" style={{ background: 'var(--brand-primary)' }}
   ```
   `--brand-primary` resolves to `#1C8DD4` under the live `theme-flow.css` (the approved global palette, loaded last). White text on `#1C8DD4` measures **3.62:1** (WCAG luminance formula), against the 4.5:1 minimum for text this size (14px/text-sm, semibold - below the 18.66px-bold "large text" threshold, so it needs 4.5:1, not 3:1). It also contradicts the locked button system CLAUDE.md spells out for this exact confusion: *"Solid actions are black #000000 with white text... two solid fills in one row is half of what 'nothing flows' meant."* The correct classes already exist and are used correctly three lines away in the same file - `CoachMark.jsx:206` uses `background: var(--action, #000)` for the "Do it now" button. The fix is `.btn-primary` (or `background: var(--action)`) on both buttons, which is also a genuine AA pass (black/white is far over 4.5:1).
   This is a brand-new, site-wide feature (the onboarding "walk") that every dashboard user meeting it for the first time will see on its two most-clicked controls.

## Should fix

3. **Touch targets under 44px on the new mobile-first onboarding modal.**
   - `CoachMark.jsx:182-191` - the exit (X) button: `p-1` padding around a 16px icon ≈ 24×24px.
   - `CoachMark.jsx:221-231` / `:233-242` - Back/Next buttons: `py-1.5` + text-sm ≈ 32px tall.
   - `TourProvider.jsx:299-302` - the paused-bar exit (X) button: `p-1` around a 15px icon ≈ 23×23px.
   All four are on a component whose entire purpose is guiding first-time mobile users through the dashboard (`prefers-reduced-motion` and RTL are both handled carefully elsewhere in the same file, so this isn't a general carelessness issue - just this one axis). Fix: raise padding to reach 44×44px hit areas, e.g. `p-2.5` on the icon buttons and `py-2.5` on Back/Next.

4. **A documented fallback tour target is never wired up, so it silently never fires.**
   `frontend/src/components/tour/tourSteps.js:30`:
   ```js
   { id: 'b.page', route: '/dashboard?tab=my-businesses', target: ['business-design', 'business-card'], ... }
   ```
   `business-card` has no `data-tour` attribute anywhere in the codebase - `MyBusinessesTab.jsx:285` only sets `data-testid="business-card-${b.id}"`. `business-design` (the array's first target, `MyBusinessesTab.jsx:430`) is attached whenever the business list has at least one item, which is the only case where a card renders at all (an empty list shows `data-testid="businesses-empty"` instead, `MyBusinessesTab.jsx:270-277`) - so the fallback's one plausible reason to exist never occurs. Per the engine's own contract ("A MISSING TARGET IS SKIPPED SILENTLY"), this degrades gracefully today, but it's dead code masquerading as a safety net. Fix: either wire `data-tour="business-card"` onto the card wrapper (`MyBusinessesTab.jsx:281-285`) or drop it from the target array.

## Improvement of the night

**Mechanism: choice overload** (Iyengar & Lepper 2000; the effect is strongest, per the later Scheibehenne et al. 2010 meta-analysis, exactly when the options don't sort into an obvious category for the chooser - which fits here, since the twelve recipes span four unrelated trigger families with no visual grouping).

**Surface:** `frontend/src/components/dashboard/AutomationsPanel.jsx:45-67` (`RECIPES`) rendered at `:580-596` inside the "starter cards" grid, `data-tour="automation-recipes"`.

**What to change:** A host account sees all 12 starter cards at once on first visit; a business-only account sees 6. This grid is exactly what the new walk's `b.automations`/`h.automations` stop spotlights as a brand-new user's *first* look at the feature (`tourSteps.js:41,54`) - the walk actively directs attention at the full wall of choices rather than a starting point. **What you'd expect to see if it worked:** a higher rate of `step_viewed` → `doIt` follow-through specifically on the `b_automations`/`h_automations` walk step, in the `/onboarding/tour` event log the walk already writes (`TourProvider.jsx:113-116`) - no new instrumentation needed, and no number gets claimed here until that comparison exists.
