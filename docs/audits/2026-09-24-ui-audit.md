## Improvement of the night

**Mechanism: the anchoring effect** (Tversky & Kahneman) - the first number a
person sees becomes the reference point they judge every number after it
against, whether or not that first number is representative.

**Surface:** the offer line in the new `ClarityPanel`, live on every business
and gig page for anyone with the page upgrade on (`ecd7521`, `36c6f21`).
`frontend/src/components/marketplace/ClarityPanel.jsx:22-46` renders `offers`
as plain text, in whatever order it receives them, capped at 3
(`offers.slice(0, 3)`).

Both call sites hand it the raw listings array with no sort:

- `frontend/src/pages/BusinessPage.jsx:558-561` — `const listings = biz.listings || [];` then `offers = listings.map((g) => ({ name, price }))`
- `frontend/src/pages/GigDetail.jsx` builds its own `offers` from the gig's tiers/products in the order the backend returns them.

Nothing in the frontend decides this order on purpose - it is whatever order
the database happens to return the business's listings or a gig's tiers in
(creation order, in practice). That means the price that anchors a visitor's
sense of "what does this cost" - the first one they read, in the biggest,
boldest text on the panel - is accidental, not chosen. A business whose
priciest service happens to have been added first shows that price as the
headline number on every page view; one whose cheapest was added first does
the opposite. Either can be the right call depending on the business, but
right now it's decided by insertion order, not by anyone.

**What to change.** Sort `offers` before slicing to 3 - cheapest first is the
safer default (it anchors low, so the second and third prices read as
reasonable next to it, and "Ask for a quote" items don't crowd out an actual
number). Concretely, in both call sites: `listings.slice().sort((a, b) =>
(a.cheapest_price ?? Infinity) - (b.cheapest_price ?? Infinity))` before
mapping to `offers`, so the component keeps rendering exactly what it's
given and the ordering decision lives with the page, where the rest of the
"what to show" logic (`upgrade_view`, `view.strengths`) already lives.

**What I would expect to see if it worked.** This can't be checked from a
new metric tonight, since nothing logs which price a visitor read first.
But it doesn't need one: the same "Leads" count already shown on the
dashboard Overview (`frontend/src/components/dashboard/OverviewTab.jsx`,
backed by `backend/utils/view_tracking.py`) is tracked per business already.
Reordering costs nothing to try, and the existing Leads count for the
upgraded businesses (a small, named cohort today, since page_upgrade is
switched on by hand per user) is the number to watch for a lift over the
following weeks - no new tracking required, just reading a number the
dashboard already computes for a smaller set of accounts before and after.
