# Dead ends — 2026-09-10

Scheduled dead-ends audit, following `.claude/skills/dead-ends/SKILL.md`. Two
parallel passes — forward (does every control resolve to what it promises?)
and backward (does every promise have a working destination, and does every
backend capability have a way to be reached?) — cross-referenced against
`docs/audits/2026-09-03-dead-ends-audit.md`, the prior run of this exact
audit. All top findings below were re-verified independently by reading the
actual source (not just trusting the sub-pass reports) before being written
up here. Read-only: nothing in this repo was changed to produce this report.

## Status of the six previously-documented recurring cases

Re-checked all six from the skill's own list of past occurrences, since this
bug class has repeated here before:

1. "Message on MyIsraelRental" 400 on most listings — **still fixed**, routes to real chat now.
2. `_normalize_category` called from nowhere — **still fixed**, called from `gigs.py:174`, pinned by `backend/tests/test_legacy_category_slugs.py`.
3. `GigPatch.status: 'paused'` unreachable — **still fixed**, `MyGigsTab.jsx` has a pause/resume toggle.
4. Requests board never sending `condition`/`min_price`/`max_price`/`include_sold` — **still fixed**, `RequestsBoard.jsx` reads/writes all four as URL params.
5. Two admin moderation endpoints with no frontend caller — **still true, and worse than before.** See Finding 1.
6. Jobs digest endpoint with no scheduler — **still fixed**, `jobs_digest_daily_loop` runs via `asyncio.create_task` in `backend/server.py:272`; the manual-trigger endpoint is a documented admin escape hatch, not a broken promise.

So the known backlog is closed except #5, which turns out to have grown a
second, independent dead end next to it (below). Three new findings of the
same general shape were also found this pass.

## Broken: goes nowhere or errors

### B1. "Sign in with Google" drops the `redirect` param — every auth-gated CTA in the app loses its destination if the visitor uses Google instead of a password
- `frontend/src/pages/Auth.js:28,36,399` — computes `redirectParam`/`redirectUrl` from `?redirect=...` and uses it for email/password sign-in (line 367 `navigate(redirectUrl)`), but passes nothing to `<GoogleSignInButton className="mb-4" />` at line 399.
- `frontend/src/components/auth/GoogleSignInButton.jsx` → `useGoogleSignIn.js:53-90` → `completeGoogleSignIn.js:96-103` — the whole chain never receives or reads a redirect target. `completeGoogleSignIn.js` ends with `navigate('/businesses/add?welcome=1' | '/dashboard?welcome=1' | '/dashboard', { replace: true })`, chosen purely by the account's role.
- **Verified:** dozens of call sites correctly build `/auth/login?redirect=<page>` before bouncing a signed-out visitor (`SubleaseDetail.js:64`, `GigDetail.jsx:597/607/639`, `PropertyDetail.js:277/317`, `BusinessPage.jsx:163`, `JobDetail.jsx:138`, `PostJob.jsx:56`, `CreateGig.jsx:305`, `JobsBoard.jsx:74/122/123`, `OrderPage.jsx:304`, every `ToAuth`-guarded route in `App.js:71-74`), and the email/password path honors it correctly. Only the Google branch drops it.
- **Impact:** a visitor bounced to sign in in order to message an owner, apply for a job, or finish an order, who chooses "Sign in with Google" instead of typing a password, lands on their dashboard with the thing they came to do gone, with no error.
- **Fix (build the missing affordance):** thread `redirect` through `GoogleSignInButton` → `useGoogleSignIn.start()` → `completeGoogleSignIn()`, and have it `navigate(redirectParam || roleDefault, { replace: true })` the same way the email/password branch does.

### B2. "Terms & Privacy Policy" link 404s on both sign-up surfaces
- `frontend/src/pages/Auth.js:618` — `<a href="/terms" target="_blank">` (also missing `rel="noopener noreferrer"`).
- `frontend/src/pages/SignupJoin.jsx:670` — `<a href="/terms" target="_blank" rel="noreferrer">`.
- **Verified:** no `/terms` route exists in `App.js`'s route table, no static file under `frontend/public`, nothing in `frontend/server.js`. Falls to the catch-all `*` → `NotFound`.
- **Impact:** every new user, on both signup flows, is shown a terms/privacy link right beside the checkbox required to create an account, and it opens Not Found.
- **Fix:** build a real `/terms` page (or point at wherever the canonical terms live) and add the missing `rel` on `Auth.js:618` while there.

## Dead-end promises: destination lacks the affordance

### P1. Admin: reported/needs-review requests have a queue, a count, and no way to see either
- `GET /admin/request-reports`, `POST /admin/request-reports/{request_id}` (`backend/routes/admin/marketplace.py:274,346`) — fully implemented moderation queue (list + hide/allow). **Zero references anywhere in `frontend/src`** — no tab, no button, no component.
- The count they'd back, `posts_awaiting_moderation`, is computed by `GET /admin/attention` (`backend/routes/admin/marketplace.py:266`) but is the one field on that response `AttentionQueue.jsx:44-86` does not render a row for — every sibling field (`requests_expiring_unanswered`, `chats_unanswered`, `services_without_photo`, `businesses_unverified`, `emails_bounced_7d`) has one.
- **Second, independent dead end found while tracing this one:** the row that *is* rendered for reports-adjacent content, "N requests expiring within 3 days with no responses" (`AttentionQueue.jsx:44-49`), calls `onNavigate('requests')`. Verified in `frontend/src/pages/AdminDashboard.js`: there is no `activeTab === 'requests'` branch (the real ids are `overview/listings/services/areas/bookings/users/chats/smart-lists/import/settings/email-health`) and no `{ key: 'requests', ... }` in the tab list either. Clicking that row sets `activeTab` to a value nothing renders — the content area goes blank with no active tab highlighted and no error.
- **Fix:** build a Requests-moderation tab wired to the two existing endpoints, add a `posts_awaiting_moderation` row to `AttentionQueue`, and give it (and the pre-existing `requests_expiring_unanswered` row) a real `activeTab` case + nav entry to land on.

### P2. In-platform gig bookings: "Requests arrive in your MyIsraelRental inbox" — the inbox doesn't exist
- `CreateGig.jsx:688-691` — a provider can set `booking_mode: 'in_platform'`, with the on-screen copy *"Requests arrive in your MyIsraelRental inbox — no phone number shared."*
- A buyer books through `BookingForm` (`GigDetail.jsx:187-247`), which really does `POST /marketplace/gigs/{id}/book` → `db.marketplace_bookings.insert_one(...)` (`backend/routes/marketplace/gigs.py:1110`) and shows "Booking request sent!".
- **Verified:** the only endpoint that could move it forward, `PATCH /marketplace/bookings/{booking_id}` (`backend/routes/marketplace/gigs.py:1116-1142`, `BookingPatch.status ∈ {accepted, declined, completed, cancelled}`), has zero frontend callers (`rg "marketplace/bookings/" frontend/src` → nothing). There is also no `GET` endpoint anywhere that lists a provider's pending bookings, and no dashboard component reads `hold_expires_at` or anything from `marketplace_bookings`.
- **Impact:** every booking made against an `in_platform` gig sits as `status: "pending"` until `booking_hold_sweep_loop` silently expires the hold. The provider is never shown it, never gets to accept or decline it, and the buyer's "sent!" confirmation is a promise the provider has no way to keep. This is the same defect class as the already-fixed `paused` enum bug, but for an entire flow rather than one field, and it affects any calendar/appointment or deliverable gig configured for in-platform booking today.
- **Fix:** build the provider inbox — a `GET` list of pending bookings plus accept/decline/complete controls feeding the existing `PATCH` — or remove `in_platform` as a selectable `booking_mode` for those gig types until it exists (store gigs already correctly route in-platform contact to chat instead; this is the one path that wasn't migrated).

### P3. Business "Verified" badge: publicly shown, counted for admins, no control to ever set it
- `BusinessPage.jsx:352-356` renders a public "Verified" badge when `business.verified` is true.
- `AttentionQueue.jsx:65-76` counts and surfaces "N trading business(es) not verified yet" (`businesses_unverified`), and this row's `go: 'services'` target does exist and load (unlike P1).
- **Verified:** `PATCH /marketplace/businesses/{business_id}/verified` (`backend/routes/marketplace/businesses.py:845-863`) is the dedicated admin-only endpoint for exactly this, and `ServicesTab.jsx` (the admin tab the attention row lands on) has zero references to "verified" — no toggle, no button.
- **Fix:** add a verify/unverify control to the admin Services tab (row action or detail view) wired to the existing endpoint.

## Wrong destination

### W1. Sublease notification click switches tab correctly but loses which sublease it was about
- `frontend/src/components/Navigation.js:275` — `navigate('/dashboard?tab=subleases&highlight=<id>&_t=<t>')`.
- **Verified:** `tab=subleases` is valid and switches correctly. But `Dashboard.js:473` only forwards `highlightId={highlightBookingId}` to `<BookingsList>` — `<SubleasesTab>` (rendered at `Dashboard.js:415`) receives no such prop and has zero references to `highlight` anywhere in its file. The renter lands on a flat, unhighlighted list of every sublease.
- Contrast: the identical booking-notification path (`Navigation.js:270`) does highlight/scroll correctly via `BookingsList.jsx`.
- **Fix:** pass `highlightId` into `SubleasesTab` and give it the same highlighted-row treatment `BookingsList` already has.

### W2 (minor, not currently live). `Auth.js`'s own signup branch still has the pre-fix version of a bug `SignupJoin.jsx` already fixed
- `Auth.js:110-116` — for `mode === 'signup' && role === 'provider'`, hardcodes `navigate('/businesses/add')`, dropping `redirectParam`. `SignupJoin.jsx:211` fixed the identical bug for its own provider branch on 3 Sep (comment cites that audit finding #6) with `navigate(redirectParam || '/businesses/add')`.
- **Checked reachability:** grepped all of `frontend/src` for links to `/auth/signup` or anything selecting `mode="signup"` on the `Auth` page — every real signup entry point in the app goes to `/signup` or `/join` (`SignupJoin.jsx`, already fixed). This branch of `Auth.js` appears to be unreachable through any in-app control today, only by typing the URL directly. Flagging for consistency/future-proofing, not as a live user-facing defect.
- **Fix:** apply the same one-line fix as `SignupJoin.jsx:211` for consistency, low priority.

- Requests board contact/status-change flow — "Message" correctly disabled once `status !== 'open'`, matching the backend guard exactly; poster-only actions (`found`/`sold`/`renew`) correctly scoped.
- Jobs board apply flow — Apply button hidden once `job.status !== 'open'`, matching the backend's own guard exactly.
- Gig/business "Message" buttons — route to real chat threads for every gig regardless of `booking_mode` (the original "Message on MyIsraelRental" bug's fix holds).
- Order status transitions (`OrderCard.jsx` `STATUS_ORDER`/`NEXT`/`BACK`) match the backend's `_TRANSITIONS` table and `can_transition()` guard exactly — no button can fire a transition the backend would reject.
- Order creation `?add=<product>` preselection, saved-search share links (including the `bedrooms_min` ↔ `min_bedrooms` param-name translation), services category deep links (`?category=&subcategory=&location=`) — all read correctly by their destinations.
- Primary nav (desktop + mobile), footer, and breadcrumb links all resolve to valid routes.
- Chat deep-links (`sublease_id`, `with` query params) — read correctly, matching every caller.
- Business-completeness dashboard checklist (`logo`, `description`, `areas`, `photo`) and the onboarding `SetupChecklist` — both open real, working controls at their destinations.
- Email CTAs across `backend/utils/email.py` and `backend/routes/marketplace/{jobs,requests}.py` — welcome, password reset, booking notification, chat/mention, pricing insights, availability-expiring, pricing quarantine (`?tab=properties&edit=<id>`, dashboard opens edit-on-arrival), property-removed (`?area=`, read by `Properties.js`), job-match deep-link auth (`/auth/deeplink` → consume endpoint), notification snooze, jobs opt-out — all point at real routes that do real work.
- No anchor-link (`href="#..."`) targets found anywhere in the frontend to check — none exist.
- External links: 23 `target="_blank"` occurrences checked; all but `Auth.js:618` (B2) already carry `rel="noopener noreferrer"` or `rel="noreferrer"`.

## Not checked (and why)

- **No live dev server or browser was used.** This audit was static analysis (grep + source reading across frontend and the matching backend routes/guards) at every step. All findings above have file:line evidence and, for the top five (B1, B2, P1, P2, P3), were independently re-verified by reading the actual source a second time before being written up here. A live click-through with `scripts/screenshot.mjs` / the relevant `scripts/check-*.mjs` scripts (`check-requests-filters.mjs`, an admin-panel screenshot pass) would be the stronger confirmation the skill recommends, and is the natural next step before fixing.
- **Self-messaging guard on `PropertyDetail`/`BookingSidebar`** — whether the "message the owner" control is hidden when the viewer *is* the owner was not fully traced through the prop chain. Not claiming a defect, just unverified.
- **`Auth.js`'s unreachable provider-signup branch (W2)** — not exercised end-to-end since no control reaches it; confidence in "unreachable" comes from an exhaustive grep for anything selecting `mode="signup"` on that page, not from a runtime trace.
- **Full param-by-param sweep of every one of the ~310 backend endpoints' query surface** was not done — only board/listing/search-shaped endpoints (requests, gigs, jobs, properties) were checked against their filter UIs.
- **`/admin/email/diagnose` and `/admin/events/health`** — flagged as legitimate ops tooling based on code/docstring evidence only; did not check for an external runbook or support tool that might consume them separately.
- **`scripts/check-dead-ends.mjs` (skill Part 7)** was not written this pass. A handful of the findings here (route/query-param resolution) are exactly what such a script would automate — recommended as follow-up work once the findings above are triaged, not done speculatively as part of a read-only audit.

1. **B1** (Google sign-in drops redirect) — small, well-contained fix, affects every gated CTA for a real share of sign-ins.
