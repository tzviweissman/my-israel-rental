## Blockers

### 1. The "What we are building" section renders completely invisible in Hebrew

`frontend/src/components/ui/pixel-text-fill.jsx:172, 191-200, 227`
`frontend/src/styles/home-v2.css:267-275`

The canvas text layout resolves each line's x-position from `getComputedStyle(el).textAlign`:

```js
const align = styles.textAlign;
const x =
  align === "right"
    ? width - lineWidth
    : align === "left" || align === "start"
      ? 0
      : (width - lineWidth) / 2;
```

`home-v2.css:267-275` sets the source element to `text-align: start`. Two facts combine into total failure:

1. Chromium's `getComputedStyle` returns the **literal string `"start"`** for `text-align: start`, in both directions - it is never resolved to `"left"`/`"right"`. Verified with a headless-Chromium repro: `RTL text-align:start computed -> start`, `LTR text-align:start computed -> start`. So the code's `align === "left" || align === "start"` branch treats both directions identically and always pins `x = 0`.
2. The page sets `<html dir="rtl">` for Hebrew (`frontend/src/i18n.js:104`); the `<canvas>` inherits `direction: rtl`; `ctx.textAlign`/`ctx.direction` are never set explicitly anywhere in the file, so `fillText`'s own default (`textAlign: "start"` under inherited `rtl`) anchors text to extend **leftward** from the origin. Verified with a real canvas in a real RTL document: painting at `x=0` under `dir=rtl` produces **zero visible pixels** (`{ anyPixelPainted: false }`); the same call at a positive anchor, or under `dir=ltr`, paints correctly.

Net effect for a Hebrew visitor: `align` resolves to `"start"` -> code picks `x = 0` -> canvas paints entirely into negative-x space -> nothing is visible. The invisible accessible fallback `<p>` underneath (`text-transparent` by design) is the only element with alignment resolved correctly by the browser, and it's invisible on purpose. Result: a large blank gap where the whole "What we are building" section should be, no console error, exactly the shape of `docs/failure-patterns.md`'s precedent - a defect that only shows with real content, in the one language that wasn't checked by eye.

**User-visible impact.** Currently limited to `/home-preview`, which is confirmed unlinked from navigation and `noindex` (`HomePreview.jsx:147`) - so no live user sees this today. It is a blocker for promoting this page, not for the current production site.

**Fix.** Resolve `start`/`end` against the wrapper's actual computed `direction` in JS (not via `getComputedStyle(...).textAlign` alone), convert to physical `x` there, then pin `ctx.textAlign = 'left'` and `ctx.direction = 'ltr'` before every `fillText` so canvas's own bidi resolution can't re-interpret coordinates already computed as physical left/right.

## Should fix

### 2. A mixed-currency listing can show a different price than it sorts and filters by

`backend/routes/marketplace/shared.py:763-779` (`_cheapest_tier_price`) vs `frontend/src/utils/gigPrice.js:44-58` (`cheapestRow`, new this batch)

The backend's cheapest-price helper is a raw numeric minimum with no currency conversion:

```python
prices.append(float(p))   # per tier/product row, currency ignored
...
return min(prices) if prices else None
```

This feeds `gig["cheapest_price"]`, which is what `/marketplace/gigs?sort=price_asc` sorts by and what the price filter compares against - both live on `/services` (`Services.jsx:50,65-66,210-211,325-326`).

`gigPrice.js`'s new `cheapestRow` (added this batch, specifically to fix the currency-mislabeling class of bug `b6bf104` addressed) converts to ILS *before* comparing:

```js
const inIls = (r) => (r.currency === 'USD' ? Number(r.price) * rate : Number(r.price));
return rows.reduce((best, r) => (inIls(r) < inIls(best) ? r : best), rows[0]);
```

For a listing with one $30 USD tier and one ₪90 ILS tier: the backend computes `cheapest_price = 30` (used for sort/filter, no currency attached); the frontend, correctly converting, now displays **₪90** as the real cheapest option. A customer sorting "Price: low to high" sees this listing rank as if it cost ~₪30, while its own card reads ₪90 - a visible contradiction on the same page. This is newly introduced by this batch's frontend fix, which corrected the display but left the backend's sort/filter algorithm on the old, currency-blind logic. Each tier can independently pick its own currency in the listing wizard (`CreateGig.jsx:918-920,998-1002`), so this is reachable by ordinary business-owner mistake, not a contrived input.

**Not confirmed against live data** - whether any real listing currently has mixed-currency tiers wasn't checked (would require a production query, out of scope for this audit); demonstrated via the batch's own test fixture (`scripts/test-gig-price.mjs`'s `mixed` case, `12/12 passed`) and by reading both implementations.

**Fix.** Make `_cheapest_tier_price` currency-aware (same ILS conversion `cheapestRow` uses) so backend sort/filter and frontend display agree.

### 3. The structured-data price range understates a mixed-currency listing's real low price

`frontend/src/pages/GigDetail.jsx:337-364`

```js
const prices = rows.map((r) => Number(r.price)).filter(Number.isFinite);
const currency = cheapestRow(gig)?.currency || 'ILS';
block.offers = { '@type': 'AggregateOffer', lowPrice: Math.min(...prices), highPrice: Math.max(...prices), priceCurrency: currency, offerCount: prices.length };
```

Raw prices are min/max'd without conversion, but `priceCurrency` is taken from the (converted) cheapest row. For the same $30/₪90 example: emits `lowPrice: 30, priceCurrency: 'ILS'` - claiming a ₪30 low price when the real range is ₪90-₪109.5. This is what Google reads for rich results; understates the low price by >3x for any mixed-currency listing.

**Fix.** Convert every row into `currency`'s terms (same conversion as finding 2) before taking `Math.min`/`Math.max`.

### 4. Offer end dates render as the raw wire format, bypassing the site's own date formatter

`frontend/src/components/marketplace/OfferBadge.jsx:58-61`, also `frontend/src/pages/HomePreview.jsx:127`

```jsx
{t('offers.until', { defaultValue: 'until {{date}}', date: discount.ends_at })}
```

`discount.ends_at` is the raw `YYYY-MM-DD` string off the model, never passed through `frontend/src/utils/formatDate.js` - the utility that exists specifically because request cards once showed this exact raw, day/month-ambiguous format to Hebrew readers. Rendered on the gig detail page and the home "Today's picks" rail, LTR and RTL, to every visitor.

**Fix.** `date: formatDate(discount.ends_at, i18n.language)` in both places; `OfferBadge` already has `i18n` in scope.

### 5. `FlipCard`'s twelve navigation targets have no keyboard access, and the label that names them is hover-only

`frontend/src/components/ui/scroll-morph-hero.jsx:112-113, 130-153`

The cards' "back" face - the only place a card's identity (title, "Rental"/"Business") lives - is gated behind `group-hover:opacity-100` with no focus equivalent. The wrapping `motion.div` has `onClick` (wired to real navigation via `CommunitySection.jsx:129-134`, `onOpen={(card) => card.href && navigate(card.href)}`) but no `tabIndex`, `role="button"`, or `onKeyDown`. A keyboard-only user cannot reach or activate any of the twelve cards, and even a sighted keyboard user who somehow triggers one never sees what it opens. WCAG 2.1.1 (Keyboard).

**Fix.** Add `tabIndex={onOpen ? 0 : undefined}`, `role="button"`, `aria-label`, `onKeyDown` for Enter/Space on the outer element; pair `group-hover:opacity-100` with `group-focus-visible:opacity-100` plus a visible focus ring.

### 6. `FlowButton`'s arrow doesn't switch sides in RTL - only the glyph mirrors, not its anchor

`frontend/src/components/ui/flow-button.jsx:52-55, 68-71`

The label's translate is correctly mirrored for RTL (`rtl:translate-x-3` / `rtl:group-hover/flow:-translate-x-3`), but both `ArrowRight` icons keep the same physical `left-*`/`right-*` anchors regardless of `dir` - only `rtl:-scale-x-100` (the glyph shape) changes. Confirmed by rendering the exact class values in headless Chromium with real `:hover`: in RTL the arrow sits on the same physical (right) edge as in LTR, just pointing the other way, rather than moving to the left edge where the mirrored label now sits. This component renders live on `/home-preview`'s two "See all..." CTAs.

**Fix.** Swap the physical Tailwind position classes for `rtl:` overrides mirroring the ones already written for the label (matching the logical-position pattern `anti-metal-button.jsx` already uses correctly).

### 7. Carousel prev/next controls are hardcoded English, and its accessible name doesn't follow the heading into "deals" mode

`frontend/src/components/ui/coverflow-carousel.jsx:417, 425, 467`; `frontend/src/pages/HomePreview.jsx:242, 260`

`aria-label="Previous slide"` / `"Next slide"` / `` `Go to slide ${index+1}` `` are literal English strings with no `t()` call in the component - a Hebrew screen-reader user hears English controls inside an otherwise fully-Hebrew page. Separately, the carousel's `label` prop (its `role="region"` accessible name) is hardcoded to `home.v2.picks.h2` ("Today's picks") even on days `hasDeals` is true and the visible `<h2>` correctly switches to `home.v2.picks.h2Deals` ("Today's deals") - so sighted and screen-reader users are told they're in different sections.

**Fix.** Add `prevLabel`/`nextLabel`/`goToLabel` props defaulted via `t()`; make `label` follow the same `hasDeals` ternary the visible heading already uses.

`backend/routes/marketplace/gigs.py:94-107` vs `backend/routes/short_links.py:288-291` (added in the same diff range, deliberately using `ZoneInfo("Asia/Jerusalem")` with a comment explaining exactly why UTC is wrong for a day-boundary check here)
