## Dead-end promises: destination lacks the affordance

- **`backend/routes/admin/core.py:490-570`, `delete_user` — the docstring
  promises a capability the code does not have.** The function's own comment
  reads: *"IT TAKES A SNAPSHOT FIRST. Every document about to be removed is
  written to `user_tombstones`... an admin who deletes the wrong row has the
  rows back."* Confirmed: `db.user_tombstones.insert_one(...)` runs at
  `:524` before the deletes. **There is no restore endpoint.** Grepped all of
  `backend/routes/` — the only other references to `user_tombstones` are in
  a test file (`test_admin_delete_user_cascade.py`), which only asserts the
  snapshot was written, never that anything can be read back from it. Contrast
  with the parallel, correctly-built flow for the same pattern:
  `property_tombstones` has `POST /admin/properties/bulk-restore`
  (`backend/routes/admin/properties_bulk.py:307`), which reads the snapshot
  back by id and re-inserts the rows. `user_tombstones` has the write half of
  that pattern and not the read half. This is the exact bug class the skill
  exists to catch — "a promise with no place to be kept" — just found from
  the backend/docstring side instead of a UI dashboard prompt. **Severity:
  real** — the docstring is what an admin (or a future engineer) would read
  before trusting the delete button, and right now it's wrong. **Fix:** build
  a `POST /admin/users/restore` mirroring `bulk-restore`'s shape (find the
  tombstone by id, re-insert each collection's rows, delete the tombstone),
  or — the cheaper fix if restore isn't actually wanted yet — rewrite the
  docstring to stop claiming recoverability and say instead that the snapshot
  exists as an audit record, not a restore mechanism.

- **`frontend/src/components/admin/UsersTab.jsx:39`,
  `admin.deleteUserDesc`** (`frontend/src/locales/en.js:2073`) — *"All of
  their properties will be deleted too. This cannot be undone."* The actual
  cascade, per `delete_user`'s own comment block (`core.py:494-499`, "THE
  BUG... Everything else keyed to them stayed: their business pages, their
  service listings, their posts on the Requests board, their saved searches
  and alerts, their subleases"), now also deletes all of those — confirmed by
  reading the `_USER_OWNED` collection list the function actually iterates.
  The confirm dialog was never updated to match commit `069d78b`'s expanded
  scope. This is the inverse of the usual dead-end promise (the code does
  *more* than the copy says, not less), but it's the same failure mode from
  the admin's point of view: they're confirming an irreversible action based
  on an inaccurate description of its blast radius. **Fix:** update
  `admin.deleteUserDesc` in `en.js`/`he.js` to name the actual scope, e.g.
  "All of their properties, businesses, services, requests, subleases, saved
  searches and alerts will be deleted too."

## Wrong destination

- **`frontend/src/components/auth/completeGoogleSignIn.js:108-118` — Google
  sign-in drops `?redirect=` for a brand-new provider account; the
  email/password form on the same page does not.** The routing block:
  ```js
  const back = safeRedirect(redirectTo);
  if (intentRole === 'provider' && user.role === 'provider') {
    navigate('/businesses/add?welcome=1', { replace: true });   // checked first, unconditionally
  } else if (back) {
    navigate(back, { replace: true });
  } ...
  ```
  `redirectTo` is captured correctly from the URL (`useGoogleSignIn.js:83`),
  so `back` is a real, present value — it's just never consulted for this
  branch. The comment directly above (`:99-109`) asserts this "exactly...
  matches" `pages/Auth.js`'s email path, but the actually-used entry point,
  `frontend/src/pages/SignupJoin.jsx:211`
  (`navigate(redirectParam || '/businesses/add')`), puts the redirect
  *first*. **Concrete repro:** a signed-out visitor bounced to
  `/join?redirect=%2Fbusinesses%2Fpost-job&role=provider` who fills the email
  form lands back on `/businesses/post-job` (correct); the same visitor
  clicking "Continue with Google" instead lands on `/businesses/add?welcome=1`
  — their original intent silently discarded, no error, no toast. Google
  sign-in is a primary, equally-prominent CTA on that page, not a rare
  fallback. **Fix:** reorder the check so `back` wins before the
  `intentRole==='provider'` branch, matching `SignupJoin.jsx`'s precedence —
  or, if the divergence is actually wanted (a brand-new provider should
  always see onboarding), fix the comment instead of the code, since it
  currently asserts something false. Not caught by the 09-14/09-15 audits:
  the responsible commit (`363dbe6`) landed one day before the 09-14 audit,
  and the confident-sounding comment likely read as already-verified.

- **`frontend/src/App.js:426,428` — `/chat/:propertyId` and
  `/payment/success` still use the bare `<Navigate to="/auth/login" />` guard
  the file's own comment (lines 68-72) says was eliminated everywhere.** Every
  other gated route (`/dashboard`, `/dashboard/settings`, `/services/post-job`,
  `/services/create-gig`, `/businesses/post-job`, `/businesses/add`,
  `/orders/print`) uses the `<ToAuth />` helper that appends
  `?redirect=<original path+search>`; these two were missed.
  `/payment/success` is the higher-impact of the two:
  `frontend/src/pages/PaymentSuccess.js:26-28` reads `?orderId=`, `?token=`
  (a PayPal order id on direct redirect) and `?flow=` to decide whether to
  activate a subscription or capture an order. If the session expired during
  the round trip to PayPal, the guard fires and all three params — along with
  a payment PayPal has already completed on their end — are dropped with no
  way back except browser history. `/chat/:propertyId` is lower-impact since
  every in-app caller already checks `token` before navigating there
  (confirmed in `PropertyDetail.js:277,317`, `BusinessPage.jsx:169`,
  `GigDetail.jsx:606/616/648`); it fires mainly on a page refresh of an
  already-open chat whose session expired mid-conversation. **Fix:** swap
  both to `<ToAuth />`, one line each — the pattern is five lines away in the
  same file. **This is now mechanically enforced going forward** — see Part 7.

- **`frontend/src/pages/Auth.js:621`** — `<a href="/terms" target="_blank">`
  still has no `rel` attribute, unfixed since the 09-14 audit first flagged
  it. Now confirmed to be **the only one of 23 `target="_blank"` anchors in
  the entire frontend** missing `rel="noreferrer"`/`rel="noopener"` — every
  other instance, including the equivalent Terms link at
  `SignupJoin.jsx:670`, carries it. Same-origin target, so the practical risk
  is low, but it's a one-line fix that's been sitting for a week.

## Part 7 — made cheaper next time

Added `scripts/check-dead-ends.mjs`: parses the route table out of `App.js`,
resolves every literal `to=`/`href=`/`navigate()` target against it, and
specifically watches for a bare `<Navigate to="/auth/login">` reappearing in
a route guard (the exact regression found in this run — flagged by name in
App.js's own comment as something already fixed once). Run with
`node scripts/check-dead-ends.mjs`; exits non-zero on any unresolved target
or bare-guard regression. Dynamic (template-literal) targets are reported
separately as "not statically checked" rather than silently skipped. Route
resolution and this one specific regression pattern are what's mechanical
here; whether a destination actually contains the promised affordance (the
`user_tombstones` and `RequestPatch` findings above) stays a human-judgement
pass — that's inherent to the check, not a gap in this script.
