## Dead-end promises: destination lacks the affordance

- **`frontend/src/components/admin/ListingsTab.jsx:326-337`** —
  `toggleFeatured()`, bound to a "feature this listing" control, PUTs
  `/admin/properties/{id}/featured` and shows a success toast
  ("Add/remove a property from the homepage Featured grid... mutates the
  global `site_settings.featured_property_ids` array"). But the live home
  page (`frontend/src/pages/Home.js`) has no featured section at all — grep
  for "featured" there returns only a comment noting "the old hero, featured
  rail... are gone" (line 70). The dedicated read endpoint that would have
  served a featured strip, `GET /properties/featured`
  (`backend/routes/properties/browse.py:471-472`), has **zero** frontend
  callers anywhere in the app (`rg -rl "properties/featured" frontend/src`
  returns nothing). The one place `is_featured` is still read client-side,
  `frontend/src/components/home/useHomeShowcase.js:157`, is explicitly used
  as a **tiebreaker for a "Recently added" row on the not-yet-live
  `/home-preview`**, and that same file's header comment (lines 14-17) says
  the ordering was deliberately changed to NOT be featured-first because
  "five of the live listings actually carry `is_featured`... so 'featured'
  was a label on a row that was mostly not featured." So an admin who clicks
  "Feature" gets a confirming toast for an action that currently has no
  visible effect anywhere on the site a visitor can reach.
  Compounding this: the legacy mechanism this control was supposed to
  replace — a raw comma-separated `featured_property_ids` textarea in
  `frontend/src/components/admin/SettingsTab.jsx:75-76` — is still present
  too, so there are now **two** admin controls that write the same
  now-unread field.
  **Fix — pick one:** (a) restore a featured section somewhere on the live
  site and wire it to `GET /properties/featured`, and delete the redundant
  `SettingsTab.jsx` textarea in favor of the per-row toggle; or (b) if
  "featured" is intentionally retired, remove the `ListingsTab.jsx` toggle,
  the `SettingsTab.jsx` textarea, and the dead `GET /properties/featured`
  endpoint together, so nothing in the admin console promises an effect the
  product no longer has.

## Wrong destination

- **`frontend/src/App.js:417`** — `<Route path="/chat/:propertyId"
  element={user ? <Chat /> : <Navigate to="/auth/login" />} />`. Unlike
  every other gated route in this file (`/dashboard`, `/services/post-job`,
  `/services/create-gig`, `/businesses/post-job`, `/businesses/add`,
  `/orders/print`, `/payment/success` — see below), this one does **not**
  use the `ToAuth` wrapper (`App.js:72-75`) that appends
  `?redirect=<intended path>` before bouncing to login. The comment right
  above `ToAuth`'s definition (`App.js:67-71`) documents this exact bug
  class as already fixed once ("Dead-ends audit 2026-09-03, #3 and #6") —
  this route was missed.
  **This is live and reachable, not theoretical**: real emails link straight
  into it with no auth context —
  `backend/utils/email.py:472` (`deep_link = f"{FRONTEND_URL}/chat/{property_id}"`,
  new-message notification), `backend/utils/email.py:549` (same, a second
  notification path), and `backend/routes/admin/chats_nudge.py:370`
  (`inbox_link = f"...{FRONTEND_URL}/chat/{property_id}"`, the admin's
  "nudge a stalled chat" email). Anyone who opens one of these emails on a
  device without an active session — a new browser, a cleared cookie jar, a
  session that expired since the email was sent — lands on `/chat/X`
  signed out, is bounced to bare `/auth/login` with the `propertyId` and any
  `?with=`/`?sublease_id=` thrown away, signs in, and (per
  `frontend/src/pages/Auth.js:33-39`, `redirectUrl = redirectParam ||
  '/dashboard'`) lands on the generic dashboard instead of the conversation
  the email was about. They then have to find the right thread by hand in
  the Messages tab.
  **Fix:** `<Route path="/chat/:propertyId" element={user ? <Chat /> :
  <ToAuth />} />` — one-line change, same pattern already used four lines
  below it.

- **`frontend/src/App.js:419`** — `<Route path="/payment/success"
  element={user ? <PaymentSuccess /> : <Navigate to="/auth/login" />} />`.
  Same bug, same missing `ToAuth` wrapper. Here the dropped query string is
  worse in kind: `PaymentSuccess.js:28` reads `?token=...` (the PayPal order
  id) to complete a capture (`payments.py`'s `POST
  /payments/orders/{id}/capture`) — losing it on a sign-out bounce would
  break the payment, not just inconvenience the user.
  **Why lower priority than the chat bug today:** the only product this
  page currently serves is the document-services checkout
  (`backend/routes/payments.py` header: `product_type="document_service"`,
  the Arnona/name-change services CLAUDE.md marks discontinued). No control
  anywhere in the frontend currently POSTs to `/payments/orders` to start
  that flow (`rg` for `payments/orders` in `frontend/src` returns only the
  two reads inside `PaymentSuccess.js` itself), so this route is not
  reachable through a live checkout button today. It would resurface the
  moment that flag is switched back on, or the moment any other payment
  product reuses this same success page, so it's a live landmine rather
  than a currently-firing bug.
  **Fix:** same one-line change, `<ToAuth />` in place of the bare
  `<Navigate>`.
