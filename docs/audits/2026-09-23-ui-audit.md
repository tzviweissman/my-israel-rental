## Should fix

### 1. The two new toggle switches ship with a 24px tap target and no wrapping label, and their OFF track fails non-text contrast

`frontend/src/components/dashboard/EmailSwitches.jsx:64-70` and `frontend/src/components/dashboard/OrdersTab.jsx:1388-1394` both render:

```
<button type="button" role="switch" ... className="... inline-flex h-6 w-11 items-center rounded-full px-1 ...">
```

`h-6` is 24px tall. At 375px width this is the only clickable element for that row (the label text beside it is a plain `<p>`, not wrapped in a `<label>`), so the actual tap target is 24 x 44px, under the 44px minimum. The OFF-state fill is `var(--brand-border)` (`#E3E3E3`) directly on the white card (`bg-white` in both files) with no border around the pill. Computed against WCAG's relative-luminance formula: `#E3E3E3` on `#FFFFFF` is **1.28:1**, well under the 3:1 minimum WCAG 1.4.11 sets for a UI-component boundary that has to be visible in its unchecked state.

This is a partial copy of an existing pattern that got both things right: `frontend/src/components/dashboard/SettingsTab.jsx:371-381` and `frontend/src/components/dashboard/SavedSearchesTab.jsx:279-282` use the identical `h-6 w-11` button, but (a) wrap it in `<label className="flex items-center gap-3 cursor-pointer">`, so the real tap target is the whole row, and (b) use Tailwind `bg-gray-300` (`#D1D5DB`) for OFF, which is still a contrast fail against white (computed: **1.47:1**) but less severe than the new `#E3E3E3`. Neither original nor new value clears 3:1, so this is also worth fixing at the two older sites, not only the two new ones.

**Fix:** wrap both new switches in a `<label>` the way `SettingsTab.jsx:371` does (or add `min-h-[44px]` to a padded wrapper around the button), and change the OFF fill from `var(--brand-border)` to something that clears 3:1 against white, for example `var(--brand-muted)` (`#666666`, which computes to 5.75:1) or add a `1.5px solid var(--brand-border)` ring plus a darker fill.

## Improvement of the night

**Mechanism: the goal-gradient effect** (Hull, 1932; Kivetz, Urminsky & Zheng, 2006). Effort and completion likelihood rise as the perceived distance to a goal shrinks, and framing the remaining amount (counting down) produces a stronger pull than framing the amount already done (counting up), especially in the back half of a task. This is distinct from the endowed progress effect already used here (09-05, on the FAQ editor): endowed progress is about how a task is framed at its *start* (already begun vs. not yet started); goal-gradient is about how the *same, unchanged remaining work* is framed as someone nears the end. Not one of the twelve mechanisms whose source I could confirm in this repo's audit history (halo, peak-end, loss aversion, denominator neglect, endowed progress, cognitive fluency, ambiguity aversion, automation bias, implementation intentions, banner blindness, position bias, social proof - see `docs/audits/mechanisms-used.md`).

**Surface:** the walk's per-step progress indicator, which every one of the walk's 8 or 9 stops shows while someone is mid-walk. `frontend/src/components/tour/CoachMark.jsx:216-219` (the tooltip's progress badge, shown at every stop) and `frontend/src/components/tour/TourProvider.jsx:294` (the same count in the "Continue the walk" paused bar) share one locale key:

```jsx
{t('tour.progress', '{{index}} of {{total}}', { index, total })}
```

**What is wrong now:** "3 of 9" and "8 of 9" are framed identically, both counting up from the start. The literature's finding is that counting up front-loads the motivational pull (which is right when someone has just committed, and is what endowed progress already exploits elsewhere on this site) but counting down produces the stronger pull as the remaining distance gets small, which is exactly the moment the walk most needs to keep someone from tapping the exit X instead of Next.

**Exact change:** once `total - index <= 2` (the last two stops of either walk), switch the string from the "of" framing to a remaining-count framing, e.g. `tour.progressLeft: '{{remaining}} to go'` (Hebrew: `נשארו עוד {{remaining}}`), computed as `total - index`. Keep the existing "index of total" string for every earlier stop, where the completed-so-far framing is doing useful work already. This touches only the two spots above (both consume the same `index`/`total` values) and needs one new key pair in `en.js`/`he.js`, no visual or layout change.

**Expectation, checkable against data already recorded:** every walk step already posts to `/onboarding/tour` with `event` in `{'started', 'step_viewed', 'step_skipped', 'completed', 'exited'}` and `step_id` (`TourProvider.jsx:113-116`, `:142-151`, `:170-178`, `:227-235`). Before/after this change, compare, per walk `role` (`business` vs `host`), the fraction of sessions whose last `step_viewed` was one of the final two stops (`b.stats`/`b.messages` or `h.stats`/`h.messages`) that go on to log `completed` rather than `exited`. No new tracking is needed; it is the same event stream the walk already writes on every step.
