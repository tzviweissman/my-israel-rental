## Broken: goes nowhere or errors

1. **The Terms & Conditions / Privacy Policy link 404s on every login and
   signup screen.** `frontend/src/pages/Auth.js:618` and
   `frontend/src/pages/SignupJoin.jsx:670` both render `<a href="/terms"
   target="_blank">`. There is no `/terms` route in `App.js` and no static
   `terms.html` under `frontend/public` — it resolves to the `*` → `NotFound`
   catch-all. This sits on the required-consent checkbox of the two most
   heavily trafficked forms in the app. `Auth.js:618`'s anchor also has no
   `rel="noopener"` (SignupJoin's does).
   **Fix:** build the missing page (this is a legal-consent link — the
   promise has to be kept, not removed) and add `rel="noopener"` to
   `Auth.js:618` while touching that line.

2. **Dashboard Overview's "Waiting on you" card opens a blank pane for most
   users.** `frontend/src/components/dashboard/OverviewTab.jsx:165`:
   `onClick={() => onGoToTab(summary.bookings_awaiting_reply ? 'bookings' :
   'job-requests')}`. The `onClick` prop itself is unconditional — `StatCard`
   (line 54: `{onClick && (...)}`) renders the "Open" button whenever
   `onClick` is truthy, which it always is here, regardless of whether
   `bookings_awaiting_reply` is 0. When it's 0 (any renter with no listings;
   any owner/manager with no pending bookings — i.e. most first-time users),
   the button routes to the `job-requests` tab. `Dashboard.js` only mounts
   `JobRequestsTab` when `showGigTabs` is true, so for a plain renter that
   tab renders nothing — no route error, no 404, just an empty pane with
   nothing selected in the sidebar. This is the canonical failure mode the
   audit exists to catch, and it's on the page every user sees first. The
   **Scans** card three rows down (`OverviewTab.jsx:197`) gets this right —
   `onClick` is `undefined` when neither `isPropertyLister` nor `showGigTabs`
   applies — this card should follow the same pattern.
   **Fix:** `onClick={waiting > 0 ? () => onGoToTab(summary.bookings_awaiting_reply ? 'bookings' : 'job-requests') : undefined}` (or equivalent gate on whichever destination tab is actually visible).

## Orphaned capabilities: endpoints with no caller

3. **Admin requests-moderation queue is fully built and fully unreachable.**
   `backend/routes/admin/marketplace.py:274` (`GET /admin/request-reports`)
   and `:346` (`POST /admin/request-reports/{request_id}`, taking
   `ModerationIn.action: hide|allow`). Zero references anywhere in
   `frontend/src`. The admin summary already surfaces a
   `posts_awaiting_moderation` count that this queue would resolve, but there
   is no `AdminDashboard.js` tab, component, or button that calls either
   path — confirmed by grep for both literal paths and for "moderation" /
   "requests" in `AdminDashboard.js` (zero hits on the latter too, so this
   isn't a naming mismatch, the surface doesn't exist).
   **Fix:** build a Moderation Queue tab in `AdminDashboard.js` (list +
   hide/allow), or remove the endpoints if reported requests are now handled
   some other way.

4. **Admin auto-owner-nudge status/run-now promised in its own docstring,
   never built.** `backend/routes/admin/chats_nudge.py:525` (`GET
   /admin/auto-owner-nudge/status`) and `:540` (`POST
   .../run-now`) — the docstring explicitly describes an admin-facing "auto
   nudges on · 12h threshold" strip with counts, plus a manual-trigger
   button. Zero frontend references to either path (the only related wired
   control is the unrelated owner-facing opt-out toggle in
   `SettingsTab.jsx`).
   **Fix:** add the promised status strip + "run now" button to the admin
   Chats tab, or strike the promise from the docstring and leave it as a
   curl-only escape hatch (matching how the jobs-digest trigger was
   deliberately kept in the last audit).

## Backward promises with no home

5. **Two automated emails point at a settings control that doesn't exist.**
   `backend/utils/email.py:747-748` (weekly pricing-insights digest —
   "manage your email preferences in your dashboard settings") and
   `:802-803` (availability-expiring email — "pause them in your dashboard
   settings"), both linking to `{FRONTEND_URL}/dashboard?tab=settings`.
   `SettingsTab.jsx` has no email-preferences or per-digest pause toggle —
   the closest thing is "Auto reply reminders," which is an unrelated
   chat-nudge setting. `POST /notifications/preferences` exists in
   `backend/routes/notifications.py` but (a) nothing in the frontend calls
   it and (b) its model is saved-search criteria (rental_type/bedrooms/
   price/area), not a digest opt-out, so it wouldn't satisfy this promise
   even if wired up.
   **Fix:** either build a real email-preferences section in Settings with
   per-digest toggles, or soften both emails' copy to something true (e.g.
   "reply to this email to opt out").

6. **The onboarding tour never shows business owners the QR/share feature it
   was clearly built to demo.** `frontend/src/components/tour/tourSteps.js`
   still carries a comment (dated 2 Sep, before the 4 Sep `8ba5e2f` business
   QR feature shipped) saying businesses get a QR "but there is no control
   for it anywhere in their dashboard." That's now false —
   `MyBusinessesTab.jsx:381-392` embeds `ShareListingsPanel` per business
   with `data-tour="business-share"` on the first one, clearly written to be
   a tour target. `TOUR_STEPS` has no step targeting `business-share`; the
   existing `share` step is `roles: ['lister']` only, targeting the
   Properties-tab `share-panel`. A business owner running "Show me around"
   never sees their own QR/link feature, and the `data-tour` attribute sits
   unused.
   **Fix:** add a `business-share` tour step scoped to the `business` role
   (low priority — cosmetic, not a functional dead end).

## Wrong destination (minor, informational)

7. **Two gated routes still use a bare `Navigate` that drops `?redirect=`,**
   contrary to the 3 Sep audit's "#3/#6: every gated route ... WITH the page
   they wanted" resolution note: `/chat/:propertyId` and `/payment/success`
   in `App.js:349,351` (`user ? <X/> : <Navigate to="/auth/login" />`, no
   `ToAuth` wrapper). In practice this is low-severity: every in-app caller
   of `/chat` (`PropertyDetail`, `SubleaseDetail`, `GigDetail`, `Navigation`,
   `BookingChip`, `MyJobsTab`, `MessagesTab`) already checks `user`/`token`
   itself and builds its own `?redirect=` back to the *source* page before
   ever navigating to `/chat`, so this fallback only fires on a
   bookmarked/shared raw `/chat/...` or `/payment/success` URL hit while
   signed out (or, for payment/success, a session that expired mid-checkout
   redirect). Real, but a narrow edge case, not a hole in the main flow.
   **Fix:** swap both to `<ToAuth />` for consistency — one-line each.
