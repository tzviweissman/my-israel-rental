## Should fix

### 1. The marquee's duplicate pass is 24 keyboard stops that announce nothing

`frontend/src/pages/HomePreview.jsx:423-431`

```jsx
<div className="hv2-marquee-cell" key={`dup-${p.id}`} aria-hidden="true">
  <StaysCard property={p} liked={...} onClick={...} />
```

`aria-hidden` hides the copy from screen readers but not from the keyboard.
Each `StaysCard` is `role="button" tabIndex={0}` with a like `<button>` inside
(`StaysCard.jsx:123-127`, `:164`).

**Measured** at 1280 and 768: tabbing from the section heading takes **49 Tab
presses** to leave the row. **24 of them land inside the aria-hidden copy.**
A screen-reader user hears nothing on those 24 stops, and a keyboard user
walks the same twelve listings twice. The duplicate hearts are also dead:
`onToggleLike` is not passed, so pressing one does nothing.

**Exact fix:** replace `aria-hidden="true"` with `inert` on the duplicate cell.
React 19 (`package.json`) supports it as a boolean prop:

```jsx
<div className="hv2-marquee-cell" key={`dup-${p.id}`} inert>
```

`inert` removes the subtree from both the accessibility tree and the tab
order, so the `aria-hidden` becomes redundant. Re-run the Tab count and expect
25 stops: 12 cards, 12 hearts and the exit.

### 2. An offer whose photo has been deleted still renders, as a broken-image card

`frontend/src/pages/HomePreview.jsx:294-305`, and the filter at
`useHomeShowcase.js:177-180`

The hook drops offers with **no** cover (`getGigCover(g)` is falsy). It cannot
drop an offer whose cover URL exists but no longer resolves.

**Rendered:** in all seven renders the second card ("Lechem Emek boxes") showed
the browser's broken-image glyph over an empty square. Its image request
returns `404` from `res.cloudinary.com/.../tzhcgvw3l3wqvdgm7tvv.jpg`.
Screenshot: `768-he-picks.png`. This is the exact empty card the section was
rebuilt on 11 Sep to never show. Locally it is stale seed data, but a business
deleting a photo in production produces the same card.

**Exact fix:** track failed images in page state and filter them out of the
row:

```jsx
const [deadImg, setDeadImg] = useState(() => new Set());
const shelf = (hasDeals ? dealCards : picks).filter((it) => !deadImg.has(it.key));
...
<img src={it.src} alt="" loading="lazy"
     onError={() => setDeadImg((s) => new Set(s).add(it.key))} />
```

Because `shelf` is recomputed from it, the section still falls through to the
honest "No offers yet" state when every image is dead.

### 3. The moving row cannot be stopped on a phone, and under reduced motion it shows every listing twice

`frontend/src/styles/home-v2.css:593-617`

Two separate problems:

- **Touch.** The row pauses only on `:hover` and `:focus-within` (`:606-607`).
  A phone has neither, so the row moves for as long as the page is open, with
  cards sliding under a thumb that is reaching for one. WCAG 2.2.2 requires a
  way to pause moving content that lasts more than five seconds.
- **Reduced motion.** The animation stops and the row becomes scrollable
  (`:615-616`), but both passes stay visible. **Measured** at 1280 with reduced
  motion: 24 cells, `overflow-x: auto`, no animation. A visitor who scrolls it
  sees all twelve listings, then the same twelve again.

**Exact fix:** treat a no-hover device like reduced motion, and in both cases
hide the duplicate pass:

```css
@media (prefers-reduced-motion: reduce), (hover: none) {
  .hv2-marquee { overflow-x: auto; scroll-snap-type: x proximity; }
  .hv2-marquee-track, [dir="rtl"] .hv2-marquee-track { animation: none; }
  .hv2-marquee-cell[inert] { display: none; }
}
```

This selector assumes finding 1's `inert` is in place. It replaces the existing
reduced-motion block at `:611-617`. Tzvi asked for a *moving* row, so this
keeps it moving wherever a pointer can stop it.

### 4. The desktop loop is 4.2 MB, more than twice the hero's own asset budget

`frontend/public/videos/preview-hero/`: `hero-loop.mp4` 4,201,781 B,
`hero-loop.webm` 3,582,273 B. The phone files are fine (1,262,679 / 1,094,614 B).

The hero brief set **under 2 MB per clip**. `LoopHero.jsx:131` sets
`preload="metadata"`, but `autoPlay` + `loop` fetches the whole file anyway, so
every desktop visitor downloads 3.6-4.2 MB before the first scroll. The site
audit that ran the same night flagged this against a 2.5 MB figure, and this
page is about to be promoted to `/`.

**Exact fix:** re-encode the desktop rendition at 1280 wide instead of 1440,
and raise CRF until both files are under 2.5 MB: H.264 roughly 30 → 34, VP9
46 → 50. Keep `-an -movflags +faststart`. Then re-check the loop seam, because
a re-encode can move the join. Do this before promotion, not after.

### 5. The two-second start deadline carried over from the old hero onto a cold phone start

`frontend/src/components/home/LoopHero.jsx:50`, `:89-93`

This is 09-11 finding 3, not fixed; it moved into the new component. The
deadline is 2000 ms for every device, `preload="metadata"` means no media
bytes are buffered before `play()`, and `setFailed(true)` is permanent for the
session. On localhost the phone rendition started in time (`currentTime` 6.5 s
after a 4.5 s wait at 375), but localhost says nothing about cellular.

**Exact fix:** cancel the bail-out when data arrives, not when frames advance,
and give phones longer:

```js
const START_DEADLINE_MS = 2000;
const COLD_START_DEADLINE_MS = 6000;
...
const bail = window.setTimeout(() => {
  if (!video.currentTime) setFailed(true);
}, phone ? COLD_START_DEADLINE_MS : START_DEADLINE_MS);
const arrived = () => window.clearTimeout(bail);
video.addEventListener('loadeddata', arrived, { once: true });
return () => { window.clearTimeout(bail); video.removeEventListener('loadeddata', arrived); };
```

## Improvement of the night

**Mechanism: position bias (primacy in a list).** When people scan a row or a
list of options, the first positions get a disproportionate share of attention
and clicks, independent of quality. See Craswell et al. 2008 on position bias
in result lists, and the serial position effect in memory. In a static row the
newest listing would own that first slot.

**Surface:** "Recently added", `HomePreview.jsx:405-431` and
`home-v2.css:593-598`.

**What is wrong now:** the animation starts when the page mounts, not when the
row is seen. A visitor who reaches the section 20 seconds in lands on an
arbitrary offset: somewhere in the middle of the list, or on the duplicate
pass. The listing the row exists to show first, the newest one, has no reliable
chance of being in view at the moment of attention. That wastes the one slot
that gets looked at.

**What to change:** start the loop at card one when the row scrolls into view.
The page already runs an IntersectionObserver for `.reveal` (`useReveal`,
`HomePreview.jsx:82-96`), and the marquee carries `reveal`. When it first
intersects, call `track.getAnimations()[0].currentTime = 0`, once per page
view. No new data, nothing invented, and it does not change what Tzvi asked for
(a moving row).

**What to expect if it works:** among clicks on the row, a larger share landing
on `recent[0..2]` than on later positions, where today the click distribution
is roughly flat across the twelve. Cards carry `data-testid="stays-card-{id}"`,
so the position of each click can be recorded against `recent`.

**What would falsify it:** if clicks stay flat by position after the reset,
visitors are choosing by photo rather than by position, and the row does not
need the reset.
