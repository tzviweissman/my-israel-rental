## Blockers

### 1. The signature canvas fix never runs, and the library wipes the signature on every window resize

`frontend/src/pages/SignContract.js:42-70`

The effect that sizes the drawing buffer and preserves strokes across a resize is
dead code on the normal path:

- Its dependency array is `[signed]` (`:70`).
- `signed` is `false` at mount and only flips after a successful POST.
- `if (loading) return <Loader2 …>` at `:148` means the first render has **no
  canvas in the DOM**, so the effect hits `if (!canvas) return undefined` at `:45`
  and attaches nothing.
- When `fetchContract()` resolves and the form renders, `signed` has not changed,
  so the effect does not re-run. `fit()` never executes and the `ResizeObserver`
  is never observed.

What the page runs on instead is the library's own handler. In
`frontend/node_modules/react-signature-canvas/dist` (v`^1.1.0-alpha.2`),
`defaultProps = { clearOnResize: true }`, `on()` registers
`window.addEventListener("resize", _checkClearOnResize)`, and
`_checkClearOnResize` calls `_resizeCanvas()`, which ends in `e.clear()` whenever
`canvasProps.width`/`height` are undefined - which is now the case, because
`bfbb3a0` removed `width: 600, height: 160` from `canvasProps` (`:304-308`).

So the removal of the fixed `width`/`height` is what actually fixed the offset-ink
problem: the library sizes the buffer correctly at `componentDidMount`. But
`clearOnResize` is left at its default, meaning **any window resize clears a
half-drawn signature** - on a phone that is the soft keyboard opening while the
name field above still has focus. The comment at `:55-57` ("Someone mid-signature
when the keyboard opens on a phone must not lose it") describes behaviour the code
does not deliver.

Exact fix, two parts:

1. `:70` - change the dependency array from `[signed]` to `[contract, signed]`, so
   the effect re-runs on the render where the canvas first exists.
2. `:294` - add `clearOnResize={false}` to the `<SignatureCanvas>` element, so the
   library stops clearing and the effect's `toData()`/`fromData()` restore at
   `:58` and `:63` is the only resize path.

Setting `canvas.width` resets the 2D transform, so the `scale(ratio, ratio)` at
`:61` after the library's own `scale` is correct, not a double-scale.

### 7. The signature field has no accessible name and no non-pointer path

`frontend/src/pages/SignContract.js:292-309`

`:292` is `<label className="…">{t('sign.drawSignature')}</label>` with no
`htmlFor`, and `<canvas>` is not a labelable element, so nothing associates them.
The `canvasProps` object at `:304-308` was rewritten by this commit and carries
`className`, `style` and `data-testid` only. A screen reader reaches an unlabelled
canvas; a keyboard-only user reaches nothing at all. This is the field that makes a
rental agreement binding.

Exact fix, at `:304-308`, add to `canvasProps`:

```js
'aria-label': t('sign.drawSignature'),
role: 'img',
```

That fixes the name. It does not fix operability - a pointer is still required to
draw. The honest remedy is a typed-signature fallback (name rendered in a script
face, submitted through the same `signature_data` field), which is a separate piece
of work and should be filed as one rather than left implicit.

## Improvement of the night

**Mechanism: ambiguity aversion.** People discount an option whose outcome
distribution is unknown far more steeply than one whose risk is merely bad but
specified - the Ellsberg result, where subjects pay to avoid the urn with unstated
proportions even when it is not the worse bet. The behavioural signature is
hesitation and abandonment at the moment of an irreversible commitment, and it is
triggered by an *unanswered* question, not by a bad answer.

Not previously proposed here. The six prior audits used the halo effect
(2026-09-01), the peak-end rule (09-02), loss aversion (09-03), denominator neglect
(09-04-2), endowed progress (09-05) and cognitive fluency (09-06).

**Surface:** the signing form on `/sign/:signToken` - the last screen before a
person who has no account here puts a binding signature on a rental agreement.

**File:** `frontend/src/pages/SignContract.js:334`, plus new keys in
`frontend/src/locales/en.js` and `he.js` under `sign`.

Everything the page says before the button is about what the signer is giving up.
`:334` renders `sign.signingDisclaimer`: *"By signing, you agree to the terms set
out in this agreement. Your signature is legally binding."* Above it, `:187` shows a
filename and `:225` offers a collapsed "View Contract Text". Nothing anywhere states
what the signer *gets*: whether a copy exists afterwards, whether it includes their
signature, whether this link still works tomorrow, whether they need to save
something now. An external signer, on a phone, with no account to log back into, is
being asked to commit against an unspecified aftermath. That is the exact shape
ambiguity aversion predicts a person will stall on.

Tonight's commits made the answer good for the first time. `f4a96e9` generates a
signed document; `bf57550` opened `/contracts/sign/{token}/file` to the token
holder; `SignContract.js:241-247` already flips the button to "Download signed
contract" once `signed` is true, and the comment at `:242-244` confirms that URL
serves the agreement *with* the signature page attached. The capability is built and
the person is told about it only after they have committed - which is precisely
backwards, because the reassurance is worth most before the button, not after it.

**What to change:** one sentence, before the action rather than after it. At `:334`,
render a second line under the disclaimer:

```jsx
<p className="text-xs text-gray-500 mt-2">
  {t('sign.afterSigning')}
</p>
```

with `en.js`: `afterSigning: 'After you sign, you can download a copy of this
agreement with your signature on it, from this page.'` and `he.js`:
`afterSigning: 'אחרי החתימה תוכלו להוריד מהעמוד הזה עותק של ההסכם עם החתימה שלכם.'`

No number is invented, no urgency is manufactured, nothing is hidden. It is a true
statement about a feature that shipped last night, moved to the moment it is load-
bearing.

**What I would expect to see if it worked:** a fall in the share of sessions that
load `/sign/:signToken`, expand "View Contract Text" at `:225`, and leave without
POSTing to `/contracts/sign/{token}`; and a rise in `download-contract-btn`
(`:239`) clicks in the signed state, because the person now arrives at that button
already expecting it. If neither moves, the hesitation was not about the aftermath
and the sentence costs one line.
