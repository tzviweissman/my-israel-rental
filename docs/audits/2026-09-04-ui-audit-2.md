## Should fix

### 1. `zoom: 0.8` on the preview page shrinks every control and every font, on phones too

`frontend/src/styles/home-v2.css:420` (added this batch, `8ba5e2f`)

```css
body.theme-preview #root { zoom: 0.8; }
```

The rule is unconditional. There is no media query around it and none of the five
media queries in the file re-scale it. `HomePreview.jsx:68` puts `theme-preview`
on `<body>`, so this applies to the whole page at every viewport, 375px included.

The commit's reasoning is desktop-only and is recorded as such in the comment
above the rule: *"Tzvi recorded the preview with the browser at 80% and asked for
that size at 100%."* That was a desktop browser at a desktop width. CSS `zoom`
scales every computed length in the subtree, so the same rule that fixes "too big
and too close up" on a wide monitor also takes 20% off every tap target and every
font on a phone, where nothing was too big to begin with.

Measured off the source (arithmetic, not rendered - see "Not checked"):

| Element | Source | Nominal | At `zoom: 0.8` |
|---|---|---|---|
| Carousel prev/next button | `coverflow-carousel.jsx:419,427` (`p-2` + `size-5`) | 36 x 36 px | **28.8 x 28.8 px** |
| `.hv2-gcard-cap small` | `home-v2.css:336` | 11.5 px | **9.2 px** |
| `.hv2-eyebrow` | `home-v2.css:167` | 12 px | **9.6 px** |
| Carousel spec table | `coverflow-carousel.jsx:449` | 12 px | **9.6 px** |
| Carousel caption | `coverflow-carousel.jsx:444` | 13 px | **10.4 px** |
| `.hv2-gcard-cap b` | `home-v2.css:335` | 13 px | **10.4 px** |
| `.hv2-hero-tagline` at 375px | `home-v2.css:85` (`clamp(20px,2.4vw,34px)`) | 20 px | **16 px** |

The carousel arrows render on this page (`showPagination={false}` but
`showNavigation` is set, `HomePreview.jsx:249-257`). At 28.8px they clear WCAG
2.5.8 Target Size (Minimum, AA, 24px) but fail 2.5.5 (AAA, 44px) and fail the
44px bar this audit is held to. The 9.2px caption subtitle is the sharper problem:
it is white-on-photo text below the size at which the scrim's measured contrast
(see Verified clean) is worth anything.

**Fix.** Scope the rule to the widths it was reasoned about:
`@media (min-width: 900px) { body.theme-preview #root { zoom: 0.8; } }`. The
900px breakpoint already exists twice in this file (`:285`, `:349`), so this adds
no new breakpoint. Separately, raise the carousel arrows to 44px (`p-3` with
`size-5` gives 44px exactly) so they survive the zoom at any width.

### 2. The gradient phrase's letters take the blob colour at the lit peak, and two of the four blobs are too light to carry text on white

`frontend/src/components/ui/gradient-text.jsx:41-45`, `frontend/src/styles/theme-flow.css:92-96`,
`frontend/tailwind.config.js:92-95`

The blob layer is `absolute inset-0` and is painted **after** `children`, with
`mix-blend-lighten`. Lighten takes the per-channel maximum, so wherever a blob
overlaps a letter, ink `#111827` (17,24,39) loses every channel to the blob and
the letter is repainted in the blob's colour. The white surface is unaffected
(255 is already the maximum). The file's own comment states the intent - *"the
phrase goes ink -> colour -> ink"* - so this is the designed behaviour, not a bug
in the blend.

The four blob colours, and the contrast each one gives on the white surface once
it has replaced the ink:

| Variable | Colour | Letters become | Contrast on white |
|---|---|---|---|
| `--color-1` | `#1C8DD4` | `#1C8DD4` | 3.61:1 |
| `--color-2` | `#3FB6EE` | `#3FB6EE` | **2.30:1** |
| `--color-3` | `#0F5E8F` | `#115E8F` | 6.95:1 |
| `--color-4` | `hsl(197 83% 85%)` = `#B9E7F8` | `#B9E7F8` | **1.33:1** |

(Unlit, the phrase is ink on white at 17.74:1.)

This is not a flicker. `gradient-breathe` (`tailwind.config.js:92-95`) is
`0%,100% { opacity: 0 }` / `35%,65% { opacity: 1 }` on a 7s loop, so the light
layer sits at **full opacity for 2.1 seconds of every 7**.

The threshold that applies is 4.5:1, not 3:1, on phones. `.hv2-hero-tagline` is
`clamp(20px, 2.4vw, 34px)`; at 375px that is 20px, and finding 1's `zoom: 0.8`
takes it to 16px rendered - below the 24px/18.66px-bold large-text boundary. So
at mobile widths this is body text sitting at 1.33:1 for two seconds in every
seven.

**Caveat, stated plainly.** The figures above model the parent's
`mix-blend-lighten` only. Each blob additionally carries `mix-blend-overlay` and
`blur-[1rem]`, which will attenuate the delivered colour by an amount I could not
compute and could not render (no browser in this sandbox - see "Not checked").
The direction and the mechanism are certain; the exact ratio at the peak is an
upper bound on lightness, not a measurement. Treat 1.33:1 as "needs measuring
before this page is promoted," not as a confirmed number.

**Impact is capped.** `GradientText` has exactly one call site,
`HomePreview.jsx:179`, on the `noindex` and unlinked preview route. Like the
first pass's finding 1, this blocks promoting the page, not production.

**Fix.** Drop `--color-4` and `--color-2` from the blob set for this component
(or darken them until the lighten result clears 4.5:1 on white), leaving the
accent, its deep end and the dark. `--color-3` at 6.95:1 and `--color-1` at
3.61:1 are the two that can carry a letter.

## Improvement of the night

**Mechanism: denominator neglect.** A count is uninterpretable without the window
it was counted over, and people reliably read the numerator and skip the
denominator. This site's standing choice to show transaction counts rather than
star averages is that mechanism applied correctly - the audit brief names it. The
new dashboard front page inverts it.

**Surface:** the Leads and Visitors cards on the dashboard Overview.
**File:** `frontend/src/components/dashboard/OverviewTab.jsx:155-167`, with
`backend/utils/view_tracking.py:193-196` as the cause.

The card is built like this:

```jsx
label={t('overview.visitors', 'Visitors, last 30 days')}   // text-sm
value={visitors ? visitors.period : '—'}                    // text-2xl font-bold
sub={visitors ? sinceLine(visitors.since) : ...}            // text-xs, --brand-muted
```

The component's author saw this coming. The header comment at `:28-30` says:
*"'Counting since' is shown instead, because a small number on a young counter is
not a verdict."* That is exactly right, and it is the right instinct. Two things
stop it from working.

**First, the correction is set in the smallest and faintest type on the card.**
"last 30 days" is in the label; the number is 24px bold; the qualifier that makes
the number mean anything is 12px in `--brand-muted` underneath. The frame wins
over its own footnote. An owner three days into a listing reads "**Visitors, last
30 days: 4**" - which is a verdict, and a bad one - when the honest reading is
four visitors in three days.

**Second, and worse, `since` does not mean what the card implies.**
`view_tracking.py:193-196`:

```python
first = await db[COLLECTION].find(base, {"at": 1}).sort("at", 1).limit(1).to_list(1)
if first:
    since = il_day_of(first[0].get("at"))
```

`since` is the day of the **first recorded event**, not the day the listing went
live. Two consequences:

- "Counting since 1 Sep" reads as *"we began counting on 1 Sep."* It actually
  means *"your first visitor arrived on 1 Sep."* A listing live since June with
  its first view yesterday reports "Counting since [yesterday]," which flatters
  rather than misleads - but it is still not what the sentence says.
- When there are **no events at all**, `since` is `None`, and `sinceLine` falls
  through to `notYet` = **"Just switched on"** (`:135-136`). That string is shown
  to a listing that has been live and unvisited for six months. It is the one
  line on this page that asserts something the data does not support, on a page
  whose own header comment is a 30-line argument against exactly that.

**What to change.** Give the counter its real denominator: days since the listing
went live, which the site knows and this endpoint does not currently return.

1. Return a `live_since` alongside `since` from the two summary endpoints -
   the earliest `created_at` across the caller's listings/gigs, which is already
   in those documents.
2. In `OverviewTab`, when `live_since` is more recent than the 30-day window,
   put the real window in the **label**, where the frame is:
   `t('overview.visitorsShort', 'Visitors, last {{n}} days', { n: ageInDays })`.
   The number stops being compared against a month it never had.
3. Replace `notYet` with the two honest cases it is currently collapsing:
   live under a day or so -> "Just switched on"; live longer with zero events ->
   "No visitors yet, live since {{date}}". Both are statements of fact.

No invented figures, no scarcity, no new endpoint - one extra field on two
responses that already do this aggregation. It is the same rule the rest of this
file already follows, applied to the one line that currently escapes it.

**What I would expect to see if it worked.** The dashboard stops telling
week-old businesses that they had 4 visitors in a month. Concretely: the "Just
switched on" string should become rare rather than the default empty state, and
it should never appear on an account whose oldest listing predates the 30-day
window. That last one is checkable from the data without asking anybody.

  `.hv2-hero-tagline:84` correctly reads `var(--font-head)`, which is what makes

- **The `top`/`left`/`right`/`bottom` values added to `tailwind.config.js:2169-2186`
  do not need RTL mirroring.** They are keyframe waypoints for the four drifting
  blur blobs - decorative motion with no reading order.
- **`OverviewTab` invents nothing.** Four cards, four real endpoints, no
  period-over-period delta anywhere, and a header comment that explains why the
  delta is absent rather than estimating it. The improvement above is a
  refinement of this component's own standard, not a correction of its direction.

## Resolution (4 Sep 2026)

Fixed in the commit that added this file: **1** (the 0.8 layout is
desktop-only, `min-width: 1024px`; the carousel arrows are 44px), **2** (the
phrase's blobs use only the accent and its deep end), **3** and **4** (every
dash named, plus the three chart titles on the live dashboard), **5** (the
cards say 0), **6** (the pagination dot sits in a 44px button). The
improvement is built: both summary endpoints return `live_since`, the day
the caller's oldest listing went live; the Leads and Visitors labels count
over the listing's real age when that is shorter than the window; and a
listing with no events reads "None yet, live since <date>" once it is older
than a day. `scripts/check-dashboard-shell.mjs` asserts a minute-old listing
counts over one day and no card shows a dash.
