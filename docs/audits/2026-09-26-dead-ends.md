## Dead-end promises: destination lacks the affordance

- **`backend/routes/admin/chats_nudge.py:525,540`** - `GET
  /admin/auto-owner-nudge/status` and `POST
  /admin/auto-owner-nudge/run-now`. The `status` handler's own docstring
  says this exists "so the admin Chats tab can render an 'auto-nudges on ·
  12h threshold' strip with counts" and give admins a manual escape-hatch
  trigger. `frontend/src/components/admin/ChatsTab.jsx` has no reference to
  `auto-owner-nudge` at all - only the unrelated, already-wired per-conversation
  manual `nudge-owner` button. The status strip and the manual run-now
  button the backend was built to support were never added to the tab.
  **Fix:** build the strip + button in `ChatsTab.jsx` (both endpoints
  already work correctly), or drop the promise from the backend comment if
  it's no longer wanted.

- **`backend/routes/admin/marketplace.py:255-274`** -
  `posts_awaiting_moderation` (count of requests with `report_count>=1` or
  `needs_review=True`). The surrounding comment frames this as the whole
  point of the moderation feature ("a report button that files into a
  drawer nobody opens is worse than no button"). The drawer now exists
  (`RequestReportsTab.jsx`, see below) but
  `frontend/src/components/admin/AttentionQueue.jsx`'s `rows` array
  (lines 43-92) never reads `data.posts_awaiting_moderation` - it has a row
  for a different count (`requests_expiring_unanswered`) but none for the
  moderation backlog itself. The one panel whose job is "what needs a
  person today" doesn't point at the queue that answers that. **Fix:** add
  a row to `AttentionQueue.jsx` for `posts_awaiting_moderation` -> `?tab=requests`.

- **`backend/routes/admin/events.py`** (added 18 Sep, commit `14043a7`) -
  `GET /admin/email-health` now also returns `postmark_token_present`,
  `send_failure_counts`, and `recent_failures`, and a new one-shot `GET
  /admin/email/diagnose?email=|user_id=` exists, with a comment explicitly
  framing it as "so support can answer 'why didn't user X get the email?'
  in one click instead of grepping Mongo shells." `EmailHealthTab.jsx`
  reads only the older fields (`delivered`/`bounced`/`complained`/
  `delivery_rate_pct`/`suppressed_users`/`recent_events`); none of the
  three new fields are shown, and no search box anywhere calls
  `/admin/email/diagnose` - it only exists as a curl command today. Judged
  lower-severity than the two above since it's genuinely usable as a
  direct-API admin tool, but the "one click" framing in its own comment is
  a promise the UI doesn't keep yet. **Fix:** add a lookup box to
  `EmailHealthTab.jsx`, or reword the comment if this is meant to stay
  API-only.

## Wrong destination

- **`frontend/src/components/admin/OverviewTab.jsx:87` and
  `frontend/src/components/admin/AttentionQueue.jsx:45-50` ->
  `RequestReportsTab.jsx`** - Two different admin controls promise two
  different, specific counts and both land on the same generic tab, which
  matches neither:
  - Overview KPI card **"Open requests: N"** (`stock.open_requests` - every
    open, non-expired request on the board) links via `go:'requests'`.
  - Attention-queue row **"N requests expiring within 3 days with no
    responses"** (`requests_expiring_unanswered`, `contact_count<=0`) also
    links via `go:'requests'`.
  - Both open `RequestReportsTab` (label "Requests"), which only queries
    `GET /admin/request-reports` - i.e. `report_count>=1 OR needs_review`,
    unhidden - a moderation queue of flagged posts, unrelated to either
    number. An admin clicking a KPI that says "47 open requests" lands on
    a queue that usually says "Nothing waiting on a decision." Not a fresh
    regression - the KPI's `go` target was set in the same commit
    (`1dbbca5`, merged 2026-09-15) that built the moderation tab, so it
    predates this baseline being caught - but it is a live mismatch on the
    current head, not hypothetical.
  - **Fix, either valid:** (a) give `RequestReportsTab`/its endpoint an
    optional filter mode so each control can pass one and the tab shows
    what was promised (the pattern Services already uses for its
    `no-photo`/`unverified` filter); or (b) reword the two labels to
    describe what the tab actually shows ("Reported posts") and stop
    implying they link to a browsable list of the numbers shown.
