# Dead ends — 2026-09-24

Scheduled dead-ends audit, following `.claude/skills/dead-ends/SKILL.md`. Three
parallel passes (forward link resolution, backward promise-to-destination,
orphaned capabilities) run against `frontend/src/App.js`'s route table,
`backend/routes/*` guards, and everything that shipped since the last
dead-ends audit (`docs/audits/2026-09-14-dead-ends.md`) — 122 commits,
including a dashboard reorg by role, an Insights/Overview tab with a Monday
digest email, an Automations engine (auto-accept, price tips, "cleaning sent
at checkout", "upkeep on a calendar"), the site "walk" onboarding guide,
account restore, flag-gated verified reviews + Google review import, a paid
page-upgrade tier, Network "find partners by kind", and a new AI page-recipe
layout engine.

**Headline: 5 of 9 items carried over from 09-14 are now fixed** (admin
request-reports moderation, courier "leave a business", `BlocksHero.jsx`
dead file, `GET /properties/featured` wired up, Requests-board
`condition`/`min_price`/`max_price`/`include_sold`), each independently
confirmed by at least one agent reading current code rather than trusting
commit messages. This run also found **2 new wrong-destination bugs** on
promotional feature cards and **4 new orphaned-capability items**, the most
notable being a whole new backend module (`utils/page_recipes.py` +
`utils/page_rules.py`, the 24 Sep "category study" layout engine) that ships
fully built and tested but is called from nowhere in the app.

## Dead-end promises: destination lacks the affordance

None found live. Every setup-checklist item, empty-state CTA, toast, and
email link chased this pass (Insights toggle/email, Automations panel, the
site walk, account restore, verified reviews, Google review import, page
upgrade) resolves to a real, visible, enabled control — see "Verified
working" below for the trace.

One thing that reads like it should be here but isn't: **the "AI page
recipes" / "drafts until the owner publishes" promise does not currently
exist live in the product**, so it can't be a dead end — there's no
draft/publish UI anywhere, no `is_published` field, and business pages save
and go live immediately (`BusinessPageEditor.jsx`'s `save()` → `PATCH
/marketplace/businesses/{id}`, no draft state). `docs/page-rules` /
`page_recipes.py` are pre-wiring for a feature that hasn't shipped its UI
yet. This is a build gap, filed under Orphaned capabilities below, not a
broken promise — nothing in the current UI tells a user their page is a
draft.

## Wrong destination

1. **`frontend/src/data/featureLibrary.js:69-74`, feature
   `hand-off-the-repeat-work`** ("Automations", `audiences: ['business',
   'host']`, `cta: '/dashboard?tab=network&view=automations'`). For a pure
   property host with no marketplace business, this CTA lands on
   `NetworkTab.jsx`, which requires owning a business before showing
   anything but a hard wall: "Add your business, free, to connect with
   other businesses" (`NetworkTab.jsx:129-137`) — nothing about
   automations, cleaning-between-guests, or maintenance reminders. The
   host-only automations in `AutomationsPanel.jsx` (`cleaningBetweenGuests`,
   `checkInDetails`, `yearlyPlumber`, `yearlyPaint`, `monthlyGarden`,
   `yearlyReminder`, all `forHosts: true`) are unreachable for any host who
   hasn't also registered a business entity. The gap is disclosed rather
   than silent (the site's own "walk" is aware of it — `tourSteps.js:54-55`
   falls back to `network-add-business`), and the path does eventually
   work after the detour, but the promise's own destination doesn't contain
   what the promise describes. **Fix:** either show host-only automations
   at a destination that doesn't require a business first, or change the
   card's CTA copy/target for the host audience to be explicit about the
   "add a business" step. Flagged independently by two of the three audit
   passes.

2. **`frontend/src/data/featureLibrary.js:120-123`, feature
   `sign-without-printing`** ("Sign a contract without printing anything",
   CTA label "Open my contracts" → `/dashboard?tab=contracts`). This card's
   `audiences` includes `traveller` (renters), but `Dashboard.js:420-422`
   hard-gates the `contracts` tab on `isPropertyLister` — a renter
   following this CTA gets a dashboard where `contracts` isn't even in
   `useDashboardNav`'s visible tabs, so nothing highlights and nothing
   renders. A renter's real signed-contract affordance exists and works
   (per-booking "View/Download signed contract" in `BookingRow.jsx:175-184`
   / `BookingChip.jsx:130-148`, reached via `?tab=bookings`) — the CTA just
   points at the wrong tab for that audience. **Fix:** one-line change,
   `cta: '/dashboard?tab=bookings'` for the `traveller` audience (or split
   the card's CTA by audience the way other multi-audience cards in the
   same file already do).

## Making it cheaper next time

Added `scripts/check-dead-ends.mjs` (skill Part 7): parses the route table
out of `App.js`, resolves every literal `to=`/`navigate()` target against
it, and fails (exit 1) on anything unresolvable — no dev server needed. Ran
clean this pass (61 routes, 0 unresolvable literal targets, 85 dynamic
targets correctly skipped rather than guessed at). It also prints a
heuristic "possible orphan endpoint" hint list (backend routes whose last
path segment doesn't appear anywhere in the frontend source) — this is
explicitly not a pass/fail check, since it has known false positives for
admin/webhook/cron endpoints (confirmed: this run's 5 hits are all
legitimately internal — a Postmark webhook, a 3D-tour provider webhook, a
poll-pending sweep, an admin run-now button, a digest-send endpoint). Route
resolution and orphan-endpoint detection automate cleanly per the skill;
whether a resolvable destination actually contains the promised affordance
still needs a human pass, which is what this file is.
