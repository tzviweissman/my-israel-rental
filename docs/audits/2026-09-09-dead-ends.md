# Dead ends — 2026-09-09

**Run:** scheduled. Method: `.claude/skills/dead-ends/SKILL.md` — route table first, then three
parallel passes (forward: does every control resolve; backward: does every promise have a home;
orphaned capabilities), cross-checked against `frontend/src/App.js` and the relevant
`backend/routes/*` guards. ~270 tool calls across three agents plus direct verification of the
highest-severity claims before writing this up.

This repo has been through this exact audit repeatedly (2026-09-03 through 09-08); most of what
those runs fixed is still fixed and is listed under Verified working, not re-litigated. New surface
since the last audit (the store-orders/courier rework, 05–08 Sep) was checked specifically and is
largely sound. What follows is what's still broken or newly introduced.

## Broken: goes nowhere or errors

### 1. A gig booking has no provider-facing UI at all — the whole accept/decline/complete flow is unreachable
`backend/routes/marketplace/gigs.py:1067-1111` (`POST /marketplace/gigs/{id}/book`) is fully wired
from the client side — `frontend/src/pages/GigDetail.jsx:200` calls it for any `booking_mode:
"in_platform"` gig (appointment or deliverable), with real time-slot/availability enforcement and a
hold timer. It writes to `db.marketplace_bookings` with `status: "pending"`.

There is **no `GET` endpoint that lists a provider's bookings**, and the one mutation endpoint that
exists — `PATCH /marketplace/bookings/{booking_id}` (`gigs.py:1117-1141`, accepting
`accepted|declined|completed|cancelled` plus a `reply`) — has zero callers anywhere in
`frontend/src`. Confirmed by grepping `marketplace_bookings|provider_reply` across the entire
frontend: no hits outside the backend. A provider who receives a booking gets an in-app
notification that one is pending, and then has no page, tab, or button anywhere to see it, accept
it, decline it, or mark it complete. This is a live, current, money-adjacent flow (holds, EMA
response-time tracking, tier pricing), not a leftover — it just never got a UI on the receiving end.

**Fix:** build a "Bookings" pane in the provider's dashboard (a `MyGigsTab`/dedicated tab) backed by
a new `GET /marketplace/bookings?as=provider` (or similar) endpoint, wired to the existing
`PATCH /marketplace/bookings/{id}`. This is new engineering, not a link fix — flag for
prioritization rather than a quick patch.

### 2. `/chat/:propertyId` and `/payment/success` guards drop the destination on sign-out
`frontend/src/App.js:385` and `:387` still use a bare `<Navigate to="/auth/login" />` instead of the
`ToAuth` helper (`App.js:71-74`) that every other gated route was moved to during the 2026-09-03
audit specifically to stop this class of bug. Both in-app callers of `/chat/:id` (PropertyDetail,
SubleaseDetail, BusinessPage, GigDetail, Navigation, MessagesTab, BookingChip) pre-check `user`
themselves and build their own `?redirect=`, so this only bites: (a) a bookmarked/shared chat URL
opened while signed out, and (b) a PayPal `return_url` redirect (`backend/routes/payments.py:170`,
`subscription.py:276`) landing when the session has expired — the user completes a payment and is
bounced to a generic login with no way back to the confirmation page.
**Fix:** change both to `<Route path="/chat/:propertyId" element={user ? <Chat /> : <ToAuth />} />`
and the same for `/payment/success` — one-line each, same pattern already used everywhere else.

## Dead-end promises: destination lacks the affordance

### 3. `/why-list` undersells a feature that's already shipped
`frontend/src/pages/WhyList.jsx:47-53` — the `ROADMAP` array (rendered separately from `BENEFITS`,
explicitly labelled "Built but NOT shipped") includes `{ key: 'dashboard' }`, copy (`en.js:3082-3083`)
*"Leads and views dashboard — See how many people viewed your listing and got in touch. **Being
built now.**"* This is inverted from the usual bug: the feature **is** live —
`frontend/src/components/dashboard/PerformancePanel.jsx` shows exactly this (views + lead counts,
per-listing) and is already rendered in both `MyGigsTab.jsx:517` and `PropertyList.jsx:466`;
`frontend/src/data/featureLibrary.js:131-137` (slug `see-what-works`) independently confirms it as
built. A provider who reads the marketing page as "coming soon" and then finds it already live on
their own dashboard reads that as evidence the site's copy can't be trusted.
**Fix:** move the `dashboard` entry from `ROADMAP` to `BENEFITS` in `WhyList.jsx` — copy-only, no
engineering.

### 4. The onboarding tour never shows business owners their own share/QR panel
`frontend/src/components/tour/tourSteps.js:59-75` gates the "share your page" tour step to
`roles: ['lister']` only, with a comment: *"Businesses do get a QR, but only on the public business
page; there is no control for it anywhere in their dashboard."* That's no longer true —
`frontend/src/components/dashboard/MyBusinessesTab.jsx:381-392` renders a `ShareListingsPanel`
(link + QR + print) per business card, with `data-tour="business-share"` already placed on the
first card specifically for tour targeting. No `TOUR_STEPS` entry references it.
**Fix:** add a `business-share` tour step for the `business` role pointing at that anchor, or delete
the now-stale comment if the tour step is deliberately still being deferred.

## Verified working

- **ToAuth return-to mechanism** (`App.js:71-74`) — correctly appends `?redirect=` for every route
  still using it (`/dashboard`, `/dashboard/settings`, `/services/post-job`, `/services/create-gig`,
  `/businesses/post-job`, `/businesses/add`, `/orders/print`), and `Auth.js`/`SignupJoin.jsx` honour
  it on return. Only the two routes in finding #2 were missed when this was rolled out.
- **Primary contact/message controls on every listing type** self-guard correctly and preserve
  intent: property (`PropertyDetail.js`), sublease (`SubleaseDetail.js`), gig/business
  (`GigDetail.jsx`, `BusinessPage.jsx`), and requests (`RequestDetail.jsx`, via server-issued
  `chat_url`).
- **Dashboard `?tab=`/query-string deep links** — checked against `ALL_TAB_IDS` in
  `useDashboardNav.js`: booking highlight (`Navigation.js:270`), `details=`/`services=` on
  `?tab=my-businesses`, `?edit=<id>` from the availability-extension email, `?section=notifications`
  from all three "-emails-off" pages, `?business=&from=&to=` on `/orders/print`, and every
  backend-generated notification `action_url` (`deliveries`, `orders`, `my-orders`,
  `properties&edit=`) — all valid and all read by their destination.
- **Post-job / create-gig / post-request CTAs** — self-guard, round-trip drafts through
  `localStorage` correctly (`PostRequest.jsx`), and surface real backend validation errors via toast
  rather than failing silently.
- **Store-orders/courier subsystem** (new since 05 Sep) — courier invite flow
  (`invite_courier`/`list_couriers`/`remove_courier`), default-courier auto-assignment, and all three
  notification `action_url`s (`?tab=deliveries`, `?tab=orders`, `?tab=my-orders`) resolve to real,
  correctly-gated dashboard tabs. `DeliveriesTab`/`OrdersTab`/`MyOrdersTab` are all wired.
  `showGigTabs` gating on the `orders` tab is satisfied whenever a business-owner notification fires,
  since only business owners receive it.
- **Requests board `condition`/`min_price`/`max_price`/`include_sold`** (previously flagged, fixed
  5 Sep) — confirmed still wired and deep-linkable, with a pinned backend test.
  `GigPatch.status: "paused"` and `JobPatch.status: "awarded"` (previously flagged, fixed) —
  confirmed both have real setters and (for `paused`) the enforcement fix (detail/booking routes
  honouring status) holds.
- **Admin-only tooling sampled**: impersonation (`UsersTab.jsx`), chat re-attach
  (`admin/ChatsTab.jsx`), duplicates/listings image links — all real handlers, no no-ops.
- **Capability-token pages**: `ShortLinkRedirect` (`/p/:slug`), `ProviderRedirect`
  (`/businesses|services/provider/:userId`), `AuthDeeplink` — all resolve server-side with honest
  failure fallbacks, no silent dead ends.

## Suggested priority

1. **#1 (gig booking has no provider UI)** — highest impact by far: a live money-path feature is
   completely one-sided. This needs a small feature build (a provider bookings pane + a GET
   endpoint), not a link fix; flag for scoping rather than doing inline.
2. **#2 (`/chat`, `/payment/success` guard fix)** — one line each, same pattern as everywhere else in
   the file.
3. **#3 (WhyList copy)** — copy-only, zero risk, fixes a page actively selling to paying providers.
4. **#4 (tour step)** — small, either add the step or delete the stale comment.
5. Everything under Orphaned capabilities is lower urgency — mostly admin/ops surfaces or
  intentionally-dormant code — except the `category`/`rental_kind` requests-board filter gap, which
  is the same class of bug (filters going to die) as two previously-fixed instances on the same
  endpoint and would be cheap to close given the UI pattern already exists for the other request
  filters.
