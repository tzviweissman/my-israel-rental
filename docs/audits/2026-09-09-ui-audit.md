## Blockers

### 1. Every money figure on the customer path is hardcoded `₪`, and the backend supports four currencies

`263dc99` is titled *"A website order keeps the store's currency"* and the backend does exactly that: `_CURRENCY_SYMBOL = {"ILS": "₪", "USD": "$", "EUR": "€", "GBP": "£"}` (`backend/routes/marketplace/orders.py:67`), the order-form payload carries `currency` per product (`:1695`), `place_website_order` resolves one currency per order and rejects mixed baskets (`:1785-1788`), and `currency` is returned on the created order (`:1882`), the order list (`:1329`) and the customer's track payload (`:1523`).

The frontend reads it in exactly one place — the per-product price line — and hardcodes `₪` everywhere else:

| `frontend/src/pages/OrderPage.jsx:211` | per-item price — **correct**, reads `p.currency` |
| `frontend/src/pages/OrderPage.jsx:313` | line total — `₪` |
| `frontend/src/pages/OrderPage.jsx:314` | delivery fee — `₪` |
| `frontend/src/pages/OrderPage.jsx:315` | **order total** — `₪` |
| `frontend/src/pages/OrderPage.jsx:175` | confirmation total — `₪` |
| `frontend/src/pages/OrderPage.jsx:229, 250` | fee chip, minimum-order line — `₪` |
| `frontend/src/pages/OrderTrackPage.jsx:141` | tracker total — `₪` |
| `frontend/src/components/dashboard/MyOrdersTab.jsx:64` | customer's own order total — `₪` |
| `frontend/src/components/dashboard/OrderCard.jsx:88, 96` | order total, amount paid — `₪` |

**User-visible impact.** A store priced in USD shows a customer `$18` next to the item and `₪18` on the line total, the order total, the confirmation, and the tracking link. A courier is told to collect `₪18` for an eighteen-dollar order. This is a false claim about money, which `site-audit` §1 ranks highest and CLAUDE.md's "never invent numbers" rule covers directly.

**Fix.** Add `frontend/src/utils/currency.js` with `const SYMBOL = { ILS: '₪', USD: '$', EUR: '€', GBP: '£' }; export const money = (n, cur) => `${SYMBOL[cur] || `${cur} `}${Number(n).toLocaleString()}`;` — mirroring `_CURRENCY_SYMBOL` including its `currency + " "` fallback. Replace every `₪${…}` above with `money(x, o.currency)`. The order object already carries `currency` on every payload listed, so no API change is needed. For the three `(₪)` *labels* in `OrdersTab.jsx`, interpolate the store's settings currency rather than baking the glyph into the string.

## Improvement of the night

**Mechanism: implementation intentions (Gollwitzer).** Stating a plan in explicit
*when-and-where* form raises follow-through markedly over holding the same
intention in general form; the effect is one of the most replicated in
behavioural science and it works by making the situational cue itself the
trigger for the action, rather than requiring the person to remember to
remember. The pattern is not persuasion — the person has already decided. It
converts a decision they have made into a specific occasion they will act on.

**Surface:** the order confirmation, `frontend/src/pages/OrderPage.jsx:164-188` —
the `done` state, and the last screen the customer sees before leaving.

**What it does now.** It shows the store's name, a *Follow my order* link, the
total, where payment goes, and, if they left an address, that an email was sent.

**What it never says is when.** The customer just picked a date at `:260` and a
collection or delivery window at `:270`. `date` and `windowKey` are both still
in state on this screen. Neither is repeated back. For a pickup — the default,
`:43` — the store's whole cost of a forgotten order is a loaf baked for nobody,
and the customer's cue to come and get it is a date they typed and closed the
tab on.

**What to change.** Between the title and the track link, render the commitment
as a plain sentence built from state already on hand:

> **Friday 12 September, 08:00–10:00.** Pickup at 14 Ben Yehuda, Jerusalem.

`data.business` would need the pickup address on the order-form payload
(`backend/routes/marketplace/orders.py:1690` returns the business block already;
adding the street is one field). Then, under it, an *Add to my calendar* link
that builds a `.ics` blob client-side from the same three values — no dependency,
no server round trip, and it plants the cue in the place the customer will
actually be looking on Friday morning. A delivery gets the same sentence with the
window and the address they gave, which also answers "when should I be home?"
without a message to the store.

**Why this and not a reminder email.** The confirmation is the moment the
intention is freshest and the details are still on screen. An email sent later
competes with everything else in the inbox; the calendar entry is the customer's
own artefact, in their own calendar, on the right day.

**What I would expect to see if it worked.** Two things already measurable in
`store_orders` without any new instrumentation, since every status transition is
timestamped: (a) fewer pickup orders still sitting at `ready` twenty-four hours
after their window closed — the uncollected ones; (b) fewer orders whose first
customer-initiated contact after confirmation is a "when is it ready?" message,
visible as track-link opens clustering *before* the window rather than a chat
thread. Both are real queries against real rows. No figure should be shown to
anyone until the query returns one.
