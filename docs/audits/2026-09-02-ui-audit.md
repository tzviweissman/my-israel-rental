## Should fix

### 1. Two of the three response paths bypass the security headers that were just added

`84c6c22` added four headers to `frontend/public/serve.json:12-28`
(`X-Content-Type-Options`, `X-Frame-Options`, `Referrer-Policy`,
`Strict-Transport-Security`). Those headers are applied by
`handler(req, res, CONFIG)` at `frontend/server.js:294`.

Two branches return before ever reaching line 294:

- `frontend/server.js:274-277` - the `/api` proxy added by `b78335c` in the same
  batch. It writes its own response at `server.js:248`
  (`res.writeHead(upRes.statusCode || 502, stripHopByHop(upRes.headers))`) and at
  `:219` / `:258` for the 502 paths.
- `frontend/server.js:281-291` - the preview-bot branch. It writes
  `Content-Type: text/html; charset=utf-8` at `:284-287` and serves markup
  assembled by `fetchPreview(slug)`.

The bot branch is the sharper of the two: it serves HTML built from
business-supplied content, on the site's own origin, with no `nosniff` and no
`X-Frame-Options`. Two commits landed together and one silently narrowed the
other's scope, which is exactly the shape that survives review.

**Fix.** Extract the four headers into a helper and call it as the first
statement of the request handler, above the `/api` check:

```js
const SECURITY_HEADERS = {
  'X-Content-Type-Options': 'nosniff',
  'X-Frame-Options': 'SAMEORIGIN',
  'Referrer-Policy': 'strict-origin-when-cross-origin',
  'Strict-Transport-Security': 'max-age=15552000; includeSubDomains',
};

const server = http.createServer(async (req, res) => {
  for (const [k, v] of Object.entries(SECURITY_HEADERS)) res.setHeader(k, v);
  if (req.url === '/api' || req.url.startsWith('/api/')) { ... }
```

`setHeader` before `writeHead` survives all three paths, and serve-handler will
not duplicate what is already set. Keep the `serve.json` block as-is so the
static path is covered if `server.js` is ever swapped out.

### 3. "nothing you typed was lost" is a promise the code only keeps on one screen

Same three lines as finding 2.

`apiErrorMessage` is a global helper. The draft persistence that would make the
claim true exists in exactly one place, `frontend/src/pages/SignupJoin.jsx:130-139`,
and even there it deliberately excludes the password and the confirmation field
(`SignupJoin.jsx:124-129` explains why, correctly). Every other caller of
`apiErrorMessage` - `Auth.js:118`, `:139`, `:164`, `SignupJoin.jsx:211` - renders
the sentence on a screen with no draft at all. A user who reads "nothing you
typed was lost" and reloads to try again loses what she typed.

The site's standing rule is that a claim comes from something real or the line
does not render. This one is a reassurance rather than a statistic, but it fails
the same test.

**Fix (closes 2 and 3 together).** Cut the clause. It is the em-dash and the
unkeepable promise in one.

```js
// en.js:1634
networkError: 'We could not reach the server. Check your connection and try again.',
// he.js:1594
networkError: 'לא הצלחנו להגיע לשרת. בדקו את החיבור ונסו שוב.',
// apiError.js:86
const fallbackLine = 'Could not reach the server. Check your connection and try again.';
```

If the reassurance is wanted where it is true, add a separate key rendered only
by `SignupJoin.jsx` (`signupJoin.draftSaved: 'Your name, email and phone are
saved on this device.'` / `'השם, האימייל והטלפון נשמרו במכשיר הזה.'`), which is a
statement the code actually backs.

## Improvement of the night

**Mechanism: the peak-end rule, plus arithmetic.** What a person carries out of a
failed session is the peak and the last moment. Both were shaped last night by
`a8afbb1`, which replaced "Authentication failed" with a message that names the
real cause. That was the right fix. It does not reach the reader.

**Surface:** every error toast on the site, and specifically the signup failure
path at `frontend/src/pages/SignupJoin.jsx:211` and `frontend/src/pages/Auth.js:118`.
**File to change:** `frontend/src/index.js:69`.

`<Toaster position="top-right" duration={1500} />`. Every toast on the site is on
screen for **1.5 seconds**.

The new network message is 17 words in English (96 characters) and 15 in Hebrew
(75 characters). Finishing it inside 1500 ms requires **680 wpm** in English and
**600 wpm** in Hebrew. Adult silent reading of prose sits around 240 wpm
(Brysbaert 2019, *Journal of Memory and Language* - cited from memory, worth
verifying, and not load-bearing here: the arithmetic alone settles it, since no
one reads prose at 680 wpm). The message is gone at roughly the one-third mark.

That is the whole failure. On 1 Sep a real person submitted the signup form
thirteen times in three minutes. The screen now has a correct explanation for
her, held up for 1.5 seconds, in the corner of a page whose centre is the form
she is staring at. She re-reads the form, not the corner. Her hypothesis - "my
details are wrong" - is what the *absence* of a visible reason says, whether or
not the copy still says it. The peak was the thirteenth failure and the end was
an ordinary-looking form with nothing on it.

**What to change.** Two lines, in the order of effort:

1. `frontend/src/index.js:69`: `duration={1500}` is a defensible default for
   "Saved" and "Copied". It is not a duration for a sentence. Raise the default
   to `4000`, or leave it and override per call, which is safer for the
   confirmations: `toast.error(msg, { duration: 8000 })` at
   `SignupJoin.jsx:211` and `Auth.js:118`, `:139`, `:164`.
2. On the network branch only (`!err.response`), also hold the message in
   component state and render it as a persistent `role="alert"` block directly
   above the submit button, cleared on the next submit. A transient toast is the
   wrong carrier for information the user needs *while* deciding what to do next;
   a server-side field rejection can stay a toast, because the field is right
   there.

Nothing here is manufactured urgency, and nothing is a new claim: it is the
message that already shipped, left on screen long enough to be read.

**What I would expect to see if it worked.** The measurable is repeat submissions
per visitor per ten minutes on `/join`. It has to be instrumented **client-side**,
using the existing `frontend/src/utils/visitorId.js` - in the incident the POST
never reached the server, so server-side counters cannot see the retries at all,
which is the same blind spot that let this run for three minutes. The claim is
that a burst like thirteen-in-three-minutes shortens, because the retries are
driven by an absent explanation rather than by hope. I have one incident, n=1,
and I am not turning it into a rate. Instrument first.
