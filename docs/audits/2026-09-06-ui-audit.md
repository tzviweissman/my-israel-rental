## Medium

### 1. A video thumbnail with no Cloudinary poster now renders as a broken image, not a video frame

`frontend/src/components/property/ImageGallery.jsx:231`,
`frontend/src/components/ui/thumbnail-carousel.jsx` (`FramedImage`,
no video branch)

The new thumbnail strip builds each thumbnail's `src` like this:

```js
src: m.type === 'image' ? sizedImage(toSrc(m.url), 320) : (videoPoster(toSrc(m.url), 320) || toSrc(m.url)),
```

and `FramedImage` (`thumbnail-carousel.jsx`) unconditionally renders
`<img src={src} .../>`. `videoPoster()` (`utils/cdnImage.js:77-79`)
returns `undefined` for any URL that isn't a Cloudinary
`/video/upload/` asset. When that happens the fallback hands the RAW
VIDEO FILE URL to an `<img>` tag — which cannot decode a video file, so
the thumbnail shows a broken-image glyph instead of a frame.

The code this replaced handled exactly this case
(`git show b330e72^:frontend/src/components/property/ImageGallery.jsx`,
old lines ~145-160): when `videoPoster` was falsy it rendered an actual
`<video preload="metadata" muted>` element, which browsers paint with
the real first frame with no extra work. That fallback did not survive
the port to `ThumbnailStrip`.

**Why this is Medium, not Low or High:** every upload in this app goes
through Cloudinary (`frontend/src/utils/fastUpload.js:167-194` signs
every image and video upload directly to Cloudinary), so a freshly
uploaded property video will always match `videoPoster`'s pattern and
never hits this path today. The risk is anything uploaded before that
was true, or any URL that doesn't match the exact
`res.cloudinary.com/.../video/upload/...` shape the regex-free string
check requires (`video_url` on the property model is an unconstrained
`str | None` — `backend/models.py:205-208` — so nothing stops a
non-Cloudinary URL from being stored). `scripts/check-gallery.mjs`, the
new check for this commit, has zero video coverage (`grep -i video` on
it returns nothing), so this gap is untested as well as unfixed.

**Fix:** give `FramedImage` (or its caller) a video branch — the same
`<video preload="metadata" muted>` fallback the old code used — for any
item whose `src` doesn't resolve to a real poster image, or pass an
explicit `kind: 'video'` down from `ImageGallery` instead of overloading
`src` with a video file's own URL.

## Low

### 2. `collections` has no server-side length cap; `pinned_service_ids` explicitly does, on the same model, in the same file

`backend/routes/marketplace/businesses.py:118-123`

```python
collections: Optional[list[Collection]] = None
# C5 — capped at three by the MODEL, not by the UI. A page where
# everything is featured features nothing, and a cap enforced only in
# a form is a cap that a second client ignores.
pinned_service_ids: Optional[list[str]] = Field(None, max_length=3)
```

The comment right there states the design principle — a cap only in the
form is not a cap. `pinned_service_ids` follows it
(`Field(None, max_length=3)`). `collections` does not: there is no
`max_length` on the list, and `Collection.service_ids` (same file,
`:64`) is `list[str] = Field(default_factory=list)` with no bound
either. `frontend/src/components/dashboard/BusinessShelfEditor.jsx:29`
caps at `MAX_COLLECTIONS = 8` and `cleanCollections` (`:38-46`) slices
`service_ids` to 200 — both client-side only. A raw API call (or any
future second client) can PATCH an arbitrary number of collections, each
with an arbitrary number of ids.

This is pre-existing backend code — `businesses.py` isn't in this diff's
file list — but `BusinessShelfEditor.jsx` is what makes the field
practically reachable by a real business owner for the first time
(outside the demo seed, dead-ends audit 2026-09-03 #10). The blast
radius is narrow — an owner can only bloat their own document, gated by
the existing ownership check (`test_business_shelf.py`'s
`test_someone_else_cannot_arrange_your_page` confirms that check holds)
— but it's the exact gap the sibling field's own comment warns against,
on the feature that just made it live.

**Fix:** `collections: Optional[list[Collection]] = Field(None, max_length=8)` and a `max_length` on `Collection.service_ids`, matching the client constants.

### 3. A new "taken down" badge introduces a third hardcoded red pair instead of reusing the one already in the dashboard

`frontend/src/components/dashboard/MyGigsTab.jsx:614-616`

```js
style={heldByAdmin
  ? { background: '#FDECEA', color: '#B3261E' }
  : { background: 'var(--surface-muted, #F9FAFB)', color: 'var(--brand-muted)' }}
```

`#FDECEA` / `#B3261E` are new to the codebase. A near-identical status
chip already exists with a different pair —
`frontend/src/components/dashboard/BookingChip.jsx:12`:
`{ bg: '#FEE2E2', fg: '#DC2626', ... }` — and most other error states in
`dashboard/` use Tailwind's `red-50`/`red-700` utilities instead of
either. None of these are catastrophic (all are legible dark-red-on-
light-red), but this is the drift the design-system rules exist to
prevent: a fourth ad hoc value where a second copy of an existing one
would do, out of scope for the "existing ~1,275 hardcoded hexes" carve-out
in `CLAUDE.md` because this is new code.

**Fix:** reuse `BookingChip.jsx`'s `#FEE2E2`/`#DC2626`, or better,
promote one pair to a real `--danger-bg`/`--danger-ink` token pair in
`theme-flow.css` now that a second call site exists.
