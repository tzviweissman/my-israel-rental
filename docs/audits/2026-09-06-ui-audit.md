## Should fix

### 2. `ThumbnailStrip` does not do the RTL centring its own header claims. Live on every Hebrew listing page.

`frontend/src/components/ui/thumbnail-carousel.jsx:110-111`:

```js
const target = active.offsetLeft - (el.clientWidth / 2 - active.offsetWidth / 2);
el.scrollTo({ left: target, behavior: reduced ? "auto" : "smooth" });
```

The file header, item 4, says: *"RTL. The strip scrolls, and a scroll offset
means the opposite edge in Hebrew; the centring maths mirrors rather than
sending the strip the wrong way."*

The `rtl` prop is referenced in exactly two places in the file - `:115` and
`:116`, both inside `onKeyDown`. It is never read by the centring effect. In a
`dir="rtl"` scroller, Chrome 85+, Firefox and Safari all put `scrollLeft = 0` at
the **right** edge and run negative leftward, while `offsetLeft` still measures
from the left content edge. The positive `target` computed above is outside the
valid range and is clamped, so the open frame is not centred.

`ImageGallery.jsx:238` passes `rtl={isRtl}`, so this is the property photo strip
in Hebrew - the lead offering's main page.

**Exact fix** - replace `:110-111` with the direction-aware primitive:

```js
active.scrollIntoView({ inline: "center", block: "nearest", behavior: reduced ? "auto" : "smooth" });
```

`scrollIntoView` resolves `inline: "center"` against the element's own writing
direction, so `rtl` is no longer needed by this effect at all.

`frontend/src/components/auth/SignupSphere.jsx:28` and `:62-66`:

```js
const WANT = 36;
...
for (let i = 0; out.length < WANT; i += 1) {
```

## Improvement of the night

**Mechanism: cognitive fluency.** The ease with which something is perceived is
misattributed to its qualities - fluently processed material is judged more
familiar, more true, and better liked, and the judge does not experience the
fluency as an input. It is not one of the five already used here: the halo effect
(2026-09-01), the peak-end rule (09-02), loss aversion (09-03), denominator
neglect (09-04-2) and endowed progress (09-05).

**Surface:** the property photo gallery, on every rental page - the lead
offering.
**File:** `frontend/src/components/property/ImageGallery.jsx:113-129`.

Tonight's `b330e72` replaced `bg-black` letterboxing with `object-contain` over a
blurred, enlarged copy of the photo itself. That was the right call and the
comment defending it is correct: cropping a listing photo removes evidence the
owner chose to show. What it does not resolve is that **the frame's shape is
still a constant while the photo's shape is not.**

`:115` and `:128`:

```js
height:   'min(75vw, 67vh, 620px)',
maxWidth: 'calc(min(75vw, 67vh, 620px) * 1.6)',
```

A fixed 1.6:1 box. Drawn `contain`, the photo's share of that box is arithmetic
on that constant, not an estimate:

| Photo | Share of frame width | Surround |
|---|---|---|
| 3:2 (most phone cameras) | 1.5 / 1.6 = 94% | 6% |
| 4:3 | 1.33 / 1.6 = 83% | 17% |
| 16:9 (video frame) | height-limited | 10% vertical |
| **4:5 portrait** | 0.8 / 1.6 = **50%** | **half the frame** |

A portrait photo is now drawn at half the width it could be, inside a blurred
gutter as wide as itself. Nothing is cropped, which was the goal, but the subject
is smaller and lower-contrast against a busy ground - and portrait is what a
phone produces by default, held the way people hold phones. Fluency is doing the
work either way: a picture that fills its frame cleanly is easier to resolve, and
that ease is read back as a better property.

**What to change.** Take the frame's shape from the photo, the way this codebase
already does one page over. `GigDetail.jsx:303-320` loads the first cover into an
`Image()` and waits up to 1500ms for `naturalWidth / naturalHeight` *before*
first paint, then `:715` applies
`aspectRatio: Math.min(16/9, Math.max(4/5, coverRatio))`, falling back to 16:9 on
timeout. The comment there explains why the wait is worth it: measuring from
`onLoad` instead cost "236px of shift at 375 on every portrait flyer."

Do the same in `ImageGallery`: measure `media[0]` once, clamp to
`[4/5, 16/9]`, and set the frame's `aspectRatio` from it in place of the fixed
`maxWidth` at `:128` - keeping `height: min(75vw, 67vh, 620px)` as the cap so the
frame never outgrows the viewport. Hold that one shape for the whole gallery
rather than re-shaping per slide, which would reintroduce exactly the shift
`GigDetail` bought its 1500ms to avoid. The blurred backdrop stays and does what
it is good at: absorbing the minority of photos whose shape differs from the
first. Most listings are shot in one session on one device, so for most galleries
the surround disappears entirely.

**What I would expect to see if it worked.** A portrait-first listing renders its
photos at roughly twice their current width with no visible gutter, and Cumulative
Layout Shift on the property page is unchanged (the measurement completes before
paint, and the fallback shape is fixed). Nothing is cropped, no copy changes, no
number is asserted anywhere - the only claim this makes to a reader is the
photograph, drawn larger.
