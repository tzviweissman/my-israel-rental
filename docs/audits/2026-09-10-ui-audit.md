## High

### 1. The courier's "Delivered" button regresses the exact contrast bug fixed hours earlier, in a new file the fix couldn't have touched

`frontend/src/components/dashboard/DeliveriesTab.jsx:243`:

```jsx
<button ... style={{ background: 'var(--status-open-bg)', color: 'var(--status-open)' }} data-testid="stop-deliver">
  <Check size={16} /> {t('orders.action.delivered', 'Delivered')}
</button>
```

`--status-open: #2E7D4F` on `--status-open-bg: #E6F4EA` = **4.44:1** — the identical figure named in commit `5d7ac07`'s own message ("the courier's Delivered button was green and 4.44:1"). That commit (09:16) fixed the button in `OrderCard.jsx`/`OrdersTab.jsx`/`CourierRunSheet.jsx`. `e6d0467`, later the same day (20:07), deleted `CourierRunSheet.jsx` and wrote `DeliveriesTab.jsx` from scratch as the courier's new home screen — reintroducing the same low-contrast pair, since the file didn't exist yet when the fix landed. The *second-tap* "Confirm delivered" button in the same file (line 292) correctly uses `var(--action)`/`var(--action-ink)` (black/white, 21:1) — only the first-tap button regressed.

**Impact:** the courier's primary action, on a screen meant to be read on a scooter, fails WCAG AA (4.5:1 required at this text size).

**Fix:** line 243 → `background: 'var(--action)', color: 'var(--action-ink)'`, matching every other post-fix instance of this button.

### 2. Order currency is hardcoded to ₪ in six places, despite the commit whose entire point was per-order currency

`263dc99` ("A website order keeps the store's currency...") added a real `currency` field to orders, validated server-side (`place_website_order` derives it from the store's own `product.currency`, refuses mixed currencies with a 400 — this part is solid). But the frontend never consistently reads it:

- `frontend/src/pages/OrderPage.jsx:229,250,313-315,175` — delivery-fee badge, minimum-order notice, cart lines, checkout total, and post-submit confirmation are all literal `₪`. Only the per-product unit price (line 211) is currency-aware.
- `frontend/src/pages/OrderTrackPage.jsx:141`, `frontend/src/components/dashboard/MyOrdersTab.jsx:64`, `frontend/src/components/dashboard/OrderCard.jsx:88,96`, `frontend/src/pages/OrdersPrintPage.jsx:104` — same hardcoded `₪`.
- `frontend/src/components/dashboard/OrdersTab.jsx:1198-1214` (`MoneyStrip`): sums `o.total` across **all** of a business's orders regardless of `o.currency` and labels the sum `₪`. A business with both ILS (manual orders are server-hardcoded `"currency": "ILS"`, `orders.py:340`) and USD (website) orders can show a mixed-currency sum mislabeled as shekels.

**Impact:** for a USD demo store (the exact case `263dc99` was built for), the customer's own cart total, delivery-fee note, and confirmation all show `₪` next to dollar amounts. This is a "number shown wrong" truthfulness issue, not a cosmetic one.

**Fix:** derive a symbol from the order/product's own `currency` once per store and thread it through the five listed files; have `MoneyStrip` group by currency instead of summing across them.

### 3. `--brand-primary` is now the accent blue, but the page-builder editor uses it as a "solid" fill — reintroducing the exact blue-solid pattern the flow theme exists to remove

`frontend/src/components/dashboard/BusinessPageEditor.jsx:459`:

```jsx
style={device === key ? { background: 'var(--brand-primary)', color: '#fff' } : ...}
```

`--brand-primary: #1C8DD4` (theme-flow.css:51) is the accent color, not the solid-action color — that's `--action: #000000` (theme-flow.css:68), consumed by `.btn-primary`/`.btn-teal`. This is the same trap CLAUDE.md documents for `--gold*` (a token whose *name* no longer matches its *role*): code reading `--brand-primary` as "the solid/primary color" now renders solid blue instead of solid black.

**Impact:** the device-preview toggle (and any future code following the same pattern) shows a solid blue fill, which is exactly "two solid fills" territory CLAUDE.md calls out as unfinished-feeling.

**Fix:** use `var(--action)`/`var(--action-ink)` for any inline "solid/selected" state.

## Medium

### 4. Feature-page copy describes the courier model the same day's later commit replaced

`frontend/src/locales/en.js:718` / `he.js:699`: "Hand a delivery to the friend with the scooter and they get one list: Waze, the items, what is due." This is the phase-3/4 (`058aaf0`) capability-link courier model, written at 09:03 in `32e89b2`. `e6d0467`, later the same day, replaced it: couriers must now have an account, be invited by email, and accept before seeing anything — "no texts, no capability links." The copy was never updated.

**Fix:** update both locale strings to describe invite-and-accept, or soften to avoid implying no-account use.

### 5. The business page's only CTA never uses the solid-black primary button — always the soft-wash accent

`frontend/src/pages/BusinessPage.jsx:502,582,653` and `frontend/src/components/pagebuilder/ServicesBlock.jsx:295` all use `btn-gold` (soft wash); `.btn-primary`/`.btn-teal` appears nowhere in these files. CLAUDE.md's rule is "primary is solid black, accent is the wash, not a second solid" — read together, the single highest-intent action on a business page (repeated in header, mid-page, and the mobile sticky bar) would be expected to be the solid black primary. Not necessarily wrong (there's only ever one CTA visible at a time, so it doesn't collide with anything), but it's a real, repeated deviation from the documented convention and worth a deliberate yes/no rather than leaving it silent.

### 6. Hardcoded `aria-label="Close"` bypasses i18n in the gig-detail lightbox

`frontend/src/pages/GigDetail.jsx:1528`. A Hebrew-UI screen-reader user hears "Close" in English — the same silent-fallback failure class the skill flags for missing translation keys, just via an ARIA attribute instead of visible text, so it won't show up in a visual pass.

**Fix:** `aria-label={t('gigDetail.closeGallery', 'Close')}`, adding the key to both `en.js` and `he.js`.

### 7. Contract-signing links for external signers never expire

`backend/routes/subleases.py:193` — `sign_token` is a strong random UUID4 (unguessable, so not an IDOR issue) but has no TTL, no one-time-use, and isn't invalidated after the contract is signed. `GET /contracts/sign/{token}` and its `/file` variant accept it indefinitely. Anyone who obtains a forwarded link, a shared screenshot, or browser history on a shared device can read — and, before first use, sign — that contract, forever.

**Fix:** expire the token after signing and/or after N days.

## Low

### 8. Order tracker doesn't announce a live status change to screen readers while the tab stays open

`frontend/src/pages/OrderTrackPage.jsx` — the `5d7ac07` fix (per-step `aria-current`/`sr-only` state words) is real and correct for an on-load read, but the page polls every 30s (`REFRESH_MS`) with no `aria-live` region, so a screen-reader user who leaves the tab open won't hear an automatic announcement when status actually changes.

**Fix:** wrap the step list (or add a visually-hidden sibling) with `aria-live="polite"`.

### 9. Lightbox close button and index badge use physical, not logical, positioning

`frontend/src/pages/GigDetail.jsx:1526,1533,1537` — `right-4`/`left-4`/`left-1/2` Tailwind classes won't mirror under RTL. Low severity: a lightbox close button pinned to a fixed screen corner is a common, defensible convention even in RTL UIs, but it should be a deliberate choice, not an accident.
