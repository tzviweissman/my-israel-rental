## Wrong destination

**8. Gig-detail "Back to businesses" button and breadcrumb still whitelist only the old `/services` URL**
`App.js`'s own comment states `/businesses` is now "the name people see" and
the primary URL, with `/services` kept only so old links don't break. Two
places never picked up the rename:
- `frontend/src/pages/GigDetail.jsx:37` —
  `GIG_RETURN_PREFIXES = ['/services']`, used at line 259
  (`useReturnDestination(GIG_RETURN_PREFIXES, '/services')`) and rendered at
  line 673 as a button labelled "Back to businesses" (line 674). Confirmed
  directly (`grep`: still exactly `['/services']`). Most real traffic arrives
  via `/businesses` (`Services.jsx`'s own card-click handlers call
  `saveReturnPath()` before navigating to `/businesses/${gig.id}`), so the
  visitor's actual origin — including their filters
  (`/businesses?category=...&location=...`) — is silently discarded, and the
  button, despite its label, drops them on the bare, filterless `/services`.
  **Fix:** `GIG_RETURN_PREFIXES` should be `['/services', '/businesses']`,
  fallback `/businesses`.
- `frontend/src/components/common/Breadcrumb.jsx:90` —
  `if (p === '/services')` with no `/businesses` branch, so `parseOrigin()`
  returns `null` for the majority of visitors and the breadcrumb that
  `GigDetail.jsx:672` explicitly renders simply never appears for them.
  **Fix:** add a mirrored `/businesses` branch.
- **Minor mirror, lower severity:** `frontend/src/pages/JobDetail.jsx:20` —
  `JOB_RETURN_PREFIXES = ['/businesses/jobs']` whitelists only the *new* URL,
  not `/services/jobs`; falls through to the correct page, just loses filter
  state. Same staleness, opposite direction.

**9. `/chat/:propertyId` and `/payment/success` route guards bypass the app's own return-to fix**
Confirmed directly in `App.js`:
```
385:  <Route path="/chat/:propertyId" element={user ? <Chat /> : <Navigate to="/auth/login" />} />
387:  <Route path="/payment/success" element={user ? <PaymentSuccess /> : <Navigate to="/auth/login" />} />
```
Both use a bare `<Navigate>` instead of the `ToAuth` helper the file defines
specifically to fix this class of bug (comment at `App.js:66-74`, referencing a
prior "#3 and #6" fix) — no `redirect=` is attached, so signing in drops the
user on `/dashboard`, never the original destination.
- **`/chat`:** `backend/utils/email.py:472,549` and
  `backend/routes/admin/chats_nudge.py:370` all build "Open Conversation" email
  deep-links as `{FRONTEND_URL}/chat/{property_id}?with={sender_id}`. Anyone
  opening that email without a live session (different device, cleared
  cookies, work inbox) hits this guard and loses the conversation. Every
  in-app click site (`GigDetail.jsx:648`, `SubleaseDetail.js:79`,
  `PropertyDetail.js:323`, `BusinessPage.jsx:166`) checks auth itself first and
  builds its own `?redirect=` URL, so this specifically affects emailed links
  and any future direct link to `/chat/:id`.
- **`/payment/success`:** `backend/routes/marketplace/subscription.py:276` and
  `backend/routes/payments.py:170` set PayPal's `return_url` to this route with
  `?orderId=&token=&flow=`, which `PaymentSuccess.js:27-29` needs to finish the
  confirmation. A session that expires during the (often multi-minute) PayPal
  redirect hits this guard and loses `flow`/`token`/`orderId` — after login,
  the user lands on `/dashboard` having never seen payment confirmation.
- **Fix:** one-line swap, both routes: `<Navigate to="/auth/login" />` →
  `<ToAuth />`.

**10. `?highlight=` on sublease notifications is read but never acted on**
`frontend/src/components/Navigation.js:275` navigates to
`/dashboard?tab=subleases&highlight=${sublease_id}`. `Dashboard.js:221` reads
`?highlight=` into `highlightBookingId` but only ever passes it to
`BookingsList` (for the `bookings` tab, `Dashboard.js:473`) — `SubleasesTab` is
rendered with no equivalent prop (`Dashboard.js:415`) and never reads
`highlight` itself. The matching `?tab=bookings&highlight=...` case
(`Navigation.js:270`) works correctly, so the gap is specific to subleases: the
user lands on the right tab but the specific item is never scrolled-to or
highlighted.
- **Fix:** wire a `highlightId` prop through to `SubleasesTab` mirroring
  `BookingsList`, or drop `&highlight=` from the sublease notification URL.
