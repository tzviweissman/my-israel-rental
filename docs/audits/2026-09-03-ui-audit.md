## Blockers

### 1. `i18n is not defined` - the jobs board throws on every row it renders

`frontend/src/pages/JobsBoard.jsx:264` and `:267`

`66136e7` replaced `{job.title}` and `{job.description}` with
`localizedTitle(job, i18n)` and `localizedDescription(job, i18n)` inside
`JobRow`. `JobRow` is a module-scope component declared at `:249`:

```jsx
const JobRow = ({ job, onClick, t, locale }) => {
```

`i18n` is not one of its props. It is destructured only inside `JobsBoard`
itself at `:38` (`const { t, i18n } = useTranslation();`), a different function
scope, and the call site at `:238` passes `locale={i18n.language}` - the
**string**, not the instance. There is no module-level `i18n` import in the file
(imports are `:25-35`). So `i18n` at `:264` and `:267` resolves to nothing in
the scope chain and throws `ReferenceError: i18n is not defined` the moment a
single job is rendered.

Confirmed, not inferred:

```
$ eslint --rule '{"no-undef":"error"}' src/pages/JobsBoard.jsx
  264:109  error  'i18n' is not defined  no-undef
  267:100  error  'i18n' is not defined  no-undef
```

The same run over all 23 changed files under `frontend/src` produced no other
real `no-undef` (the rest were browser globals absent from the throwaway config
- `sessionStorage`, `URL`, `requestAnimationFrame`, `IntersectionObserver`).

The empty state renders fine, which is exactly why this can pass a glance: the
board is only broken once there is something on it.

**Fix.** Pass the instance the same way `t` is already passed. At `:234-241`:

```jsx
<JobRow
  key={j.id}
  job={j}
  t={t}
  i18n={i18n}
  locale={i18n.language}
  onClick={() => { saveReturnPath(); navigate(`/businesses/jobs/${j.id}`); }}
/>
```

and at `:249`:

```jsx
const JobRow = ({ job, onClick, t, i18n, locale }) => {
```

`locale` stays - `timeAgo(job.created_at, t, locale)` at `:265` uses it.

Worth a second look separately: `eslint-config-react-app` sets `no-undef` to
`error`, so this should have failed the build. It did not. Whatever runs lint in
CI is either not running on this path or not failing on it.

### 2. Two owner buttons can open, and then save over, a different business

`frontend/src/pages/GigDetail.jsx:918` and `:925`
`frontend/src/components/dashboard/MyBusinessesTab.jsx:77` and `:84`

```jsx
navigate(`/dashboard?tab=my-businesses&services=${gig.business_id || 1}`)
navigate(`/dashboard?tab=my-businesses&details=${gig.business_id || 1}`)
```

`1` is not an arbitrary placeholder - it is the sentinel the backend already
emits at `backend/routes/onboarding.py:156,162,173,180` (`&details=1`), where it
correctly means "any of this owner's businesses", because that checklist is
computed across all of them (`_business_items`, `:103-119`). The receiving code
honours it at `MyBusinessesTab.jsx:77`:

```jsx
const target = items.find((b) => b.id === wantDetails) || items[0];
```

Business ids are UUIDs (`backend/utils/businesses.py:95`,
`"_id": str(uuid.uuid4())`), so `1` never matches and the `|| items[0]` branch
always takes it.

That is right for the checklist and wrong here. `GigDetail` has one specific
business in mind. If `gig.business_id` is ever absent, the owner presses "Edit
hours, areas & logo" on listing B and gets the details form for whichever
business sorts first - pre-filled with that business's data, and `save()`
(`BusinessDetailsForm.jsx:126-158`) PUTs to that business's id. The form's
header is the literal string "Business details" (`:218-220`); it never names
which one, so there is nothing on screen to catch it.

I could not establish that any live gig lacks `business_id` -
`backend/routes/marketplace/gigs.py:444` sets it on every create - so this is a
latent path, not an observed incident. The `|| 1` was written by someone who was
not sure either.

**Fix.** Three edits. Do not send the sentinel from a place that knows the id:

```jsx
// GigDetail.jsx:918 / :925 - render the block only when there is an id
{user?.id && user.id === gig.provider?.user_id && gig.business_id ? (
  ... navigate(`/dashboard?tab=my-businesses&services=${gig.business_id}`)
  ... navigate(`/dashboard?tab=my-businesses&details=${gig.business_id}`)
) : ( ...View profile... )}
```

and make the fallback explicit rather than positional, so the sentinel still
works and a wrong id does nothing:

```jsx
// MyBusinessesTab.jsx:77 and :84
const target = wantDetails === '1' ? items[0] : items.find((b) => b.id === wantDetails);
if (target) setDetailsBiz(target);
```

Then give the modal a subtitle so the question cannot arise again -
`BusinessDetailsForm.jsx:218-220`:

```jsx
<h2 className="text-base font-bold" style={{ fontFamily: 'var(--font-head)', color: 'var(--ink)' }}>
  {t('businesses.editDetails', 'Business details')}
  <span className="block text-xs font-normal" style={{ color: 'var(--brand-muted)' }} dir="auto">{b.name}</span>
</h2>
```

### 3. The new logo upload has no visible keyboard focus

`frontend/src/components/dashboard/BusinessDetailsForm.jsx:249-263`

The control is a `<label className="... cursor-pointer">` wrapping
`<input type="file" className="sr-only">` (`:260`). A `<label>` is not
focusable, so the only tab stop is the input. Tailwind's `sr-only` is
`position:absolute; width:1px; height:1px; overflow:hidden; clip:rect(0,0,0,0)`
- the element stays focusable but its painting, including its outline, is
clipped to nothing.

The global rule that normally saves this - `frontend/src/App.css:550-556`,
`input:focus-visible { outline: 2px solid var(--focus-ring); outline-offset: 2px }`
- does fire, and is drawn inside a 1×1 clip rect. A keyboard user tabbing
through the form gets no indication that the logo control is focused. WCAG 2.4.7
(A). This is the third variant of the same defect the 2026-09-01 audit reported
at `ItemFilters.jsx:296` and the board documents against itself at
`RequestsBoard.jsx:604`.

The rest of the repo does not use this pattern. `AddPhotoNudge.jsx:82`,
`BulkPhotosModal.jsx:63` and `QrShareCard.jsx:203` all use
`className="hidden"` on the input plus a real `<button>` that calls
`fileRef.current.click()` - `display:none` is not focusable, so there is no
invisible tab stop and the button carries the focus ring.

**Fix, matching the house pattern:**

```jsx
const logoRef = useRef(null);
...
<button
  type="button"
  onClick={() => logoRef.current?.click()}
  disabled={uploadingLogo || saving}
  className="inline-flex items-center gap-1.5 px-3 py-2 rounded-lg border text-xs font-semibold"
  style={{ borderColor: 'var(--brand-border)', color: 'var(--brand-primary)' }}
>
  {uploadingLogo ? <Loader2 size={14} className="animate-spin" /> : <ImagePlus size={14} />}
  {form.logo_url ? t('businesses.logoReplace', 'Replace') : t('businesses.logoUpload', 'Upload a logo')}
</button>
<input ref={logoRef} type="file" accept="image/*" className="hidden" onChange={pickLogo} data-testid="biz-details-logo-input" />
```

`button:focus-visible` is not covered by the `App.css:550` selector list, so add
`button` to it, or put `focus-visible:outline focus-visible:outline-2` on this
button.

### 4. The listing hero resizes itself after the image loads

`frontend/src/pages/GigDetail.jsx:646` with `:277` and `:650-657`

```jsx
style={{ aspectRatio: coverRatio ? Math.min(16/9, Math.max(4/5, coverRatio)) : 16/9 }}
```

`coverRatio` starts `null` and is set from `naturalWidth / naturalHeight` in the
image's `onLoad`. So the box lays out at 16:9, the image arrives, and the box
becomes as tall as 4:5. Everything below the hero moves down, after paint, on
every portrait flyer - which the comment at `:270-276` says is the common case
here.

At 375 with the page's 16px side padding (343px of content width): 16/9 is 193px
tall, 4/5 is 429px. **+236px of shift.** `max-h-[78vh]` does not catch it - 78%
of an 812px viewport is 633px. I did not measure the desktop column width, so I
am not quoting a desktop number.

The reason this is worth fixing rather than accepting is that the information
needed to avoid it already exists and is thrown away.
`frontend/src/utils/fastUpload.js:116` returns Cloudinary's full response, which
carries `width` and `height`; `uploadOneFile` at `:253` narrows it to
`return res.url`.

**Fix.** Persist the shape at upload and read it at layout, so the box is
correct on first paint:

1. `fastUpload.js:253` - return `{ url: res.url, width: res.width, height: res.height }`, or add a sibling that does, and store `cover_w` / `cover_h` on the gig alongside the URL.
2. `GigDetail.jsx:646` - `aspectRatio: gig.cover_w && gig.cover_h ? clamp(gig.cover_w / gig.cover_h) : 16 / 9`, and delete `coverRatio` (`:277`) and the `onLoad` (`:650-657`).

Until (1) lands, revert `:646` to the fixed `aspect-video` it replaced. A
constant wrong-ish shape beats a shape that changes under the reader.

### 6. The plural sweep missed the key twelve lines above the one it fixed

`frontend/src/pages/RequestsBoard.jsx:317-319`

`fbe33c7` converted `myCount`, `renewedTimes`, `chatsOpened` and `expiresIn` to
real i18next plural keys, and its comment at `:326-334` explains precisely why a
hand-written ternary at one call site leaves the other call sites broken. Nine
lines earlier, in the same component, the identical shape survives:

```jsx
{r.contact_count === 1
  ? t('requests.responsesOne', '1 response')
  : t('requests.responses', '{{n}} responses', { n: r.contact_count })}
```

```js
responses_other: '{{count}} פניות',
```

```jsx
// RequestsBoard.jsx:317-319
{t('requests.responses', '{{count}} responses', { count: r.contact_count })}
```

## Improvement of the night

**Mechanism: loss aversion, restricted to a loss that is real.**

**Surface:** the per-business completeness panel on the dashboard.
**File:** `frontend/src/components/dashboard/BusinessCompleteness.jsx:30-57`
and `:71`.

The panel currently argues from absence: *"Your page is 0% complete"*, then
*"Add a logo"*, *"Write a description"*. Its own header comment
(`:18-21`) explains, correctly, why it does not do more:

> NO invented statistics. The spec is explicit and it is right: nobody has
> measured what a logo does to enquiries here, and "businesses with photos get
> 3x more customers" would be a number we made up to create urgency.

That ruling stands. What has changed is that the honest version of the same
sentence is now available, and was not when the rule was written.

`backend/utils/view_tracking.py:93-135` records a view every time a business
page is opened. It has two properties that matter here. It drops the owner's own
visits (`:102-104`, *"The owner looking at their own listing is not demand"*),
and it dedupes per visitor per Israel calendar day (`:120-131`), so a count is
distinct people, not refreshes. `businesses.py:661-665` already calls it on the
public business page. `il_day_window(days)` at `:138-144` is the window helper.

So the panel can say the true thing:

> **31 people opened your page in the last 30 days.** It has no photo.

That is loss aversion where the loss actually occurred: 31 real strangers
arrived at this business and left without seeing what its work looks like. It is
not manufactured scarcity - there is no countdown, no "3 left", no deadline. It
is not an extrapolation, a benchmark, or a claim about what a logo *would* do.
It is a count of something that happened, sitting next to the thing that was
missing while it happened.

It also does what the spec's own compromise line
(`docs/onboarding-tutorial-spec.md:43`, *"Visitors decide in about a second"*)
was reaching for, without that line's problem: "about a second" is an unsourced
generalisation about people in general, and "31 people" is a fact about this
owner's page.

**What to change.**

1. Add `GET /businesses/{id}/view-count?days=30` returning
   `{"views": n, "days": 30}` from `view_tracking` scoped to the business,
   owner-only. `il_day_window(30)` gives the cutoff; the collection is already
   indexed on `entity_id`.
2. `BusinessCompleteness.jsx:71` - render the line **only when `views > 0` and
   at least one item is undone**. Zero views means the sentence is either
   meaningless or discouraging, and a complete page has nothing to be told.
   One clause per undone item, at most one line, above the existing bar.
3. The clause names the gap, not a consequence: *"It has no photo"*, *"It does
   not say what you do"*. Never *"you are losing customers"* - that is the
   inference, and it belongs to the reader.
4. Hebrew needs a real plural (`_one` / `_two` / `_other`) with `count`, per
   finding 6.

**What I would expect to see if it worked.** The measurable is the rate at which
a business with a non-zero view count and an undone item completes that item
within seven days of first seeing the line, against businesses whose count is
zero (who never see it). Both cohorts exist already and the data to split them
is the same query. I have no baseline for that rate and am not inventing one -
instrument before shipping, or treat it as an honesty fix on its own terms,
which it also is: the panel currently withholds from an owner a number the site
has been keeping about their own page.
