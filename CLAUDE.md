# CLAUDE.md

Guardrails and project knowledge for working in this repo. Read this before making changes.

## What this is

MyIsraelRental — a rental/marketplace web app. FastAPI backend (`backend/`) + React (CRA/craco) frontend (`frontend/`). MongoDB Atlas for data, Cloudinary for media and private contract storage, Google Identity Services for sign-in, the direct Anthropic API for LLM features (translation, CSV mapping, bulk extraction). Deployed on Railway. Migrated off Emergent (formerly hosted there) in July 2026 — see `docs/emergent-exit-checklist.md` for what that involved and what's still outstanding.

**Offerings:** property rentals (long/short-term, vacation), a two-sided local **services marketplace** (hire/offer pros), and a **Requests board** (post what you're looking for; owners/pros respond via chat).

**Positioning — read before writing any copy or designing any page:**

- **Rentals are the lead offering** (reinstated by Tzvi, 2026-08-18, reversing the services-first ruling made earlier the same day). Where a page, hero, nav or campaign has to choose what to put first, rentals come first; the services marketplace is equally supported. The existing Stays -> Services -> Marketplace ordering across the nav, /join and the boards is correct as built — do not reorder it.
- **This site is NOT aimed at property owners.** It serves *anyone with something to offer or something they need*: service businesses (cleaners, movers, plumbers, electricians, tour guides, handymen…), property owners and managers, renters, and buyers of services. Never write copy, nav labels, onboarding or marketing that addresses "owners" as the default audience — that language excludes the majority of the people the site is for.
- **Standing supply-side CTA:** *"Add your business, free"* / *"reach more customers"*. A comma, not a long dash (Tzvi, 16 Sep 2026; the long dash is banned by the copy rules in `brand/voice.md`). Free to list, free to be found, no commission. The equivalent for property is one option among several, not the primary framing.
- Consequence for existing surfaces: the `/why-host` page, the join/role-picker ordering, and the nav CTA need to be checked against this. Services-first, business-owner-inclusive, owner-neutral. **The home page is exempt.** Since 15 Oct 2026 it is `pages/HomeNext.jsx`, live at `/` (and at `/home-preview` as the lab copy): an Old City film with the live counts that breaks into tiles of real listings (`components/home/HomeOpening.jsx`, tiles from `/api/home/opening-tiles`), then the headline "Stays, local businesses and restaurants across Israel" with Tzvi's services line "Grow. Build. Any revenue stream" under it, all on a golden-hour ground (sky into Jerusalem-stone sand) that Tzvi chose over plain white. The pages it replaced were exempt the same way: `pages/HomePreview.jsx` (19 Sep, still in the repo) and `pages/Home.js` (18 Aug, in git history). Apply the positioning to every other surface.

**Discontinued — do not surface or build for:** (1) document / government "paid services" (Arnona discount, name change, document filing, Bituach Leumi benefits) — related code may still exist behind the `DOCUMENT_SERVICES_ENABLED` flag; keep it off and clean it up separately, don't extend it; (2) **storage rentals** — the `storage` rental_type still exists in code (e.g. `property.storageType` labels, rental-type maps); don't show it in new UI or marketing, and clean it up separately.

## Before making changes

- **Business sites have a commit check** (Tzvi, 24 Oct 2026: "the rules get skipped a lot"). `.githooks/pre-commit` refuses a commit that touches a site in `scrollcraft/builds/` unless `check-rules` and `check-concept` pass for it, and refuses a live page in `frontend/public/pages/` that differs from what `scripts/publish-page.mjs` wrote (edit the build, then republish; publishing runs fits, site and motion). Turn it on in every clone or worktree with `git config core.hooksPath .githooks`. Never commit with `--no-verify` to get past it: fix the site. `node scripts/publish-page.mjs <folder> <slug> --check` lists every problem without publishing.
- **Look for existing code first.** Check `backend/routes/` and `backend/utils/` before adding a new backend module; check `frontend/src/components/` and `frontend/src/utils/` before adding a new frontend one. Don't duplicate what's already there.
- **Guard costly or irreversible operations.** Confirm before: calls that spend real API credit (Anthropic, Cloudinary uploads at scale), writes to the production Atlas database, `git push`, and anything that triggers a Railway deploy. A dry run first is usually the right move when a script is about to touch production data.
- **Ask before broad edits to this file or other standing config** (`.gitignore`, `railway.json`, `nixpacks.toml`, CI config). These are load-bearing — a wrong edit breaks the build silently.
- **Document what you learn.** When something fails in a non-obvious way (a rate limit, a platform quirk, a wrong assumption), write it down — in this file if it's a standing gotcha, in `docs/` if it's part of a larger effort, or as a code comment if it's local to one function. Future sessions (yours or not) shouldn't have to rediscover the same failure.

## Secrets — hard rules

- Real secrets live only in `backend/.env` / `frontend/.env` (gitignored). `.env.example` files are the checked-in template — keep them in sync when a new var is added, but never put a real value in them.
- **Never print a secrets file or a full variable dump to the terminal or into a response.** `cat`, `cat -A`, and `railway variables list` (no `--kv`, but it *still* shows raw values by default) will all put every secret in plaintext into the transcript. If you need to check a var is *set*, check for presence/key names only, or check application behavior (e.g. a health-check boolean), never the raw value.
- If a secret does end up printed or pasted into chat, say so plainly and get it rotated — don't let it linger unspoken.
- Frontend `REACT_APP_*` vars are **public** by design (CRA bakes them into the JS bundle at build time) — never put a real secret in one.

## Railway deploy — gotchas learned the hard way

- **CRA env vars are baked at build time.** Set `REACT_APP_*` vars on the frontend service *before* triggering a build/deploy, or the old (or empty) values ship in the bundle. Changing them requires a rebuild, not just a restart.
- **The Railway CLI's project link is directory-scoped.** `railway link` writes state relative to the current working directory. Run `railway link` and the command that needs it (`variable set`, `volume add`, etc.) from the *same* directory in the *same* command chain — `cd`-ing away between calls loses the link.
- **Git Bash mangles `/`-prefixed arguments** (like `/app/private_contracts`) into Windows paths before Railway's CLI sees them. Prefix the command with `MSYS_NO_PATHCONV=1` whenever passing an absolute Unix-style path as a CLI argument.
- **Railway's Root Directory setting is dashboard-only** — no CLI flag on `service add` or `service source connect` sets it. Create the service via CLI or dashboard, then set Root Directory by hand in Settings → Source.
- **Service names in the dashboard don't have to match what you typed when creating them** — Railway may auto-name from the GitHub repo. Check `railway service list --json` (or the dashboard) for the real name before scripting against it; don't assume.
- **Project/service names can change** (someone renames it in the dashboard) but the project ID doesn't. Prefer linking by `-p <project-id>` over project name for anything scripted.
- **CRA's `npm start` is a dev server** — never the production start command. `frontend/railway.json` builds the static bundle and starts `node server.js`, which serves it (and gives link-preview crawlers real OG tags — see the top of `frontend/server.js`). Don't revert to `npm start` for deploy, and don't swap the start command back to `npx serve -s build` without reading that file first: `serve` cannot vary on User-Agent, which is the one thing `server.js` exists to do.
- **`nixpacks.toml` IS NOT READ. Both services build with RAILPACK**, chosen in the Railway service settings, and a builder set there overrides the `"builder"` field in `railway.json`. Railpack picks its own commands and prints the plan at the top of the build log — read that, never the toml, to know what actually runs. This bit twice: `frontend/nixpacks.toml` specified npm while the build ran yarn (deleted 27 Aug 2026), and `backend/nixpacks.toml` still declares the `tesseract-ocr` apt packages that the contract OCR path needs — they are not installed, and the failure is silent. See `docs/railway-deploy.md`.
- **Frontend install needs `--legacy-peer-deps` LOCALLY** — `react-day-picker@8.10.1` declares a peer on `date-fns ^2||^3`, but the app pins `date-fns ^4`, so a plain `npm install` aborts. The deploy does not need it: Railpack installs with `yarn install --frozen-lockfile`, and yarn 1 does not enforce peer ranges. There is no `yarn.lock` in the repo, so the deploy resolves from `package.json` and never reads `package-lock.json` — a dependency ships because it is declared in `package.json`, nothing else.
- **Set Root Directory BEFORE the first deploy, or the start command is guessed and sticks.** A service created from a repo without a root directory builds from the repo root, never sees `backend/railway.json`, and Railpack invents a start command — for FastAPI it guesses `uvicorn main:app`, which crashes with `Could not import module "main"` even after the root directory is fixed, because the guess was baked at build time. Setting `startCommand` explicitly on the service is the reliable fix; don't rely on `railway.json` being discovered.
- **Never put a volume back on the backend.** A service with a volume cannot run two deployments at once, so every update hung requests for a minute or two ("Could not reach the server" while saving a business, 18 Oct 2026). The contracts volume was removed that day once every contract lived in Cloudinary (see Contract file storage), and a test redeploy then answered every request. Also set on the services (dashboard, not `railway.json`): watch paths `/backend/**` and `/frontend/**`, so a change to one side or to docs does not restart the other, and 20s overlap and draining on both. If the API is ever unreachable, the proxy in `frontend/server.js` answers "The site is updating".
- **Creating a service with a branch does not necessarily deploy that branch.** The MCP `create-deployment` (and the dashboard's repo picker) can trigger the first build from the repo's default branch even when another branch was named — the service config will *say* the right branch while the deployment metadata says `main`. Always check `list-deployments` → `meta.branch` after creating, and pin it with `railway service source connect --repo <owner/repo> --branch <branch> --service <name>`, which does take effect and triggers a correct deploy.
- **A push whose last commit is a merge can skip the backend.** Watch paths are checked against the pushed head commit's own changes, so a branch commit touching `backend/` followed by a merge of `origin/main` (which brings in only frontend files) deploys the frontend and marks the backend SKIPPED, leaving the backend change unshipped with no error (28 Oct 2026: the page editor's "add a line" and another session's Stays change both sat undeployed). After pushing backend work, check `railway deployment list --service "my-israel-rental Backend"` shows a new build, not SKIPPED; merge main first and commit the work on top, so the head commit carries the backend files.

## Contract file storage — do not regress this

Signed contracts and uploaded contract templates are **personal/legal documents** and must never be reachable through the public static file mount:

- They are written to `backend/private_contracts/` (`/app/private_contracts` on Railway), which is only a cache: since 18 Oct 2026 there is no volume there and the disk is wiped at every deploy. The durable copy is the Cloudinary one below.
- **Since 18 Oct 2026 every contract is kept in Cloudinary** as a `raw` + `type=authenticated` asset (verified: unsigned fetch → 401), and the server's disk is only a cache. The rule lives in `utils/contract_files.py`: after writing a file to `CONTRACT_DIR`, `await keep_contract_file(path)` before the database points at it (it refuses the request with a 503 if Cloudinary will not take it); to read, `await ensure_contract_file(stored, public_id=...)`, which fetches the file back into `CONTRACT_DIR` when this copy of the server has not seen it; to delete, `forget_contract_file(stored)`. The Cloudinary id is derived from the filename (`myisraelrental/contracts/<filename>`); rows migrated in July also carry their own `*_public_id`. Fetching uses `private_download_url`: a signed delivery URL is refused (401) for these assets, which silently broke every Cloudinary read until this was found. At startup on Railway, `mirror_local_contracts()` copies anything still only on disk.
- Every contract read goes through a permission-checked endpoint (`/bookings/{id}/signed-contract`, `/properties/{id}/contract-file`, `/contracts/download/{id}`) that verifies the caller is a party to that contract (owner, renter with a matching booking, or admin) before serving bytes. Do not add a route that serves a contract file directly from a public static mount — that exact bug existed three separate times before this was fixed (see `docs/emergent-exit-checklist.md`) and cost one contract permanently (Emergent's ephemeral disk wiped it before the fix landed).

## Local dev

- **Never make Tzvi sign in to test a build.** Open every local preview with `?as=owner` on the URL (also `renter`, `provider`, `admin`), e.g. `http://localhost:3210/dashboard?tab=orders&as=owner`. It signs in as a persistent local test account (`dev-owner@local.test`) and drops the param. Needs `DEV_AUTOLOGIN=1` in `backend/.env` and a localhost `MONGO_URL`; the endpoint is a 404 otherwise, and the frontend hook is dead outside `NODE_ENV=development`. Never set the flag on Railway.

- **Run pytest from `backend/`** (`backend/.venv/Scripts/python -m pytest tests/...`), not the repo root: from the root nothing puts `backend/` on the import path and most of the suite fails to collect, which reads like hundreds of real failures (site audit 27 Sep). Tests that need the live API skip, not fail, when it isn't running.

See `backend/.env.example` and `frontend/.env.example` for the full list of variables and what each does. Local dev typically runs a local MongoDB rather than pointing at production Atlas — check `backend/.env`'s current `MONGO_URL` before assuming which database you're touching, especially before running any migration or backfill script.

## Design system (locked) — do not reinterpret

The brand and UI are locked. When building or changing any UI, treat these as the source of truth and **copy exact values — never re-derive, "improve", or invent** colors, spacing, radii, or component styles.

- **Source of truth files:** `brand/design-tokens.css` (import it; reference its CSS variables everywhere — no hardcoded hex/spacing in components), the two design mockups `home-redesign-preview.html` and `wanted-board-preview.html` (match them section-for-section), the logo assets in `brand/`, and `brand/inspiration/` for the intended premium feel. Full build spec: `docs/redesign-and-wanted-board-prompt.md`. Per-phase definition-of-done: `docs/acceptance-checklist.md`.
- **Palette — REPLACED 3 Sep 2026 by the "flow" theme** (Tzvi: "there's blue and white and tan, each part seems separate"). The values live in `frontend/src/styles/theme-flow.css`, which loads LAST and overrides `design-tokens.css`. Read that file's header before changing any colour; the two paragraphs at the top explain why two of the supplied variables could not be used as written.
  - Ground: white `#FFFFFF`, with `#F9FAFB` as the ONLY alternate surface. Sections are separated by a `#E3E3E3` hairline, never by a different coloured block — that alternation is exactly what was removed.
  - Ink `#111827`; muted text `#666666`.
  - Accent (links, icons, focus, chips) `#167AB8`, dark and deep `#0F5E8F`; soft wash `rgba(36,175,235,.33)` with `#111827` on it. The supplied accent `#1C8DD4` was moved one step darker on 5 Oct 2026 (Tzvi's choice): it was 3.61:1 on white and under white text, and an axe sweep found 164 unreadable spots. Text on a solid accent fill is white, never ink (3.8:1).
  - Solid actions are **black** `#000000` with white text.
  - **The `--gold*` names now hold the accent blue**, including `--gold-text-on-light`, which is defined in `App.css` and is what every listing price reads. They kept their names because ~200 call sites say `var(--gold)` meaning "the accent"; renaming them is a sweep, not a theme change. The only gold left is the logo mark, which is an image.
  - **Green is still functional only** (status/verified/available — `#2E7D4F` on `#E6F4EA`, verified `#1F8A50` on `#E3F3EA`) — never a brand accent or button color.
  - The previous palette (blue `#1E5F8C`, gold `#C9A227`, limestone `#EFE9DC`) is what the five `*-preview.html` mockups still show. Where a mockup and the theme file disagree about COLOUR, the theme file wins; the mockups remain the source of truth for layout.
  - **Theme experiments are scoped to `/home-preview` only** (Tzvi, 3 Sep 2026, after a trial palette reached the live home page for ten minutes). `pages/HomeNext.jsx` puts `theme-preview` on `<body>` **only when served at `/home-preview`**; the same page is the live home page at `/` without it. (Its golden-hour ground lives under `.hn` in `styles/home-next.css` and is the approved look of the home page only, not a site theme.) Never set `theme-preview` on `/`; any theme under test is written entirely under `body.theme-preview` (`frontend/src/styles/theme-neon.css` is the worked example) and `scripts/test-theme-scope.mjs` fails on a rule that escapes it. Only `theme-flow.css` is global, because it is the approved site palette. Promoting a theme to the whole site is a separate, explicit step.
- **Type:** Playfair Display headings, Manrope body; Frank Ruhl Libre + Assistant under `[dir="rtl"]`. Every page must work LTR and RTL. **RTL font gotcha:** ~69 headings across ~45 files set `style={{ fontFamily: 'Playfair Display' }}` inline; inline styles beat `[dir="rtl"] h1{…}`, and Playfair has no Hebrew glyphs, so RTL headings silently fall back to a system serif. Fix is in `brand/design-tokens.css` — RTL swaps the font *variables*; any heading you touch must read `fontFamily: 'var(--font-head)'`, never the literal face. Verify via a heading's computed `fontFamily` in RTL.
- **Buttons, under the flow theme:** primary (`.btn-primary`/`.btn-teal`) is **solid black with white text**; the accent button (`.btn-accent`/`.btn-gold`) is the **soft blue wash with ink text**, not a second solid — two solid fills in one row is half of what "nothing flows" meant. **Exception:** over a hero photo the CTAs are still solid white (`.btn-white`) + outline-white (`.btn-outline-white`) by design.
  - This line said *frosted glass-gold with white text* until 29 Aug 2026, describing a treatment the CSS had already replaced. Frosted takes a tint from whatever is behind it, so on the limestone pages it went **lighter** exactly where white text needed it dark — measured **1.88:1**, against a 4.5:1 minimum, with a text-shadow disguising it. It read fine only on the dark hero (~4.85:1), which is why it survived review. Ink on solid gold is **6.71:1 on both** surfaces because a solid fill takes no tint. The rationale and the measurements live in full above the rule in `design-tokens.css`; do not reintroduce the frosted version without re-measuring on a light background.
- **Gold on dark:** use `--gold` (#C9A227) on dark surfaces; `--gold-lg` (#A9831C) is for large/display gold on **light** only (it's ~3.3:1 on dark).
- **Scope of "no hardcoding":** copy exact token values in **new/changed** UI; do not refactor the ~1,275 existing hardcoded hexes app-wide. The hero (`docs/hero-cinematic-spec.md`) uses literal values on purpose — copy them verbatim; that's the one intended exception.
- **shadcn token collision (load-bearing):** `frontend/src/index.css` defines `--primary`, `--border`, `--muted` as HSL triplets used via `hsl(var(--…))`. `brand/design-tokens.css` therefore namespaces brand colors as `--brand-primary`/`--brand-border`/`--brand-muted` and must be imported **after** `index.css`. Never redefine those three shadcn names as hex — `var(--primary)` would return an HSL triplet, `background:var(--primary)` gets dropped, and primary buttons silently lose their fill. When porting preview CSS, rewrite `var(--border)`→`var(--brand-border)`, `var(--muted)`→`var(--brand-muted)` (`--teal*`, `--gold*`, `--ink`, `--bg`, `--surface` are safe).
- **Icons:** the mockups' `<use href="#i-…">` are placeholders — implement with `lucide-react` (mapping in `docs/hero-cinematic-spec.md`). **Scroll reveal** must use the fail-safe `.js-reveal` pattern (content visible if JS doesn't run). **Verify with `scripts/screenshot.mjs`**, not by stalling for a human screenshot.
- **Logo:** nav = navy rounded tile holding `brand/logo-mark.png` + "MyIsraelRental" wordmark; footer uses the dark logo variant.
- **Feel:** premium/editorial — generous whitespace, large serif headings with a single gold accent word, soft layered shadows, gentle hover lifts, slow scroll reveals (respect `prefers-reduced-motion`). Restraint with gold; most of the page is neutral with blue structure.
- **Verify visually before claiming done.** After a UI change, run the app, screenshot the page, and compare against the matching mockup; fix differences before reporting complete. If you can't screenshot, ask for one — don't guess. Work one section/component at a time and show a diff.
